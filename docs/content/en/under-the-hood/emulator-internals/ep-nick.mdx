# NICK: A Picture Built Slot by Slot

Ask an Enterprise where its screen is, and it has no answer. There is no screen address, no mode
register, no fixed resolution. Instead a program writes a little table into memory that says, block
by block down the frame, what each group of lines should be: text here, a bitmap there, 256 colours
for twenty lines, a different palette on every line if you like. The video chip, NICK, reads that
table again on every single line, and draws whatever it says.

That makes NICK one of the most flexible video chips of its time, and it is why the details matter in
practice. A game that splits the screen, a demo that changes colours on every line, or a program that
simply wants its writes to video memory to be fast all depend on when NICK reads what, and on when it
lets the CPU in. You should know what a scan line and a frame are first:
[How a television draws a picture](/en/under-the-hood/emulator-internals/crt-display/) explains them.

## The road ahead

We start with the two clocks of the machine and the slot, NICK's unit of time, which NICK and the CPU
share. Then we stretch the slot out into a line of 57 and see what NICK does in each. The line
parameter block and the table built from it come next: this is the heart of the chip, and the reason
the Enterprise has no fixed screen. After that we follow the bytes from memory to the screen and meet
the one-slot delay between a fetch and its pixels. The last stop is the CPU's side of the bargain, the
clock stretch that holds it back whenever it touches video memory.

<Callout type="info">
The numbers are for an Enterprise 128 running EXOS 2.1, with the line parameter table EXOS builds at
power-on; the Enterprise 64 draws the same way. The behaviour described is Klive's emulated machine,
checked against the hardware's documented design by Klive's tests.
</Callout>

## Two clocks that never meet

The Z80 runs at 4 MHz, from an 8 MHz crystal. NICK runs from an oscillator of its own, at
14,237,536 Hz: exactly 912/284 times the PAL colour subcarrier, so that one line of 912 NICK clocks is
284 subcarrier cycles. The two frequencies have no small common multiple. Over a long run they drift
past each other forever, and a CPU instruction can start anywhere relative to NICK's work.

Here is the twist: **NICK makes the CPU's clock.** It divides the 8 MHz crystal by two to get the
Z80's 4 MHz, and it can hold that clock still when it needs the CPU to wait. It holds it for whole
periods of the 8 MHz crystal, so the CPU is delayed in **half-T steps** of 125 ns. Keep that in mind;
it comes back at the end.

## The slot

NICK counts its clocks in groups of sixteen, called **slots**. A slot lasts 1.124 µs, which is 4.495
T-states of the CPU, and NICK shows 16 pixels in it, one per NICK clock.

The memory is shared, so the slot is shared too. NICK uses clocks 0 to 4 for its first read and 5 to 9
for its second, and **clocks 10 to 15 are the Z80's window**: the only time the CPU may touch video
memory or NICK's ports.

Two reads a slot is NICK's whole memory budget. Everything it shows, the description of the line
included, has to fit into those reads.

## A line of 57 slots

A line is **57 slots**, 912 NICK clocks or 64.06 µs (256.2 T-states). NICK does not spend them all on
the picture:

- **Slots 0 to 7** read the line's description, two bytes a slot: the 16-byte line parameter block of
  the next section.
- **Slots 8 to 53** are display fetches: here NICK reads the picture's bytes, but only between the
  line's margins.
- **Slots 54 to 56** refresh the dynamic RAM, and slot 56 resets the slot counter.

The television signals ride on the same count. Horizontal sync is on in slots 0 to 3 and the colour
burst in slots 6 to 9, and the picture is **blanked** from slot 56 through slot 9: those slots send
colour 0 whatever the margins say. So 46 slots, 10 to 55, can show anything at all, 736 pixels.

The **margins** are slot numbers. Display turns on when the slot counter reaches the left margin and
off when it reaches the right one, and between the two NICK fetches picture bytes; outside them it
shows the **border** colour from port `81h`. EXOS's text rows have their left margin at 11 and their
right margin at 51, 40 slots for 40 characters.

Hey, notice what a margin of 57 or more does: the counter never reaches it. A right margin that never
matches leaves the display on into the next line, and that is not a bug to avoid but a tool, as the
vertical sync of the frame shows later.

## The line parameter block

Every line is described by a **line parameter block** (LPB), 16 bytes in video memory:

```text
 byte  0     SC     256 - the number of lines in the block
 byte  1     MB     the mode byte: bit 7 VINT, bits 6-5 colours, bit 4 VRES, bits 3-1 mode, bit 0 RELOAD
 byte  2     LM     left margin (bits 5-0); bit 7 MSBALT, bit 6 LSBALT
 byte  3     RM     right margin (bits 5-0); bit 6 ALTIND1, bit 7 ALTIND0
 bytes 4-5   LD1    line data pointer 1, low byte first
 bytes 6-7   LD2    line data pointer 2, low byte first
 bytes 8-15  COL0-COL7, the palette's first eight entries
```

A block covers one or more lines. Here is the surprise: **NICK reads the whole block again on every
line of it**, in slots 0 to 7, two bytes a slot. Only a few things happen on the block's first line
alone: the line counter loads, LD2 loads, and LD1 loads (and on every line too, while VRES is clear).
Everything else, the margins, the mode and the palette, is taken fresh on each line.

That has a practical side. Rewrite one of a block's palette bytes while the beam is in the middle of
the block, and the very next line shows the new colour. A colour bar that changes on every line needs
no interrupt per line at all, only a block of one line per colour, or a program that races the beam.

A few of the mode byte's bits deserve a word now:

- **Colours** (bits 6-5): 2, 4, 16 or 256. A pixel's colour number picks one of the palette's 16
  entries; in 256-colour mode the byte is the colour itself.
- **The palette.** Entries 0 to 7 are the block's own COL0-COL7. Entries 8 to 15 are shared by every
  block: FIXBIAS, port `80h`, gives bits 7-3 and the entry number gives bits 2-0. A colour byte holds
  three bits of red, three of green and two of blue.
- **VINT** (bit 7) asks for the video interrupt. NICK raises its interrupt line at the start of each
  VINT line, and DAVE, the chip that handles interrupts, interrupts the CPU where the VINT block ends.
- **RELOAD** (bit 0) marks the last block of the table, the subject of the next section.

## The line parameter table

The blocks follow each other in memory, 16 bytes apart, and together they form the **line parameter
table** (LPT). NICK keeps a pointer into it. After a block's last line the pointer moves on 16 bytes
to the next block; after a block with RELOAD set it goes back to the table's start, which a program
writes into ports `82h` and `83h`. So the table is a loop, and one pass of it is a frame.

The frame is exactly as long as the table says. A program can make it 312 lines, 310, or anything
else; the television follows whatever sync it is given. EXOS builds a table of 34 blocks and 312
lines:

control bits in `83h`. At power-on the ports hold random values, so NICK walks a random table until
EXOS writes them.

## Where the picture's bytes come from

The display fetches read through two pointers that count as the line goes: LD1 and LD2. What they
point at depends on the mode (MB bits 3-1):

- **PIXEL**: two bitmap bytes a slot through LD1. In two colours that is 16 pixels a slot, 640 across
  40 slots: the mode for fine graphics.
- **LPIXEL**: one bitmap byte a slot, each pixel twice as wide. Half the memory for the same width.
- **ATTRIBUTE**: LD1 reads an attribute byte, LD2 a bitmap byte. The bitmap's 1 bits take the
  attribute's low four bits as their colour and its 0 bits the high four: colour cells, as on the ZX
  Spectrum, but one byte wide and any number of lines high.
- **CH256, CH128, CH64**: character modes. LD1 reads a character code, and the code picks a byte of the
  font at LD2: LD2 × 256 + code in CH256, LD2 × 128 + the code's low 7 bits in CH128, LD2 × 64 + its
  low 6 bits in CH64. LD2 counts once a line, so the next line reads the next row of the font.
- **VSYNC**: nothing shown; the margins make vertical sync, as in EXOS's table.

LD1 counts once in every slot between the margins (twice in PIXEL), the slots 0-7 and 54-56 included
when the margins reach them, even though nothing is fetched there.

Let's follow EXOS's text rows through this. Each is a CH128 block of 9 lines with VRES clear, so LD1
reloads from the block on every line and all nine lines read the same 40 character codes. LD2 starts
at the font's first row and moves one row down each line. So a 40-character row of text costs 40
bytes of codes, and the font, which every row shares, does the rest. Clever, isn't it? A whole screen
of text is 28 × 40 codes, about 1K, plus one font.

## One slot late

NICK's pixels do not come out in the slot that fetches them. The bytes a slot reads go into a buffer,
and **the next slot shows them**. Here is the order of things in each slot:

1. NICK compares the slot counter with the right margin and then the left one, and turns the display
   off or on.
2. It shows the bytes the previous slot fetched: 16 pixels, or the border if the previous slot was
   outside the margins.
3. It does this slot's reads: the block, a display fetch, or a refresh.

For an ordinary picture the delay is a uniform 16-pixel shift to the right, and you would never know.
It matters for anything timed to the beam: a write that changes a byte NICK fetches in slot *n*
changes the pixels of slot *n* + 1. EXOS's text, fetched in slots 11 to 50, is on the screen in slots
12 to 51.

Two more consequences. The buffers load only in the display-fetch slots, 8 to 53, so with a right
margin of 55 or more, slot 54 fetches nothing and slot 55 shows slot 53's bytes a second time. And the mode is latched at the left
margin, so a program that rewrites the mode byte in the middle of a line sees the change at the next
left margin.

## Sharing the memory: the clock stretch

Now for the CPU's side. Video memory is the top four 16K segments, `FCh` to `FFh`, NICK's whole 64K
address space. Whenever the Z80 reads or writes one of them, through whatever page the segment is in,
or reads or writes NICK's ports `80h` to `8Fh`, its access must fall into the Z80's window of a slot,
clocks 10 to 15.

So NICK holds the CPU's clock until it does. Step by step:

1. Each kind of machine cycle has a point where it needs the bus: an opcode fetch at T2.0, a memory
   read or write at T2.5, an I/O cycle at T3.5.
2. If that point falls in clocks 10 to 15 of a slot, nothing happens.
3. Otherwise NICK holds the CPU's clock, one half-T step (1.78 NICK clocks) at a time, until the point
   falls in the window.

Back to the first figure for the numbers. An access whose point arrives at NICK clock 3 is held for 4
half-T steps, 0.5 µs, and lands at clock 10.1. One that arrives at clock 0, just after a window has
closed, is held for 6 steps, 3 T-states, the most it can ever cost. One that arrives inside the window
costs nothing. Since the two clocks drift, the same instruction costs a different amount each time.

Uhm, so the cost is random? Not when code keeps touching video memory. Take a run of `NOP`s executed
from video RAM. A `NOP` takes 4 T-states, 14.2 NICK clocks, a little less than a slot. After the first
one is held into a window, the next opcode fetch arrives just after that window has closed and waits
for the next slot's. **The code locks to the slot grid: every `NOP` takes one slot, 4.495 T-states.**
A loop of video memory reads locks the same way, to whole slots.

Three things set NICK's stretch apart:

- **It does not depend on the beam.** Every slot has its Z80 window, in the border, during blanking
  and during the picture alike. Racing the beam does not make video memory any faster.
- **It never touches ordinary RAM.** Segments `F8h` to `FBh` on the 128 run at full speed, apart from
  DAVE's own wait states, which EXOS sets to one T-state on each opcode fetch. Code runs faster from
  ordinary RAM; keep video memory for the picture.
- **A port write lands in the window**, so a new border colour, FIXBIAS or LPT address takes effect
  from the next slot. That is the finest step for changing them in the middle of a line.

In return the CPU and NICK never use the memory at the same moment, so the Enterprise shows no snow,
however hard a program writes to the screen.

## How Klive does it

Klive's Enterprise core keeps the CPU's whole T-states and, beside them, a half-T clock in 125 ns
steps, because the stretch moves the CPU by half-T steps. NICK's position is an integer: each half-T
step adds 40,434,603 to an accumulator, and a slot passes every 363,520,000. That is the exact ratio
of the two clocks, so no rounding ever creeps in, and replaying a recorded run (reverse debugging
does) meets every slot at the same moment.

As the CPU's clock passes the start of a slot, the core runs that slot: the margin compares, then the
picture (the previous slot's bytes drawn as 16 pixels), then the slot's own reads. The CPU's memory
and port hooks compute the stretch from the accumulator: how many half-T steps until the access point
falls in clocks 10 to 15. Exactly where inside a cycle NICK samples a request is not documented; the
access points are named constants, so a measurement on a real machine would change one line.

The picture a television would show is the unblanked slots 10 to 55, 736 pixels, and 288 lines
starting at the 25th line after vertical sync begins. EXOS's 252 lines then have 18 lines of border
above and below them. The machine's frame ends where vertical sync starts, as the television's does.

The **NICK** panel in the Debug activity shows the ports, the beam's line and slot, the block NICK is
showing, decoded, and the whole table, block by block (see
[The Enterprise 64 and 128](/en/guides/machines/enterprise/#debugging)).

## What to take home

NICK's unit is the slot: 16 of its clocks, 1.124 µs, 4.495 T-states, 16 pixels. NICK reads twice in
each slot and gives the CPU the last six clocks. A line is 57 slots: eight to read the line's
description, 46 for the picture, three for refresh, and only slots 10 to 55 are ever visible.

The picture is a program. Each block of the line parameter table says how many lines it covers, its
mode, colours, margins, data pointers and eight palette entries, and NICK reads the block again on
every line, so a palette byte rewritten mid-block shows on the next line. The table loops at its
RELOAD block, and it alone decides the frame: EXOS's is 312 lines, 50.04 frames a second, with its
video interrupt three lines before vertical sync.

Every byte NICK fetches appears one slot later, a 16-pixel shift that matters only to code racing the
beam. And the CPU pays for sharing: every access to video memory or NICK's ports is held, in half-T
steps of up to 3 T-states, until it falls in its window. Code that keeps touching video memory locks
to the slot grid, wherever the beam is; in exchange there is never any snow.
