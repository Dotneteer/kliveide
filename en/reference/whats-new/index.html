What’s new

Every release of Klive IDE, newest first. Unreleased lists what is already in the source code and comes with the next release. Download a release from the releases page .

0.64.0 (2026-10-18)

Highlights

  • Reverse debugging on every Z80 machine: step back, reverse-continue to the last breakpoint hit, take over in the past, and save the session as a .klr debug recording (#1445).
  • Code coverage, a memory heat map and an exact profiler on every Z80 machine (#1446).
  • Z80 unit tests in DeZog’s conventions, with a Unit Tests panel and the new klive command line for CI (klive test with JUnit and LCOV, klive build, klive run) (#1446).
  • ZX Spectrum Next inspectors: Copper debugging, and live Sprite, Tilemap and Layer 2 inspectors, with layer hiding and a pixel probe on the emulator screen (#1434).
  • New machines: the Pentagon 128 with TR-DOS disks, the ZX Spectrum +2A/+3 with Amstrad’s original ROMs, and experimental Timex TC2048/TC2068/TS2068 and Scorpion ZS-256 machines (#1431).
  • RZX input recordings: play, debug, record, roll back and render .rzx files to video (#1431).
  • Reverse-engineering tools: annotations on every machine, annotated ROMs, code and data detection from coverage, a graphics finder, SkoolKit import/export and export as re-assemblable source (#1448).
  • Boriel BASIC 2 comes with Klive, with source-level debugging on the ZX Spectrum and the Next (#1463).
  • Klive speaks your language: the IDE in Spanish, Portuguese (Brazil and Portugal), German and Hungarian (#1464, #1465).
  • A reorganised menu bar and a new Settings dialog, with a Debug menu and one File › Open File… for every kind of file (#1443).

Key fixes

  • Cambridge Z88: no more noise below a small Screen Base File on the larger LCDs, the known issue of 0.63.0 (#1433).
  • Assembler: DEFB accepts strings (#1437).

Breaking changes

  • ZX Spectrum 48K, 128K and +2E/+3E machine states saved by 0.63.0 no longer load exactly, because the emulator cores’ memory layout changed. Such a .kls file loads from the .szx snapshot it carries: nearly the same state, without the tape’s exact position, the disk controller’s state and a few CPU details. Klive says when this happens (#1431, #1432).
  • Boriel ZX BASIC 1.x (zxbc 1.19) is no longer supported as the external compiler, and the zxb-reset command is gone. An existing zxbasic.compiler zxbc setting now means Boriel BASIC 2 (#1463).
  • Many menu items moved in the menu redesign, and the per-type load items, the IDE menu and the View and Machine check items are gone (the options are in Settings). Keyboard shortcuts are unchanged. The Settings page of the documentation has a Where Did It Go? table with the new place of every moved item (#1443).

Features

  • Execution History on every Z80 machine: Debug › Execution History (or show-history) lists the last instructions the CPU ran in a debug session: 131,072 on the Next and 65,536 on the other machines. Each row shows the bank and address, the bytes that actually ran, the disassembly, the source line, and the registers and flags the instruction changed. A HALT wait, a ZX80/ZX81 display line and a Next DMA bus hold are each one row with a count, and Fold interrupts turns each interrupt service into one expandable row. Click a row for the full registers before and after it and the memory map at that time; double-click it to go to its source. A plain Start records nothing (#1445).
  • Reverse debugging on every Z80 machine: while a debug session is paused, Step Back, Step Forward, Reverse Step Over, Reverse Step Out and Reverse Continue (Alt+F5) put the whole machine back at any recorded instruction, memory, devices and screen included, and every panel shows that moment. Stepping or continuing from the past replays the recorded run with your breakpoints active, and Take over here makes the current point the present and goes on live (on the Next this undoes the SD card writes of the discarded future). Reverse Continue checks every breakpoint kind, so a memory-write breakpoint finds where a byte last changed; a long search shows its progress and can be cancelled (reverse-continue-cancel). The status bar shows how far back you are, and a click returns to the present. Settings › Debugging sets how much memory the timeline may use (#1445).
  • Trace export: Debug › Export Execution History…, the Execution History’s Export button or history-export (hexp) saves a range of the history as a text or CSV trace. The defaults suit diffing two runs: times are relative to the first row, the header has no export time, and -nointerrupts leaves interrupt services out. The columns can be chosen, and CSV has one column per register (#1445).
  • Debug recordings: Debug › Save Debug Recording… (drsave) saves a reverse-debugging session to a .klr file. Debug › Open Debug Recording… (drload), File › Open File… or dropping the file on the Emulator window opens it on the same machine and configuration, paused where it was saved, with its whole past to step back through; its breakpoints and watches come with it as session breakpoints. A minute of a ZX Spectrum game takes about 1-2 MB, and .klr files have a viewer in the Explorer. A recording replays only in the Klive build that made it; for a file from another build, Klive offers to open its end state instead (#1445).
  • The advanced debugging features can be turned off: the execution history, reverse debugging, debug recordings, code coverage and the profiler are on by default. set -u features.advancedDebugging 0 and a restart turn them all off; a debug session then records nothing extra, and the related commands say how to turn the features back on (#1445, #1446).
  • Code coverage and the memory heat map on every Z80 machine: Debug › Code Coverage (or coverage on) records which bytes of every bank ran, were read or were written, and how often, at full speed as well as while stepping. The editor marks source lines as covered, partly covered or not covered, and the Disassembly view marks the instructions that ran. The Memory view’s Heat selector draws execution, read or write counts as a heat map and outlines self-modified bytes; coverage smc lists self-modifying code. coverage export writes LCOV, CSV or .kcov files, coverage load merges a .kcov file, and Debug › Reset Coverage starts over (#1446).
  • Profiler on every Z80 machine: Debug › Start Profiling and Stop Profiling measure every instruction in a window of the run, with no sampling, and open the Profiler document. Routines shows the time per routine (from Klive BASIC SUBs and FUNCTIONs, .proc blocks or labels), Addresses the time per address, Call tree inclusive and exclusive time, and Callers what called a routine. Interrupts count as roots of their own, and time waiting in HALT is kept apart. profile start -at <label> -until <label> measures exactly one pass of a loop. Profiles export to speedscope, callgrind (KCachegrind), CSV and Fuse’s format, and Settings › Debugging › Profile hints in the editor shows each routine’s share in the source. The assembler’s .proc blocks also appear in the editor’s Outline (#1446).
  • Z80 unit tests, with the Klive assembler and with sjasmplus, in DeZog’s conventions, so DeZog unit-test projects run unchanged: a routine labelled UT_... is a test, and TEST_... macros check values. Add unit-test support in the Testing activity’s menu (or test-init) adds the include file to a project. The Unit Tests panel runs each test on a fresh machine in the background, without touching the emulator, and shows passed, failed or error, the values that made a test fail and the T-states each test took; a click goes to the source. A failing test can be debugged in the emulator, and Run all tests with coverage feeds code coverage. Commands: test-list, test-run, test-debug and test-junit. Tests run on the ZX Spectrum 48K/16K, 128K, +2A/+3/+3E and Next (#1446).
  • The klive command line, for scripts and CI, needs nothing else installed and never opens a window. klive test builds a project and runs its unit tests, with exit codes, pretty, plain or TAP output, JUnit XML, and LCOV or .kcov coverage, giving the same results on every run. klive build compiles a project to a flat binary or Intel HEX. klive run runs a project, a tape, a snapshot, a state file, a NEX file or a ZX80/ZX81 program until a frame count, an exact T-state count, an address, a HALT, a breakpoint or a timeout, then writes memory dumps, registers, a PNG screenshot or a state file. On macOS, Klive IDE › Install Command Line Tool… puts klive on the PATH; the Windows installer adds it there (#1446).
  • Automation: with Settings › General › Automation on (it is off by default), scripts drive the running Klive with klive ide: build, run and debug the project, wait for a stop, read and write registers and memory, set breakpoints, take screenshots and, at the Full level, run any IDE command. Any language can do the same through a local, token-authenticated JSON-RPC 2.0 protocol. Three permission levels (Read, Control, Full) limit what scripts may do, and an Automation status bar item and output pane show the connected scripts and their calls (#1446).
  • Faster debugging: debug sessions and project starts now run close to the speed of a plain Run on most machines, also with memory, I/O or conditional breakpoints set; before, they could take two to three times longer. A source-level Step Over of a long call is almost four times faster (#1446).
  • ZX Spectrum Next Copper debugging: a Copper panel in the Debug activity shows the Copper’s mode, state, PC, write pointer, line offset and beam, with the instructions around its PC. The Copper List document (View › Machine Views › Copper List, or show-copper [index]) decodes all 1024 instructions with their meaning and a colour swatch for palette writes, marks the Copper’s PC and last hit, flags a list without HALT and WAITs that never match at the current timing, and draws a raster ruler of where in the frame each WAIT acts. bp-set cu:<index> stops the machine when the Copper completes an instruction, with hit counts, conditions, logpoints and one-shots; set one from the list’s gutter, its row menu (Run to here, run-to cu:) or the margin of a .copper source line. Step Copper (Debug › Step Copper, step-copper) runs to the Copper’s next instruction (#1434).
  • The .copper pragma writes Copper instructions in the Klive Z80 Assembler: .copper wait, move, nop, halt and word, with highlighting, completion and hover. The Copper List matches the live Copper memory back to these source lines, even when the list is uploaded at an offset or patched at run time, and Go to source opens the line (#1434).
  • Sprite Inspector for the ZX Spectrum Next: View › Machine Views › Sprite Inspector, show-sprites [n] or show-patterns [n] opens one document with two linked views. Sprites decodes all 128 attribute slots (pattern, position, palette offset, transforms, anchors, visibility) with diagnostics chips, change markers since the last stop and copy as nextreg/.db; Patterns shows the 16K of pattern RAM in the live or a pinned sprite palette, with usage badges. An inspector shows the selection and a map of sprite space. export-patterns (or Export pattern RAM as .spr) saves the pattern RAM. The inspector only reads: it does not clear the sprite status port $303B (#1434).
  • Tilemap Inspector for the ZX Spectrum Next: View › Machine Views › Tilemap Inspector, show-tilemap [x y] or show-tiles [n] opens one document with two linked views: Map, the 40x32 or 80x32 map (whole, or as displayed) with each cell’s tile, attributes and address, and Tiles, the 256 or 512 definitions with usage counts and unused tiles dimmed. Select a tile and every cell that uses it is outlined. Diagnostics check the map, the tile definitions and the ULA screen for setup mistakes such as overlaps. The inspector only reads, so opening it never changes the machine (#1435).
  • Pattern and tile snapshots: Open in sprite editor in the Sprite Inspector pops a sprite pattern, as its sprite shows it, into a read-only sprite editor, and Open tile snapshot in the Tilemap Inspector pops a tile into a read-only 8x8 viewer, with the cell’s transform and the palette frozen at the stop (#1435).
  • Layer 2 Inspector for the ZX Spectrum Next: View › Machine Views › Layer 2 Inspector or show-layer2 [shadow|window] shows the displayed ($12), shadow ($13) or $123B write-window banks as an image at their resolution, either whole with the 16K bank boundaries outlined, or as displayed with the scroll and clip window applied. A Banks strip names each bank’s role, and the pixel inspector gives a pixel’s byte, palette index and addresses: Show in memory opens the byte (in its 8K page when it is not mapped), and Break on write sets a bank-relative write breakpoint (#1436).
  • A viewer for .sl2 and .nxi Layer 2 pictures, at 256x192, 320x256 or 640x256 (the toolbar switches between the last two, which have the same size), with the palette the file carries or the Next’s default Layer 2 palette (#1436).
  • Hide, solo and probe the ZX Spectrum Next’s video layers: the Layers strip under the emulator screen (Settings › Emulator › Show the Layers strip, the status bar’s context menu, or the layers command, such as layers spr off or layers l2 solo) lists the layers in their $15 priority order, hides or solos each one, marks where no layer is opaque, and draws the four clip windows. A paused picture is redrawn exactly at once, even after mid-frame Copper changes. The pixel probe names the layer that produced a pixel and the rule that made it win, and a click opens the inspector that owns it. View › Machine Views › Layers (show-layers) shows the priority stack and a card per layer. This changes only what the emulator shows, never what the machine does, and a pill on the screen says when a layer is hidden (#1442).
  • The beam position on the paused screen, on the ZX Spectrum Next and on the 48K, 128K, +2A/+3, +2E/+3E, Pentagon, Scorpion and Timex models: when the machine pauses, a line marks the beam’s row, a pill gives its raster line, paper row, position in the line and frame tact, and the part of the picture left from the previous frame is hatched. The paused picture is first brought up to the beam, without changing the machine. Blanking is named, pointing at a pixel tells how many tacts until the beam draws it, and on the Next a Copper breakpoint’s hit is shown as a second marker. Switch it with the emulator toolbar’s beam button, Settings › Emulator › Beam position or beam [on|off] (#1442).
  • Sprite attribute breakpoints on the ZX Spectrum Next: bp-set sp:<sprite> stops after an instruction writes an attribute byte of that sprite, whether the CPU, the DMA or the Copper wrote it, through port $57 or the NextReg mirrors. The stop reports the byte, its old and new value, and the writer, and -attr limits the breakpoint to some of the five bytes. You can also set one from the breakpoint dialog or the Sprite Inspector’s row menu (#1445).
  • Copper and DMA regions in .NEX annotations: mark a range of a popped-out bank as a Copper list or a zxnDMA program, and the listing shows it as .copper / .dma pragmas, with each instruction’s meaning in the comment column. Every row reassembles to the bytes it shows, and the annotation file stays readable by older Klive versions (#1444).
  • New model: the Pentagon 128, the Russian 128K clone much of the demoscene writes for. It is a model of the ZX Spectrum 128K with the same ROMs, paging and AY and the Pentagon’s own timing: 3.5 MHz, a 71,680 T-state frame (224 T-states by 320 lines), no memory or I/O contention and no floating bus. Running, debugging, injecting code, the tape loader, snapshots and state files work as on the 128K. .szx and .z80 snapshots of a Pentagon open on it and are saved as a Pentagon, and a 128K snapshot keeps a Pentagon project on the Pentagon (#1431).
  • TR-DOS disks on the Pentagon 128: the Pentagon has the Beta 128 disk interface, with two drives that take .trd and .scl images, and TR-DOS. Klive cannot ship the TR-DOS ROM, so name your own 16K copy under Settings › Machine › TR-DOS ROM; without it the Pentagon runs without its drives. Machine › Disks inserts, ejects and write-protects disks; TR-DOS writes go back into .trd files, while an .scl is never changed (Save Disk in Drive A as .trd… keeps the changes). Create Disk File… and crd (for example crd trd80ds games) make blank TR-DOS disks, and Boot Disk in Drive A selects 48 BASIC, enters TR-DOS and runs the disk’s boot program. The debugger shows the TR-DOS ROM as partition R2, so R2:$3D2F stops only in TR-DOS. .szx snapshots and state files keep the disk interface’s state (#1432).
  • ZX Spectrum +2A/+3 with the original Amstrad ROMs: the +2A/+3/+2E/+3E machine gains eight models that boot Amstrad’s unmodified ROMs: the +2A (v4.1 and Spanish v4.1) and the +3 (v4.1, the 1987 v4.0 and Spanish v4.1, each with one or two drives). Pick one when a program must behave exactly as on the original machine; running, debugging, injecting code, tapes, .dsk disks, snapshots and state files work as on the +2E/+3E. A .z80 or .szx snapshot of a +2A or +3 stays on a +2A/+3 model when the project already uses one, and is saved back as a +2A or +3 (#1431).
  • New experimental machines: the Timex TC2048, TC2068 and TS2068. They run 48K software and add the Timex SCLD’s screen modes (a second screen, 8x1 extended colour and 512x192 two-colour), port $FF and the 3.528 MHz clock; the TS2068 has a 60 Hz frame and the TC2048 a built-in Kempston port. The 2068s add 8K bank switching from the HOME bank, the cartridge DOCK and the Extension ROM (partitions H0-H7, D0-D7 and X0-X7 in the views and breakpoints), an AY chip with the PSG panel, two joysticks, and cartridges: Machine › Cartridge › Insert Cartridge… takes a .dck file. Klive cannot ship Timex’s ROMs, so name yours under Settings › Machine (TC2048 ROM, TC2068 ROM or TS2068 ROM); until then the machine boots the Sinclair 48K ROM. With a 2068 ROM other than the known TS2068 one, the IDE cannot start a program or a tape. .szx and .z80 snapshots load and save; a .sna saves as a 48K, and Klive names what it loses (#1432).
  • New experimental machine: the Scorpion ZS-256, a Russian 128K-compatible machine with 256K of RAM in sixteen banks (B0-B15), port $1FFD, four ROMs (R0-R3: the 128K editor, 48K BASIC, the service monitor and TR-DOS) and a built-in Beta 128 disk interface with two drives, as on the Pentagon. Klive cannot ship its 64K ROM, so name yours under Settings › Machine › Scorpion ROM. Until then it boots the 128K ROMs and takes TR-DOS from the TR-DOS ROM setting, and running, debugging, the tape loader and booting a disk work as on the 128K. With the Scorpion’s own ROM the IDE cannot start a program, tape or disk in its editor, so load them by hand. .szx and .z80 snapshots keep all sixteen banks; a .sna is refused while $1FFD is in use (#1432).
  • RZX input recordings: Klive plays and records RZX files (version 0.13) on the ZX Spectrum 48K (16K and NTSC too), the 128K and the +2E/+3E, and a recording made on a +2A or +3 plays on the new Amstrad models. Open an .rzx file with File › Open File…, drop it on the Emulator window, use Play recording in the Explorer or the recording’s tab, or zx-rzx <file>. Debug recording (zx-rzx <file> -d) stops at the first instruction, breakpoints and stepping work while it plays, and a desync pauses the machine and names the frame. The .rzx viewer shows the file’s details, its segments (each can be played from, zx-rzx <file> -s <n>) and its first snapshot. Machine › Record › RZX: Record (zx-rzx-record) records from the current state with a rollback point every five seconds, with RZX: Roll Back (zx-rzx-rollback), RZX: Insert Rollback Point (zx-rzx-point) and RZX: Stop and Save… (zx-rzx-stop <file>). RZX: Render a Recording to Video… (zx-rzx-video <file>) plays a recording into a video file. A PLAY/REC badge in the status bar shows the frame counter (#1431).
  • Machine code for the ZX81 and ZX80: the assembler takes .model ZX81 and .model ZX80 (and #ifmod), the .defzx pragma writes text in the machines’ character sets, and code above $7FFF gets a warning; a source with no .model is assembled for the running machine. Run and Debug put the code into a 1 REM line followed by 2 RAND USR <entry> and type RUN, so the code is debugged at source level as on the other machines, and Inject only writes the program. Code that starts at the program’s base is taken as a complete program. Export (or expc <file> -f p|o) writes a .p or .o file, and on a .p file -as makes it run itself once loaded. New ZX81 and ZX80 project templates print a welcome message, and klive run works on these projects (#1461).
  • BASIC Listing for the ZX81 and ZX80: View › Machine Views › BASIC Listing lists the program in a ZX81 or ZX80 the way the machine’s own LIST prints it, with the ROM’s keyword spacing, and line numbers above 9999 shown as the ROM shows them (14393 as E393). A ZX80 with the 8K ROM is listed as a ZX81 (#1460).

Features

  • New machines: the Sinclair ZX81 and ZX80. One WebAssembly core runs both: the ZX81 with 1K, 16K or 64K, in PAL or NTSC (Timex Sinclair 1000), and the ZX80 with 1K or 16K, or with the 8K ROM upgrade. The ULA is emulated cycle by cycle: SLOW and FAST modes, a jitter-free picture, and the hi-res (WRX) graphics programs build on it. Open a .p/.81 (ZX81) or .o/.80 (ZX80) program from Machine → Select Program File… or the Explorer, and Load and Run types LOAD "", loads it (instantly with fast load, or in real time from its tape signal) and types RUN. The ZX81 has a virtual keyboard that follows the original’s layout. The debugger works as on the other machines, and the disassembler decodes the ZX81 ROM’s error codes and calculator literals. The ZX80 and ZX81 ROMs ship with Klive; they are free for non-commercial use (see zx8081-roms-readme.txt).

  • Klive BASIC, a built-in ZX BASIC compiler (#1400). It needs no installation and is now the default compiler. It is compatible with Boriel ZX BASIC 1.19: the same options and #pragmas, the standard libraries, the zxbasm inline-assembly dialect, and NextBuild’s CODEBANK for the Next. Build options go in '@name value header lines. .zxbas files are recognised, and a new zx-basic project template is available for the 48K, 128K and Next. set zxbasic.compiler zxbc switches back to Boriel’s zxbc.

  • Source-level BASIC debugging (#1400). Step Into (with a Step Into Target drop-down), Step Over, Step Out and Step Over Line step BASIC statements, and a Source / Z80 toolbar toggle switches the stepping mode. Breakpoints can be set on individual statements of a line. The Call Stack panel shows SUB/FUNCTION/GOSUB frames, with Run to this frame, and the Variables panel shows parameters, locals, globals and BASIC watch expressions. A run stops on a BASIC error. New commands: em-src, em-err and em-jmc (Just My Code). A NEX export writes <name>.nex.kbasic-debug.json, so nex-run -d debugs it at source level.

  • New assembler features (#1400): #LINE remaps reported source locations, and the .page <page>[, addr[, count]] pragma places code in an 8K Next page.

  • BASIC editor intelligence (#1415). Background checking drives hover (types, scope, signatures, keyword help), Go to Definition (F12, which also opens #include files), Find All References (Shift+F12), context-aware completion (choosing a library routine adds its #include), signature help, Rename (F2), the Outline (Cmd/Ctrl+Shift+O), folding and block highlights — all across included files. With zxbc selected, only the keyword-level features work.

  • Conditional breakpoints and hit counts (#1413), on every breakpoint kind. bp-set ... -hit <spec> takes 10, >10, >=10, <10, <=10 or *10; -if <condition> (it must come last) takes an expression over registers, flags, VAL/ADDR, memory reads (w[HL], b[05:$C010]), page(), nr() and build labels. The new bp-reset-hits command resets the counts, and bp-list prints lines you can paste back into bp-set. Conditions can also be edited in the breakpoint dialog and the editor margin’s menu.

  • Logpoints (#1414). bp-set ... -log "x={A} at {PC:hex16}" writes to a new Log output pane and keeps running; formats include hex8, hex16, int8, uint16, bits and string. A [GROUP] prefix puts a logpoint into a group; switch groups with lp-en and list them with lp-groups. The breakpoint dialog has an Action row, the margin menu has Add Logpoint…, and logpoints are drawn as diamonds. DeZog ; LOGPOINT comments are read from the Klive assembler and from sjasmplus (which needs SLDOPT COMMENT WPMEM, LOGPOINT, ASSERTION).

  • DeZog ASSERTION and WPMEM comments (#1414). A failing assertion stops the machine and reports the values it read; WPMEM becomes a memory watchpoint over a range. Both are on by default; switch them off per project with as-en -d and wp-en -d.

  • Memory range breakpoints and watchpoints (#1414). bp-set <addr> -r|-w -len <bytes> watches a range. Watch view rows gain Break on write/read/access, which follows the symbol across rebuilds (shown as WS:<symbol>). show-disass <address> moves the Disassembly view to an address.

Fixes

  • Host cursor keys did nothing on the Cambridge Z88 (#1374). The joystick key bindings took the arrow keys, right Shift, right Ctrl, \ and NumpadEnter on every machine, not just the ZX Spectrum Next. They now belong to the emulated keyboard on any machine without joystick connectors, which also restores the ZX Spectrum’s arrow keys and the Z88’s two-Shift sleep/wake from the keyboard.
  • Choppy Cambridge Z88 sound (#1374). The Z88 delivers its sound in 40 ms bursts of eight short frames, and the audio buffer, sized for a single frame, dropped over half of every burst. The beeper and the 3200 Hz tone now play smoothly again. The Z88 also no longer goes silent after about 22 minutes of running.
  • Queued keys could stick after about 10 minutes of running (#1374), on the Cambridge Z88, the ZX Spectrum 48/128/+3E and the ZX Spectrum Next. These are the keys the on-screen keyboard and code injection type. A key queued as the machine’s cycle counter passed 2^31 stayed pressed for good, or never started and blocked every key after it. That point comes after about 10 minutes at 3.5 MHz (11 on the Z88), and after 80 seconds on a Next running at 28 MHz.
  • The ZX Spectrum 48, 128 and +3E froze after about 20 minutes of running (#1374). When the machine’s 32-bit cycle counter wrapped, the frame loop stopped running instructions and the machine hung for good. The cores now keep their internal counter well away from the wrap, and the counter the IDE shows carries on as before.
  • The Cambridge Z88 keyboard could go dead under OZ 4.7 (#1374). With Keyclick on, a key press in the Index moved the highlight once, then no key worked while the machine kept running. The emulated Z80 had an NMOS chip quirk the Z88’s CMOS Z80 does not have, and OZ 4.7 read it as “interrupts off”. The Z88 now emulates the CMOS behaviour; the ZX Spectrum machines are unchanged.
  • The Cambridge Z88 screen lost its corner pixels to the emulator display’s rounded corners (#1374). The LCD now sits in a narrow surround in its own colour: unlit green, or grey while the LCD is off. The display’s 1px frame also no longer hides one pixel on each edge of every machine’s picture. Z88 screen recordings carry the same surround (4 pixels), so a player that rounds its window’s corners no longer clips the LCD either.
  • The Cambridge Z88 never switched itself off after the Panel’s idle timeout (#1374). Two faults in the emulated real-time clock hid the passing minutes from OZ 4.7 and OZ 5.0. Both now go into coma on time, as OZ 4.0 already did.
  • Screen recording never produced a file in the installed app (#1374), on any machine. The app looked for its bundled FFmpeg inside the app archive, where it cannot run, and only an empty KliveExports/video folder was left. A recording that fails now says why, instead of ending as if it had worked.
  • Cambridge Z88 recordings had the wrong sound (#1374): a beep recorded as a dull thump. The recorder took each frame’s sound only after the next frames had already overwritten it, so every 40 ms of recorded audio repeated the same 5 ms slice. Recordings now carry exactly what the speaker plays.
  • Half-fps recordings lost half their sound, on every machine. The audio of each skipped video frame was thrown away, so 2 seconds of video carried about 1 second of squeezed-together audio. All of the audio is now kept.
  • ZX Spectrum Next panels showed stale data. On the standard (WASM) Next the Palettes panel and the sprite editor’s palette showed power-on colours whatever a program had written, the ULA & I/O panel read values the emulator never updated, and the Memory Mapping panel showed logical instead of physical page offsets and zero for the paging and DivMMC ports. (On the now-removed Next Compatibility model the ULA & I/O panel failed outright, and the memory editor treated the ROM pages as RAM.)
  • No sound while debugging the ZX Spectrum Next. With the debugger attached, the standard model played nothing after its first frame; it now sounds as it does without the debugger.
  • The ZX Spectrum Next’s F2 (scandoubler), F3 (50/60 Hz) and F7 (scanline weight) menu items had no effect on the standard model.
  • On the standard ZX Next the status bar always showed 3.5 MHz, however fast the CPU ran, and a memory or I/O breakpoint hit was reported against address $0000 in the Breakpoints panel.
  • ZX Spectrum Next: a mid-line write to NextReg $68 bit 2 (half-pixel ULA scroll) now takes effect at the next 8-pixel cell, as on the hardware; and the frame interrupt is raised in the first frame after a reset.
  • ZX Spectrum Next sprites could vanish. On the standard model, sprites numbered above the one a program made visible last were not drawn at all. Both models also forgot a sprite’s fifth attribute byte after a four-byte write, instead of keeping it for when the sprite becomes five-byte again.
  • ZX Spectrum Next hardware fixes found by the new cross-checks (each against the FPGA source): CTC and UART interrupts, and an NMI with NextReg $CC bit 7, now break into a DMA transfer; a CTC control word that counts the channel down to zero raises its zero count; a Layer 2 read mapping (any segment) disables the DivMMC’s ROM 3 entry points; a RETN at $0066 is recognised from the code the DivMMC pages in; a tilemap in bank 7 wraps at 8K; and a soft reset now resets the sprite upload positions and keeps NextReg $02 bit 7.
  • A popped-out NEX bank could be open twice. Opening a bank from the NEX viewer and then stopping in it while debugging (or following a label into it) gave two documents for the one bank, and the debugger scrolled the one you were not looking at. The two also carried different tab titles.
  • Go to Definition landed at the start of the line instead of on the symbol.
  • Opening a file whose viewer is not a code editor through the nav command (the NEX viewer, for example) took about five seconds.
  • In a disassembly listing, a label on the target of a jr or djnz appeared in the label column but never in the jump itself, which kept the generated L… name.
  • Only source files came back when you reopened a project. Every other document backed by a project file — the NEX, DSK and Z80 viewers, plain text files — was saved into the workspace correctly and then discarded while restoring it, because restoring matched on the code editor alone. Losing such a document also lost the selected tab, since the active one fell back to the first document that happened to survive.
  • A breakpoint in partition 0 (bank B0 on the 128K, bank 00 on the ZX Next) could never fire.
  • A source-code breakpoint fired in the wrong memory bank. For a line inside a .bank section, the breakpoint was placed by address alone — and .bank sections share addresses, so it also stopped the machine in every other bank’s code at the same address. It now carries the bank its line was assembled into.
  • A rebuild left phantom breakpoints behind. When recompiling moved a line’s code, the machine kept stopping at the address the line used to be at, as well as at its new one, with nothing in the Breakpoints panel to explain it.
  • Several breakpoints could disturb each other when they landed on the same address — and a bank-relative breakpoint occupies eight addresses, so this was easier to hit than it sounds. Adding or removing one breakpoint could silently disarm another, permanently; a disabled breakpoint could mask an enabled one.

  • Replacing a set of breakpoints (opening a project, saving one, refreshing after a build) did not remove the ones it was replacing — it added to them. Invisible in the Breakpoints panel, because the replacements took the same names, but the old ones stayed armed where they were.
  • The breakpoint dialog never showed a breakpoint’s hit count: the emulator was not reporting it.

The debugger’s shadow stack of return addresses was only ever pushed to, never popped, so once a routine had returned its entry stayed on top — and Step Out aimed at an address the program would not reach again, running on to the next breakpoint instead. It went wrong whenever the routine you were in did not own the newest entry: after a tail call (jp SomeRoutine, which pushes nothing, so the routine returns past its caller), and after stepping into and back out of a nested call before stepping out of the routine containing it. The stack is now balanced on every RET actually taken, so a conditional RET that falls through still costs nothing.

  • The buttons a document adds to the tab bar (Run, Debug, and the script and NEX actions) sat hard against the right-hand end of the header, with no space after the last one.
  • The NEX viewer’s Header attributes rows were taller than they needed to be, spreading the header over more vertical space than its content asks for.
  • Opening a project no longer discards breakpoints the project does not own.
  • Removing a partition-scoped breakpoint through the editor gutter silently did nothing.
  • The Disassembly view’s breakpoint gutter no longer shows a breakpoint from one bank while you are looking at another.
  • The Memory Mapping panel’s All RAM row always read Off. Two separate causes: the field was read under a different name than it was written, and the ZX Spectrum Next reported nothing for it at all.
  • The Memory Mapping panel’s page rows showed the same number twice on the ZX Spectrum Next, one of them labelled “16K bank” in the tooltip. It now shows the real 16K bank beside the 8K one.
  • A memory-read, memory-write or I/O breakpoint shown in the disassembly margin could not be removed or disabled by clicking it. The margin did not know the breakpoint’s type, so it asked to remove an execution breakpoint at that address — which is a different breakpoint, and matched nothing. On the ZX Spectrum Next a bank watchpoint failed a second way: the address it named carried a type suffix the commands do not accept as part of an address.
  • A disassembly line carrying more than one breakpoint showed whichever the emulator happened to list last, which also decided what right-clicking it would remove. It now shows the execution breakpoint, preferring an enabled one.

Breaking changes

  • The “ZX Spectrum Next Compatibility” machine model is gone. It ran a second, TypeScript implementation of the Next, which existed to check the current emulator against while that one was being written. The two now agree everywhere they were measured — the whole hardware test suite, every pixel test, and a 1500-frame instruction-by-instruction comparison of the NextZXOS boot — so the old one has been removed, and with it the last places where the Next quietly ran two emulators at once. A project or a session saved with the Compatibility model opens on ZX Spectrum Next; nothing else about it changes.

  • The “Cambridge Z88 (TypeScript)” machine models are gone. The Cambridge Z88 runs on its WebAssembly emulator, and the older TypeScript one stayed in the Machine menu, in its own submenu, only to compare the two. They agreed on every OZ version booting and typing, every LCD size, the beeper, every card type being programmed, the IDE’s panels and the debugger, so the TypeScript Z88 has been removed and the submenu with it. A project or a session saved with one of those models (or with an earlier “WASM preview” model) opens on the same Z88 model in the main list.

  • On the ZX Spectrum Next, a positive memory partition index now means an 8K page rather than a 16K bank. Everything else already described these as 8K pages — the 224-entry partition list, the Memory view’s bank chooser and the documentation — but the breakpoint and disassembly layer halved the number, so bp-set 0A:$C000 and the Memory view’s bank 0A named different memory.

    Two visible consequences: the Disassembly view’s bank column shows different numbers on the Next (an address in 16K bank 5’s low half now reads 0A, not 05), and a partition in bp-set, in a saved script, or in an existing .kliveproject now names an 8K page. Saved Next partition breakpoints are not migrated — a stored index is genuinely ambiguous, since a user following the documented behaviour already meant the new reading. 16K bank B is the partition pair 2B/2B+1.

Features

  • Multiple document hubs are available through the Split Right and Split Down document tab context menus.
  • Context menus and modal dialogs are restyled.
  • Fixed-size data rows in NEX annotations. A bytes region in a .nex.dis file can set rowBytes (1–4), so a table of records lists one record per .defb line — each two-byte copper instruction on its own line, for example — with its own comment.
  • Go Back and Go Forward. Klive remembers the places you jump to — Go to Definition, an output-pane link, a breakpoint, a document tab, Go To in the Memory and Disassembly views, a NEX bank or label — and takes you back through them with Ctrl+- / Ctrl+Shift+- on macOS and Alt+Left / Alt+Right elsewhere, the mouse’s back and forward buttons, the new toolbar buttons, or IDE › Go. The arrow between the toolbar buttons lists the whole history. Debugger stops are not remembered, so after debugging, Go Back returns to where you were before. A remembered line follows its code as you edit, and a place in a closed document — including a popped-out NEX bank — opens it again. New commands: nav-back, nav-forward, nav-history and nav-clear; nav gained -r to record its jump.
  • bp-set, bp-del and bp-en accept a bank-relative address on the ZX Spectrum Next: bp-set 05:+$0100 breaks at offset $0100 inside 16K bank 5, wherever that bank is paged in.
  • Any .nex file can be run or debugged on its own, without a project: from the Project Explorer’s context menu, from the buttons in a NEX file’s document tab, or with the new nex-run command.
  • A popped-out NEX bank has a breakpoint gutter: click it to break at that offset in that bank, wherever the bank is paged in. Those breakpoints are remembered in the .nex.dis sidecar, so they survive a restart even when no project is open.
  • Debug a NEX file from its first instruction. nex-run <file> -e, or the new Debug NEX file (break at entry point) item in the Explorer menu and the NEX document’s tab bar, stops the machine the moment NextZXOS hands control to the program — with the entry bank paged in. Klive reads the entry point from the NEX header, so you do not have to know where the program’s code lives.
  • Bank watchpoints on the ZX Spectrum Next. The Memory read and Memory write breakpoint types now work with a bank-relative address (bp-set 05:+$0100 -w), so you can break when a byte of a particular 16K bank is read or written, wherever that bank is paged. The breakpoint dialog’s Address field accepts the bank-relative form too, which means you can click a popped-out NEX bank’s margin to set an execution breakpoint and then double-click it to change its type.
  • The NEX viewer checks the file before you run it. A banner reports problems decidable from the header: an entry bank the file does not contain, an entry point or stack pointer in ROM, a bank the entry point needs but the file lacks, a core version newer than the emulator’s, and a bank count that disagrees with the file’s own flags. Each of these otherwise fails silently — NextZXOS reports a successful load and the program runs into memory it never loaded.
  • Breakpoints anchored to a NEX label are remembered in the .nex.dis file, so they come back with the file — still anchored to the label, not to wherever it happened to be last time.
  • Name what you just worked out, without leaving the debugger. Paused inside a NEX’s code, the new nex-label <name> command (alias nl) adds a label to that file’s annotations at the offset you are stopped at — and the live disassembly starts using it. It writes a bank-local label, because the address is only meaningful as an offset in its bank. With the NEX’s viewer open the label joins your unsaved annotation edits and is kept when you save them; with the viewer closed it is written straight to the .nex.dis file.
  • Your NEX labels appear in the live disassembly. With a NEX launched, the Disassembly view names operands from the labels you wrote in the NEX viewer — call DrawSprite rather than call $C100. A bank’s own labels apply only while that bank is paged in, so the names follow the program as it pages; labels you made global apply everywhere.
  • A bank listed at $4000 no longer disassembles the screen. That range is the ULA screen — bitmap and attributes, $4000–$5AFF — and it used to fill the listing with thousands of rows of decoded pixels ahead of the code. It now collapses to a single line, and a Screen switch in the toolbar brings the disassembly back when you want it. The switch appears only for a NEX bank listed at $4000, and it changes the listing only: regions and annotations you made inside the range are kept.
  • Follow a label to where it is defined. A NEX bank’s disassembly context menu opens with Go to Definition whenever the line names a label — ld hl,InitPalettes — and it takes you there. A definition inside the bank on screen is a scroll, and works with no machine running. One outside it needs a machine, because which bank holds an address depends on how the program has paged memory: with one running, that bank is brought forward and scrolled to the label; without one, the command is greyed rather than guessing. Ctrl+F12 reaches it from the listing — plain F12 is the macOS Step Into accelerator, so it was not free to take.
  • A popped-out NEX bank shows the machine, not the file — without being asked. Whenever a machine is running, both the bank’s memory and its disassembly are built from the bank’s current contents, with every byte that differs from the file marked and counted in the toolbar. This is how self-modifying code, a decompressed payload, or a bank corrupted by a stray write become visible — none of it can be told from a clean load otherwise. It works for every bank of the file, including ones the program has paged out, and falls back to the file’s bytes when no machine is running. There is no switch to find: a Live marker in the toolbar says which of the two you are looking at.
  • A paused NEX bank’s disassembly is aligned to the program counter. Decoding a bank from its first byte is a guess about where instructions start, and self-modifying code or a jump table can make it wrong for everything below. While the machine is paused with the PC inside the bank, the listing is cut and re-decoded at the PC — the one offset where the alignment is known rather than guessed — so the rows from there on are the instructions that will actually run. A listing that was already aligned is left exactly as it was.
  • The Memory Mapping panel says which slots hold banks of the NEX you launched. Hovering a page row names the file when that bank is one the NEX declares — so you can tell at a glance which bank to pop out. It names the file rather than claiming what the slot currently holds: the program is free to have overwritten the bank, and popping the bank out is what answers that — its view is the machine’s bytes, with the differences from the file marked.
  • A popped-out bank highlights the line the program counter is on. While the machine is paused and the PC is inside that bank, its disassembly marks the current instruction the way the Disassembly view does, and the toolbar adds a PC marker so you can tell without hunting for it.
  • A popped-out ZX Spectrum Next bank says where it is paged in. Its toolbar shows Bank at $8000, or Bank not paged in, updated as the machine runs — with the 8K slot numbers in the tooltip, and a note that a paged-out bank’s breakpoints stay armed and will fire once it comes back. A bank whose two 8K halves are not paged in as one block is reported as exactly that.
  • The NEX viewer counts the breakpoints in each bank. A bank’s heading shows how many it carries, with the breakdown by type in the tooltip, so a collapsed bank still tells you it is armed.
  • Run to a line. The new run-to command (alias rtc) runs the machine until it reaches an address and then stops, leaving no breakpoint behind. It accepts everything bp-set does, including the Next’s bank-relative 05:+$0100 form, so you can run to an offset inside a bank that is not paged in yet. Hold <kbd>Ctrl</kbd> (<kbd>Cmd</kbd> on macOS) and click the breakpoint margin in the Disassembly view or a popped-out NEX bank to do the same thing without typing a command.
