Klive — sprite editor modernization lab

Four layout proposals for src/renderer/features/sprite-editor, each drawn in dark and light from the real token values in src/renderer/theming/tokens/* and the real Next colour maths in src/emu/machines/zxNext/palette.ts. Every frame is the same markup with a different data-v attribute — so what differs between them is the design, not the mock-up. Sprite pixels are real palette codes from the app's default 0–255 ramp; the transparency swatch is index $E3 = #ff00db, which is what the editor hardcodes in eight places today. The sprite's "white" is $FF = #ffffdb, not white — the fixed 0–255 ramp the editor substitutes for the machine's sprite palette leaves bit 8 of the register layout always clear, so four of the Next's eight blue levels are unreachable and there is no pure white and no pure blue in it at all. No JavaScript. Read A — Current first; it is a replica of what ships, not an impression of it.

1 — The four layouts

Shown in a 660×600 document pane, which is about as small as this editor is usefully opened. Each caption names the trade-off, not just the idea.

A — Current  — 660×600 pane, dark & lightWhat ships today, drawn from the real code. Two toolbars with the sheet strip wedged between them; the canvas is a fixed 257/385/513 px (zoom 1–3) whatever the pane is; the 285 px palette sits beside it in the same flex row and everything right of the palette is dead space. No rulers, no preview, no selection shown in the palette, and the pen/fill chips share one cramped strip with the position readout. Cost: the canvas is the smallest thing in the editor.

B — Tool rail + fitted canvas + inspector  — 660×600 pane, dark & lightThe conservative move: nothing new is invented, everything is re-seated. One file toolbar, tools in a vertical rail against the canvas, canvas fills the pane at an integer zoom, and a right inspector carrying pen/fill, the palette and a live preview. Sheet strip docks at the bottom with a header. Cost: 300 px is permanently the inspector's (wants a draggable splitter), and the sheet strip costs ~82 px of height even when you are not using it.

C — Studio  — 660×600 pane, dark & lightB plus the things a pixel editor is normally judged on: rulers, 8 px guides, onion skin, an animation preview, and the sheet as a wrapping browser with index labels rather than a one-line strip. Cost: the most chrome and the most to build; rulers eat 14 px on two edges; a wrapping browser is better for a 40-sprite sheet and worse for scrubbing a 4-frame animation.

D — Canvas-first  — 660×600 pane, dark & lightThe opposite bet: the canvas takes everything. Tools, pen/fill and an 8-slot recents column live in a 44 px rail; the full 256-swatch palette is a popover off the pen chip (shown open here); the sheet is a thin unlabelled strip. Cost: the palette is a click away, which is expensive on multi-colour work, and recents only help once you have used a colour.

2 — What a wide pane does

The same two layouts at 1100×580 — a normal maximised document pane. This is the single biggest complaint the current editor earns: the canvas is capped at 513 px (zoom 3) no matter how much room there is, so the editor gets emptier as the window gets bigger rather than more useful.

A — Current, 1100×580Canvas at zoom 2 (385 px). The palette is wider than the canvas; everything right of it is dead space. Zoom 3 would make the canvas 513 px and still leave ~300 px empty.

Today selected and hovered draw the same 2 px highlight border, so you cannot tell which sprite you are editing while the pointer is in the strip; an all-transparent sprite is invisible; and there is no index on the cell, only in a tooltip. Proposed: a checkerboard ground so an empty cell is still a cell, a persistent index, an accent ring for selection and a raised surface for hover.
Palette selection
now
new
NextPaletteViewer already takes a selectedIndex prop and the sprite editor never passes it, so the palette shows no selection at all — including the pen colour restored from the saved view state, and after the Swap button. Proposed: an accent ring for the pen and a secondary-accent corner for the fill, so both are locatable in 256 swatches.
Position / colour readout
now
Position:(4:5) Color:$FF (R: 7, G: 7, B: 6)
new
x 5, y 4 $FF#ffffdb R7 G7 B6
(4:5) is row:column — the reverse of the x,y every other pixel tool reports, and unlabelled. The RGB triple is on the Next's 0–7 scale with no note that it is. Proposed: explicit x/y, the swatch, the index, the CSS colour and the 0–7 parts, in a real status bar at the foot of the canvas.
