# ZX Spectrum Next core 3.02.01 -> 3.02.04: the hardware delta, classified

P2 of `.plans/ZXNEXT_CORE_VERSIONS_PLAN.md`. Written 2026-10-31 from the pinned trees in
`vendor/next-fpga/sources.json` (3.02.01 = `5ad7546d`, 3.02.04 = `dc8d7641`, branch `30204`) and
upstream `changelog.md` 3.02.02-3.02.04. The raw material is `npm run next-fpga:diff` (add
`-- --brief` for the region list only); it diffs pristine upstream, so Klive's comment patches do not
show. Citations are `file@version ~line`; files are relative to upstream `cores/zxnext/`.

The issue 4 (KS2) build is `src/zxnext_top_issue4.vhd`: `g_board_issue = X"2"`, and from 3.02.04
`g_option = X"FFF2"` (`zxnext_top_issue4.vhd@3.02.04 ~40`, decoded at `zxnext.vhd@3.02.04 ~42-67`):
CPU variant `"10"` = T80N with the debug wedge (**not** the "complete" memptr/XY variant), Pi SPI
slave with every command (bits 4-11), TZX hotkeys (12), SRAM port C (13). Everything below is judged
for that build; issue 2/3/5 items are listed as board-only.

Classes: **behaviour** (software can observe it), **new register/bit**, **timing**, **bug fix**
(upstream calls it a fix; also observable), **board-only** (other PCB, pins, video/SPI pads),
**no emulator impact** (inside the FPGA, or a device Klive does not emulate).

## 1. Items with an emulator impact (KS2)

### 1.1 CTC: counter reload and state machine (bug fix, timing) - changelog 3.02.02
`device/ctc_chan.vhd@3.02.01 ~136-265` -> `@3.02.04 ~146-289`; notes in `ports.txt@3.02.04 ~303-324`.
- **Terminal count.** 3.02.01 decrements to $00, holds $00 for one 28 MHz clock, then detects the
  zero edge (`t_count_zero and not t_count_zero_d`) and reloads. 3.02.04 detects
  `t_count_next = 0 and t_count_en` on the clock that would decrement 1 -> 0 and reloads the time
  constant directly: **the counter never reads $00** (a read of the channel port at that clock
  returns the time constant instead). `o_zc_to` is registered (`zc_to_d`, ~172-183), so ZC/TO and the
  interrupt come out on the same clock as before; chained channels see the same edges.
- **State machine.** `S_CONTROL_WORD/S_TIME_CONSTANT/S_WAIT/S_RUNNING` becomes
  `S_RESET/S_RESET_TC/S_TRIGGER/S_RUN/S_RUN_TC` (~198-245). "Time constant follows" is now a state,
  not `control_reg` bit 0, and `control_reg` shrinks to bits 7:3 (~105-108, ~263-276). Observable
  differences: (a) a control word with D2 = 1, D1 = 0 while the channel waits for its trigger
  (`S_TRIGGER`) goes back to waiting for a time constant (3.02.01 stayed in `S_WAIT` and could
  start on the trigger before the new constant arrived); (b) while `S_RUN_TC`, every write is the
  time constant (as before); (c) `zc_to_d` clears on hard reset.
- **Vector writes** now only count on channel 0 (`device/ctc.vhd@3.02.04 ~150`); `o_vector_wr` is
  `open` in `zxnext.vhd@3.02.04 ~4578`, so no impact.
- **C:** `zxnext-ctc.c` - `zxnextCtcClock` (the per-clock port of the 3.02.01 state machine, ~236-296),
  `zxnextCtcAdvanceCounterByFires` / `zxnextCtcFirstZcToOffset` (the fast path's `countZeroD`
  bookkeeping) and `zxnextCtcPeekAhead` (the read value). The read value at terminal count and
  state (a) are what a test can pin.
- **P4: implemented.** `zxnext-ctc.c`: `zxnextCtcClock` (reload on the enable that would count 1 -> 0;
  S_TRIGGER + D2 control word -> state 1), `zxnextCtcAdvanceCounterByFires` / `zxnextCtcFirstZcToOffset` /
  `zxnextCtcStartOnTrigger` (a count of 0 never means a pending zero edge). Test:
  `test/zxnext-hw/ctc/ctc-core-versions.test.ts` (CTC-018). The terminal-count read is not pinned: the
  C core's fast path already reloaded at once for 3.02.01 (it never modelled the one clock at $00), so
  both profiles read the same; only state (a) differs observably.

### 1.2 Sprites: no early termination (bug fix, behaviour) - changelog 3.02.02
`video/sprites.vhd@3.02.01 ~825-827, ~849-855, ~984-995` -> `@3.02.04 ~844-848, ~977`.
3.02.01 refused a sprite (and all after it) when its qualify step fell in the last 4/8/16/32 dots
before X = 320 (`spr_cur_notime`), and set the overtime flag for it. 3.02.04 removes that check: the
engine runs until the line-buffer swap, a last sprite may be drawn partly, and `$303B` bit 1 is set
only by the swap time-out (`sprites_overtime <= '1' when state_s /= S_IDLE and line_reset_re = "01"`).
Observable: more sprites per line (at least 100), different `$303B` bit 1.
**C:** `zxnext-ula.c` `zxnextUlaComputeSpriteLineCuts` (~758): drop the `whc >= 288 ... mask` branch;
keep the `clock + drawn > lineClocks` cut and the 3-clock start.
**P4: implemented** as described (`zxnext-ula.c` `zxnextUlaComputeSpriteLineCuts`, the window under
`< 30204`). Test: `test/zxnext-hw/sprites/sprite-time-budget.test.ts`, now per profile (108 / 56 / 29 / 15
sprites drawn at 1x-8x on 3.02.04, the last one cut part-way; 76 sprites finish with no flag).

### 1.3 ULA: I/O and memory contention at the same time (bug fix, timing) - changelog 3.02.02
`video/zxula.vhd@3.02.01 ~591, ~595` -> `@3.02.04 ~591, ~595`. `ioreqtw3_n` now goes low only for a
contended port, and the memory-contention term also needs `ioreqtw3_n = '1'`. In 48K/128K timing
an `IN`/`OUT` to an even (contended) port whose high byte is in a contended page used to be
contended on every T-state (memory term during the whole I/O cycle); 3.02.04 gives the classic
C:1, C:3 pattern. +3 timing is unaffected (it uses `o_cpu_wait_n`).
**C:** `zxnext-cpu.c` `zxnextCpuDelayPortAccess` (~328): today it adds plain T-states and models
**no** I/O contention at all, for either version. Implementing I/O contention is a separate fidelity
item; when it is done, 3.02.01 = "C on every T-state when the high byte is contended", 3.02.04 =
the Zilog-documented patterns.
**P4: skipped** (not modelled in either version); a separate fidelity item.

### 1.4 EAR input: symmetric relaxation and the issue 2 MIC bit (bug fix, behaviour) - 3.02.02
`zxnext_top_issue4.vhd@3.02.01 ~677-689` -> `@3.02.04 ~705-739` (`misc/symmetric_relaxation.vhd`,
new), `zxnext.vhd@3.02.01 ~3456` -> `@3.02.04 ~3951` (port `$FE` read), `~6449` -> `~7059` (MIC).
- 3.02.01: port `$FE` bit 6 = `(relaxed EAR xor pi_fe_ear) or port_fe_ear or (port_fe_mic and
  nr_08_keyboard_issue2)`: with "issue 2 keyboard" (NextReg `$08` bit 0) and MIC set, bit 6 is
  stuck at 1, so tape loading fails.
- 3.02.04: the relaxation counter restarts on **any** edge of the (debounced) EAR level and, once the
  level has been steady for 64 membrane enables (~1.15 ms), outputs `issue2 and mic` instead of the
  level; port `$FE` bit 6 = `relaxed EAR or port_fe_ear`. Without issue 2 + MIC this equals 3.02.01
  (a steady 1 relaxes to 0); with them, a steady level reads 1 and a live tape signal comes through.
  The Pi I2S EAR bit (`pi_fe_ear`) is folded into the relaxation's input instead of XORed at the port.
- MIC line: `beep_mic_final = i_AUDIO_EAR xor (port_fe_mic and issue2) xor port_fe_mic`
  (3.02.01: `port_fe_mic xor i_AUDIO_EAR xor pi_fe_ear`).
- **Check before implementing:** `i_sig => ear_port_i_qq xor not zxn_pi_fe_ear` with `INVERT => '1'`
  makes the relaxation's view of the pin `ear_qq xor pi_fe_ear`, where 3.02.01 had `not ear_qq`.
  Either the polarity of port `$FE` bit 6 relative to the socket flipped (the ROM loader is
  edge-driven and would not notice) or I misread the pin chain; confirm on a 3.02.04 machine
  (read `$FE` with a steady level on EAR) before pinning a test.
- **C:** `zxnext-tape.c` (the relaxation loop, ~240-275: clear on edges, relax to `issue2 & mic`),
  `zxnext-ports.c` (the `$FE` read: drop the `mic & issue2` OR and move the Pi EAR XOR), the Pi EAR
  bit from `zxnext-pi-i2s.c`, and `zxnext-beeper.c` (MIC line, ~7).
- **P4: implemented as the VHDL reads.** The pin chain is unambiguous (`not` binds tighter than
  `xor`): 3.02.01 delivers `not ear_port_i_qq` relaxed; 3.02.04 delivers `ear_port_i_qq xor pi_fe_ear`
  relaxed - the socket's level and the Pi's bit both **inverted** against 3.02.01. Implemented so:
  `zxnext-tape.c` (a 3.02.04 `zxnextTapeInputSync`: the Pi bit in the input, any edge restarts the
  count, relaxed output `port_fe_mic and issue 2`), `zxnext-ula.c` `zxnextUlaReadPortFe` (bit 6 =
  EAR in or EAR out), `zxnext-beeper.c` (`ZXNEXT_BEEPER_MIC_LINE`, `zxnextBeeperSetTapeEarAt` with the
  relaxed flag). Still unconfirmed on a machine: whether real 3.02.04 boards read the inverted level
  (the tests avoid pinning it). Tests: `test/zxnext-hw/tape/tape-ear-versions.test.ts` (TAPE-010
  issue 2 real-time load fails on 3.02.01 and loads on 3.02.04; TAPE-011 levels and relaxation
  lengths, polarity-agnostic), `test/zxnext-hw/audio/pi-i2s-ear-versions.test.ts` (I2S-010, a steady Pi
  bit relaxes on 3.02.04; which edge shows is not pinned).

### 1.5 NextReg `$0A` bit 5 and port `$E7`: swap SD0/SD1 (new bit) - changelog 3.02.03
`zxnext.vhd@3.02.04 ~1224` (signal, hard reset 0), ~5702-5704 (write), ~6446 (read), ~3607-3609
(port `$E7`). Write: bit 5 is stored only when config mode (`$03`) is on **and** bit 2 of the written
value is 1. Read: bit 5 = the swap (bit 2 still reads 0). It survives soft reset. Effect: later
`$E7` writes of `xxxxxx10` / `xxxxxx01` select the other card (`"111111" & not swap & swap`); the
current selection does not change at the moment of the swap.
**C:** `zxnext-nextreg.c` (write handling and `zxnextNextRegReadZeroMask` `$0A` `0x24` -> `0x04`),
`zxnext-sd.c` `zxSdSpiCsWrite` (map the two card selects through the swap).
**P4: implemented.** `zxnext-nextreg.c` (write rule, read mask `0x04`), `zxnext-sd.c`
`zxnextSdSpiCsWrite` (maps `xxxxxx10`/`xxxxxx01` through the swap before the shared SD file's
`zxSdSpiCsWrite`), called from `zxnext-ports.c`. Test: `test/zxnext-hw/sd/sd-swap.test.ts` (SPI-009).

### 1.6 NextReg `$81` bit 3 and port `$1FFD` bit 3: +3 FDC signals (new bit) - changelog 3.02.03
`zxnext.vhd@3.02.04 ~1323` (signal), ~6004 (write), ~6660 (read), ~4235-4253 (motor latch),
~1818-1837 (pins, issue 5 only), ~976 / ~4216 (`port_1ffd_reg` now 3 bits), ~4804 (Multiface).
On every board the bit is stored and reads back; with it set, `OUT ($1FFD)` bit 3 latches the disk
motor (cleared when the bit is 0 and on reset). Only issue 5 drives pins. Observable on KS2:
- `$81` bit 3 reads back what was written (3.02.01: always 0).
- The Multiface +3 readback of `$1FFD` (MF port with A15:12 = `0001`, `nr_0a_mf_type = "00"`):
  3.02.01 returned the whole last byte written to `$1FFD`; 3.02.04 returns
  `"0000" & motor & bits 2:0`, with motor = 0 unless `$81` bit 3 was set when bit 3 was written.
- **C:** `zxnext-expansion.c` (`$81` store and read, read mask), `zxnext-memory.c` (`memPort1ffd`
  keeps bits 2:0; a separate motor latch), `zxnext-multiface.c` (~68, the readback).
- **P4: implemented.** `zxnext-expansion.c` (`zxnextExpansionFdc`, the motor latch
  `zxnextExpansionWriteMotor`, cleared on reset and while bit 3 is 0), `zxnext-nextreg.c` (read mask
  `0x07`), `zxnext-memory.c` (`memPort1ffd` keeps bits 2:0), `zxnext-multiface.c` (readback),
  `zxnext-ports.c` (the latch on every `$1FFD`-decoded write, port enable and `$7FFD` lock ignored, as
  `port_xffd` in ~4243-4248). Test: `test/zxnext-hw/multiface/multiface-1ffd-motor.test.ts` (MF-008).

### 1.7 NextReg `$A0` bit 1: Pi SPI slave enable (new bit) - changelog 3.02.04
`zxnext.vhd@3.02.04 ~2568-2601` (GPIO roles), ~5586-5587 (soft reset clears bits 7:2 and 0, **not**
1), ~6723 (read: bit 1 = `en(1) and g_option(4)`, 1 on KS2). Observable: bit 1 is writable,
reads back, and survives a soft reset (hard reset = 0); bit 0 (master) is overridden while bit 1 is
set. The slave itself (the Pi pausing the CPU, reading/writing NextRegs, SRAM, BRAM and CPU
registers) has no emulator counterpart.
**C:** `zxnext-nextreg.c` (read mask `$A0` `0xc6` -> `0xc4`; soft-reset path keeps bit 1).
**P4: implemented** as described. Test: `test/zxnext-hw/gpio/pi-spi-slave.test.ts` (GPIO-008).

### 1.8 MD pad: A + B + C + START is a reset button (behaviour) - changelog 3.02.02
`zxnext_top_issue4.vhd@3.02.01 ~711` -> `@3.02.04 ~761-763`: `btn_reset_n_i_q` is also pulled low
while either connector reports B, C, A and START together (`zxn_joy_*(4..7)`, the
`MODE X Z Y START A C B U D L R` order). That is the board's reset button: a soft reset.
**C:** `zxnext-input.c` (`zxnextJoystickLeftState/RightState`, bits 4-7) raising the same soft reset
as the reset button (`zxnext.c` ~335).
**P4: implemented**, with the button's whole path: the line is debounced (8 enables of 2^18 clocks,
~75 ms) and emu_fnkeys turns a release after less than 100 enables (~0.94 s) into F4 (soft reset,
not in config mode) and a longer press into F1 (hard reset). `zxnext-input.c` `zxnextInputOnFrameWrap`
(sampled once a frame, from the frame wrap in `zxnext-cpu.c`), raising `zxnextResetRequest` 1 / 2.
Test: `test/zxnext-hw/joystick/md-pad-reset.test.ts` (JOY-009).

### 1.9 Things 3.02.04 fixed that Klive never had (no change, but tests must not encode the bug)
- **Memory cycle delay removed** (`zxnext.vhd@3.02.01 ~3099-3142` -> `@3.02.04 ~3438`, ~3312): 3.02.01
  delayed `sram_memcycle` by 7/3/1/0 28 MHz clocks at 3.5/7/14/28 MHz so a slow expansion-bus ROMCS
  could arrive. Its side effects are the 3.02.02 fixes "DMA read byte one cycle behind at 3.5 and
  7 MHz" (`dma.vhd` is unchanged) and "LDPIRX at all CPU speeds". The C core reads memory at once,
  so it already behaves as 3.02.04. If a DMA or LDPIRX test pins 3.02.01's stale byte, it must be
  guarded.
- **`EX (SP),HL` machine cycles** (`cpu/t80n_mcode.vhd@3.02.01 ~667-692` -> `cpu/t80n/t80n_mcode.vhd@3.02.04
  ~668-693`, `cpu/t80n/t80n.vhd@3.02.04 ~1383-1450`): 3.02.01's T80N ran read (SP), write (SP),
  read (SP+1), write (SP+1); 3.02.04 runs the Zilog order read SP, read SP+1, write SP+1, write SP
  (19 T either way) and loads WZ. The shared Z80 (`src/emu/z80/wasm/z80.c` `opE3ExSpHl`, ~1804)
  already uses the Zilog order under `Z80_T80N`. Only per-cycle contention differs; nothing to do
  unless 3.02.01 must be exact (not recommended).
- **P4: no change**, as planned.

## 3. NextReg description delta (D5)

`nextreg.txt` changed in 72 hunks, almost all re-indentation and wording. The meaning changes:

| Reg | 3.02.04 text | Set |
|---|---|---|
| `$0A` | bit 5 = swap SD0/SD1 (hard reset 0, config mode only, affects later `$E7` writes); bit 2 = write enable for bit 5 | 30204 delta |
| `$81` | bit 3 = enable +3 FDC signals on the expansion bus (issue 5 only; stored and readable on all boards) | 30204 delta |
| `$A0` | bit 1 = SPI in slave mode Pi -> Next (hard reset 0, overrides master, reads 0 if unavailable); bit 0 = master mode | 30204 delta |
| `$04` | bits 7:0 bank; bit 7 ignored except on issue 5 | 30204 delta (board note) |
| `$0F` | adds `0011` = issue 5 | 30204 delta (board note) |
| `$F0`, `$F8`-`$FA` | "Issue 4 only" -> "Issues 4 and 5" | 30204 delta (board note) |
| `$7F` | "soft reset = 0xff" -> "hard reset = 0xff" | **base fix**: the VHDL of both versions only initialises it (`zxnext.vhd@3.02.01 ~1210`) |
| `$02` | footnote "only one of bits 1:0 will be set" | base wording (true of both) |

**P4: `$0A`, `$81`, `$A0` are in `src/emu/machines/zxNext/nextRegSets/30204.ts`** (base descriptor
copied, only the re-meant bits changed; the board notes are not added). Two base-set errors seen on the
way are fixed in `nextRegDescriptors.ts`: the base `$0A` documented bit 5 as the SD swap (3.02.01 says
"Reserved, must be zero"), and the base `$81` carried `$80`'s bit 2-0 slices.

`ports.txt` changed only in the CTC notes (section 1.1). Port `$E7`'s swap and `$1FFD` bit 3 are not
in `ports.txt`; the IDE's port descriptions get them from this file.

## 5. Recommendation for the P2 gate

**D3: keep compile-time guards; no second file.** The KS2 delta is eight items, each local: one
state-machine function and two helpers in the CTC, one branch in the sprite time budget, a register
bit or a read mask in four places, the relaxation loop and the `$FE` read, and one input combination.
None rewrites a subsystem; the largest, the CTC, is about 60 C lines in one function plus the
`countZeroD` bookkeeping, which reads better as one `#if ZXNEXT_CORE_VERSION >= 30204` block around
`zxnextCtcClock`'s next-state/reload logic than as a forked `zxnext-ctc-30204.c`. Board issue can
stay a compile-time constant: KS2 builds share every board-gated line, and the issue 5 items are
not targeted. Two notes for P3/P4:
- The 3.02.01 artifact is already 3.02.04-like in the two "fixes Klive never had" (1.9); leave them,
  do not guard them back in.
- I/O contention (1.3) is missing in both versions; treat it as its own fidelity item, implemented
  once with a guard for the 3.02.01 pattern only if it is wanted.

**D5: confirmed as planned.** `nextRegSets/30204.ts` needs three re-meant registers (`$0A` bits 5/2,
`$81` bit 3, `$A0` bit 1) and, optionally, the board notes (`$04` bit 7, `$0F` `0011`, `$F0`/`$F8`-`$FA`).
The `$7F` reset wording is a fix to the base set, not a delta. The assembler's union set gains no new
register numbers, only bits.
