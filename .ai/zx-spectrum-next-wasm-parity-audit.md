# ZX Spectrum Next WASM Parity Audit

Created: 2026-08-16

## Scope

This audit compares the current ZX Spectrum Next TypeScript implementation with
the working ZX Spectrum 48K, 128K, and +2E/+3E WASM V2 integrations. It is a
migration map only; it does not introduce ZX Spectrum Next WASM code.

The TypeScript Next implementation remains the behavioral oracle. Spectrum WASM
code is a pattern reference for loader shape, adapter boundaries, typed views,
and focused oracle tests, but it is not proof that a behavior can be shared by
the Next backend.

## Pattern Summary

- Existing Spectrum WASM machines use a two-value implementation switch and a
  factory that chooses `"typescript"` or `"wasm"` from config.
  See `ZxSpectrum48Implementation.ts:10-22`,
  `ZxSpectrum48MachineFactory.ts:12-16`,
  `ZxSpectrum128Implementation.ts:9-22`,
  `ZxSpectrum128MachineFactory.ts:12-16`, and
  `ZxSpectrumP3eImplementation.ts:9-22`.
- Existing Spectrum WASM loaders validate required exports and construct stable
  typed views over exported memory before the adapter runs.
  See `Sp48WasmV2Loader.ts:337-405` and
  `Sp128WasmV2Loader.ts:333-405`.
- Existing Spectrum WASM adapters keep hot deterministic state in C/WASM and
  expose public machine APIs from that state: frame execution, memory, ports,
  screen, audio, CPU registers, bus events, tape, and disk where applicable.
  See `ZxSpectrum48WasmV2Machine.ts:124-183`,
  `ZxSpectrum48WasmV2Machine.ts:216-260`,
  `ZxSpectrum128WasmV2Machine.ts:112-213`, and
  `ZxSpectrumP3eWasmV2Machine.ts:375-407`.
- Existing C backends own the normal frame loop and preserve frame overshoot.
  See `sp48.c:371-470`.
- Existing WASM tests centralize artifact builds, test ROMs, oracle machines,
  and test-only controls under `test/wasm/zxSpectrum/wasm-test-helpers.ts:77-204`.

## Guardrails For Later Steps

- Do not claim a Next behavior can reuse an existing Spectrum WASM behavior
  unless a future test cites the relevant Next TypeScript source or a copied
  Next test as the oracle.
- Any adapter method inherited from `ZxNextMachine` must be audited as a
  potential stale TypeScript state read when WASM owns that surface.
- Use public IDE-facing APIs in parity tests first. Raw WASM exports can isolate
  C behavior, but they do not prove the renderer, debugger, disassembler, or
  panels see the same state.
- The first Next WASM scaffold should expose deterministic diagnostics with an
  `implementationIncomplete` flag and a list of scaffolded surfaces.
