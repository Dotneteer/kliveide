# Enterprise 64/128 — the NICK video chip and display system

Research notes for a cycle-accurate NICK emulation inside Klive IDE.
Written in our own words from the sources listed at the end; emulator logic is
*described*, not copied. Anything that is our own reasoning rather than a stated
fact is marked *inference*. Where sources disagree, both versions are given.

Abbreviations: **LPT** = Line Parameter Table, **LPB** = one 16-byte Line
Parameter Block (one entry of the LPT, describing one "mode line"), **slot** =
one NICK character clock of 16 NICK cycles, **LD1/LD2** = the two line data
pointers.

Primary references used throughout:

- Nick Chip Programmer's Guide (Enterprise technical documentation, fan-hosted
  transcription): http://www.ep128.hu/Ep_Konyv/Technical_Documentation_Nick_Chip_Programmers_Guide.html
  (mirror: http://ep.lgb.hu/doc/Nick.html — certificate expired at time of research)
- ep128emu (István Varga) — `src/nick.cpp`, `src/nick.hpp`, `src/ep128vm.cpp`,
  `src/dave.cpp`: https://github.com/istvan-v/ep128emu
- MAME — `src/mame/enterprise/nick.cpp`, `nick.h`, `ep64.cpp`:
  https://github.com/mamedev/mame/tree/master/src/mame/enterprise
- CLK (Tom Harte) — `Machines/Enterprise/Nick.cpp`, `Enterprise.cpp`, and the
  wiki page https://github.com/TomHarte/CLK/wiki/The-Enterprise
- Xemu / Xep128 (LGB) — `targets/ep128/nick.c`, `dave.c`:
  https://github.com/lgblgblgb/xemu

Of these, ep128emu is the most detailed slot-level model (it reads the LPB in
specific slots, emulates the floating data bus, models CPU contention with a
phase-dependent wait); CLK is the second cycle-level model; MAME and Xemu are
line-based. *Inference:* ep128emu is generally treated by the Enterprise
community as the reference emulator, so where models disagree its behaviour is
the safest default — but the disagreements are listed so they can be tested
against real software.

## 1. Clocks and frame timing

### 1.1 Stated facts

| Quantity | Value | Source |
|---|---|---|
| Line period | 64 µs (generated by NICK itself) | Nick guide §"Line Parameter Table" — http://www.ep128.hu/Ep_Konyv/Technical_Documentation_Nick_Chip_Programmers_Guide.html |
| Slots per line | 57, numbered 0–56 | Nick guide (margins section); ep128emu `nick.hpp` comment "57 slots = 912 pixels"; CLK `Nick.cpp` (`line_length = 912`) |
| NICK cycles per slot | 16 (one pixel per NICK cycle at the highest resolution) | CLK wiki https://github.com/TomHarte/CLK/wiki/The-Enterprise |
| NICK cycles per line | 57 × 16 = 912 | CLK wiki; ep128emu `nick.hpp` |
| Slot use | slots 0–7 read the LPB, slots 54–56 are DRAM refresh, slots 8–53 (46 slots) are available for display data | Nick guide (margins section) |
| Bytes per slot | up to 2 video-RAM bytes per slot | Nick guide |
| Lines per normal PAL frame | 312 (vertical timing is entirely defined by the LPT) | Nick guide |
| Z80 clock | 4 MHz = 8 MHz oscillator / 2 | MAME `ep64.cpp` (PCB notes: "Z80A … clock input 4MHz [8/2]") |
| NICK clock pin | the expansion bus carries a "14 MHz Clock (Nick)" on pin B29, separate from the 8 MHz (A23), 4 MHz CPU (A22) and 1 MHz (A21) clocks | https://wiki.enterpriseforever.com/wiki/Expansion_Bus |
| PAL crystal | 4.433619 MHz crystal near the LM1889 modulator | MAME `ep64.cpp` PCB comments |

### 1.2 The exact NICK clock — two candidates

The guide states that NICK is phase-locked to the PAL colour subcarrier but does
not give the frequency. The CLK wiki works out two candidates
(https://github.com/TomHarte/CLK/wiki/The-Enterprise):

1. **912 NICK cycles = 284 subcarrier cycles.** NICK clock ≈ **14 237 536 Hz**
   (exactly 4 433 618.75 × 912 / 284), line ≈ 64.06 µs, ≈ 15 611 lines/s.
   **ep128emu uses this**: `Ep128VM` constructor sets `nickFrequency(889846)`,
   which is the *slot* rate (14 237 536 / 16) — `src/ep128vm.cpp`, constructor
   and `setVideoFrequency()`. CLK also uses it (ratio 40434603/11360000 NICK
   cycles per Z80 cycle ≈ 3.559) — `Machines/Enterprise/Enterprise.cpp`
   constructor.
2. **NICK clock = 16/5 of the subcarrier** ≈ 14 187 580 Hz, line ≈ 64.28 µs
   (≈ 285 colour cycles). Not used by any emulator examined.

MAME is a simplification: it clocks NICK from the 8 MHz oscillator and models
**64** slots of 16 pixels per line (1024 pixel positions, 800 visible) at a
16 MHz pixel clock — `src/mame/enterprise/nick.h` (`ENTERPRISE_SCREEN_WIDTH`
= 64*16, `ENTERPRISE_VISIBLE_WIDTH` = 50*16, height 312, visible 35*8),
`ep64.cpp` (`screen.set_raw(XTAL(8'000'000)*2, …)`). This contradicts the
57-slot structure in the guide and in ep128emu/CLK; **do not follow MAME for
timing**.

Xemu models 58 slots (0–57) per line — `targets/ep128/nick.c`,
`nick_render_slot()` — another deviation from the 57 in the guide.

### 1.3 Derived timing (using candidate 1, 4 MHz Z80) — *inference (arithmetic)*

| Quantity | Value |
|---|---|
| NICK cycle | ≈ 70.24 ns |
| Slot (16 NICK cycles) | ≈ 1.1238 µs ≈ **4.4952 Z80 T-states** (ep128emu `cpuCyclesPerNickCycle`) |
| NICK cycles per Z80 T-state | ≈ 3.5594 |
| Line (912 NICK cycles) | ≈ 64.055 µs ≈ **256.22 Z80 T-states** |
| 312-line frame | ≈ 19.985 ms ≈ **79 942 T-states**, ≈ **50.04 Hz** |

The Z80 clock and the NICK clock are **asynchronous** (different oscillators;
CLK wiki: NICK "runs asynchronously from the processor"). The number of
T-states per line is therefore not an integer, and an emulator must carry a
fractional phase between the two clock domains. ep128emu does this with 32.32
fixed-point counters (`Ep128VM::run()`, `updateTimingParameters()` in
`src/ep128vm.cpp`); CLK uses a rational ratio in a `JustInTimeActor`
(`Enterprise.cpp`).

*Inference for Klive:* a "frame" for the IDE's frame loop has to be defined
by the LPT (e.g. by the start of the VSYNC-mode line), not by a fixed T-state
count, because the frame length is whatever the LPT says (normally 312 lines).

### 1.4 Dave's clock (for context)

Dave port BFh bit 1 selects whether Dave assumes an 8 MHz (bit clear) or 12 MHz
(bit set) input; in both cases its internal tick is 250 kHz — ep128emu
`src/dave.cpp`, register 1Fh handling (source comment there). Dave's clock is
locked to the CPU clock (8 MHz / 2), not to NICK. MAME clocks Dave from the
same 8 MHz XTAL (`ep64.cpp`).

### 1.5 Interlace

The guide says resolution reaches 672 × 512 "with interlace" and that interlace
or special effects may need an LPT longer than 312 lines (Nick guide, LPT and
features sections). NICK has no interlace bit: an interlaced picture is made by
an LPT whose total length is 625 lines with the vertical sync placed so that the
two fields are offset by half a line (*inference*: the margins of a VSYNC-mode
line choose where in the line the vertical sync starts and stops, which is
exactly what a half-line offset needs). The enterpriseforever wiki states that
the standard EP picture is not interlaced
(https://wiki.enterpriseforever.com/wiki/Nick). An emulator therefore has to
detect fields from the position of vertical sync, as ep128emu does by passing
the slot number to `vsyncStateChange(bool, uint8_t currentSlot_)` (`nick.hpp`).

## 2. The slot structure of one line

### 2.1 ep128emu model (`src/nick.cpp`, `Nick::runOneSlot()`)

| Slot | Activity |
|---|---|
| 0 | read LPB bytes 0, 1 (scanline count, mode byte) |
| 1 | read LPB bytes 2, 3 (left margin + LSBALT/MSBALT, right margin + ALTIND) |
| 2 | read LPB bytes 4, 5 (LD1) |
| 3 | read LPB bytes 6, 7 (LD2) |
| 4–7 | read LPB bytes 8–15 (palette 0–7, two per slot) |
| 7 | also starts the visible line buffer (falls through into the slot-54 path); a FIXME comment says that on hardware slot 7 is still horizontal blanking |
| 8–53 | display data slots (call the current renderer) |
| 54 | rendered from the floating data bus (see §9.1) |
| 55 | the finished line is handed to the display (`drawLine()`) |
| 56 | end-of-line bookkeeping: line counter decrement, LPT pointer advance/reload, `lptFlags` recompute; then wraps to slot 0 |

Important: **ep128emu re-reads the whole LPB on every scanline**, not only on
the first line of a mode line. A program that modifies the LPB in RAM in the
middle of a mode line changes mode, margins and palette from the next scanline
on. (The guide also says NICK reads the block during horizontal blanking at the
start of a scanline.) What depends on "first line of the block" is only the
loading of LD1/LD2 and the line counter (§3.4).

### 2.2 CLK model (`Machines/Enterprise/Nick.cpp`, `Nick::run_for()`)

Same byte-to-window assignment (window 0: bytes 0–1, window 1: 2–3, window 2:
LD1, window 3: LD2, windows 4–7: palette), **but** CLK latches the parameters
and palette only on the first line of each block (when
`should_reload_line_parameters_` is set). This **disagrees with ep128emu**.
*Inference:* ep128emu's per-line re-read is the more plausible hardware model
(NICK has no reason to suppress the fetch, and the palette fetch occupies the
same slots on every line in both models); worth testing with a demo that
rewrites palette entries of the current LPB mid-block.

### 2.3 Sync, blanking and burst positions (CLK)

CLK outputs per line: windows 0–3 horizontal sync, 4–5 blank, 6 to
`first_pixel_window_` colour burst (first pixel window 8 for RGB, 10 for
composite in its framing), then pixels inside the margins and border colour
outside — `Nick.cpp`. ep128emu has no explicit HSYNC signal; horizontal timing
is implicit in the 57-slot line (`nick.cpp`). The enterpriseforever wiki gives
≈ 53 µs visible / ≈ 11 µs retrace per 64 µs line
(https://wiki.enterpriseforever.com/wiki/Nick).

### 2.4 Visible area

- Guide: margins of 10 (left) and 52 (right) are the practical limits for a TV
  (42 slots ≈ 672 pixels at full resolution), because of overscan.
- ep128emu: the default margins after reset are 8 and 54 (46 slots); its
  display receives 48 slots of 16 pixels = 768 pixels per line (`nick.hpp`,
  `drawLine` comment), i.e. slots 7–54.
- MAME: 50 visible slots of its 64 (`nick.h`).
- Xemu: 46 slots × 16 = 736 pixel surface (`nick_addressing_init()`), raster
  lines 25–312 visible.

## 3. The Line Parameter Table

### 3.1 Location and base pointer

- The LPT lies in NICK's 64K video address space (§6) and must start on a
  16-byte boundary: NICK supplies address bits A0–A3 itself (Nick guide, "Line
  Parameter Base Pointer").
- The base pointer is written through two ports: **82h (LPL)** = address bits
  A4–A11, **83h (LPH) bits 0–3** = address bits A12–A15 (Nick guide; ep128emu
  `Nick::writePort()`; CLK `Nick::write()`; MAME `lpl_w()/lph_w()`).
- A new base takes effect only when the current scan of the table finishes, i.e.
  when an LPB with RELOAD set ends (Nick guide). Writing the base while NICK is
  reloading can mix old and new bytes, so the guide recommends doing it from the
  video interrupt.

### 3.2 LPB layout (16 bytes)

| Byte | Name | Content |
|---|---|---|
| 0 | SC | two's complement of the scanline count: lines = 256 − SC, SC = 0 → 256 lines |
| 1 | MB | mode byte (below) |
| 2 | LM | bits 0–5 left margin (slot number); bit 6 **LSBALT**; bit 7 **MSBALT** |
| 3 | RM | bits 0–5 right margin (slot number); bit 6 **ALTIND1**; bit 7 **ALTIND0** |
| 4, 5 | LD1L, LD1H | line data pointer 1 (low byte first) |
| 6, 7 | LD2L, LD2H | line data pointer 2 (low byte first) |
| 8–15 | COL0–COL7 | palette entries 0–7 (colour bytes, §5) |

Sources: Nick guide; ep128emu `NickLPB` struct in `nick.hpp` and slot 0–7 code
in `nick.cpp`; MAME `LPT_ENTRY` in `nick.h`.

**Mode byte (MB):**

| Bit(s) | Name | Meaning |
|---|---|---|
| 7 | VINT | video interrupt request for this mode line (§7) |
| 6–5 | CM | colour mode: 00 = 2, 01 = 4, 10 = 16, 11 = 256 colours |
| 4 | VRES | 1 = full vertical resolution (LD1 keeps counting from line to line); 0 = LD1 reloaded every scanline |
| 3–1 | VM | video mode: 000 VSYNC, 001 PIXEL, 010 ATTRIBUTE, 011 CH256, 100 CH128, 101 CH64, 110 invalid, 111 LPIXEL |
| 0 | RELOAD | last LPB of the table: after it, the LPT pointer returns to the base |

Same in Nick guide, ep128emu (`nick.cpp` slot 0: IRQ = bit 7, colour mode =
bits 6–5, VRES = bit 4, video mode = bits 3–1, reload = bit 0), MAME
(`(MB >> 1) & 7`), CLK.

### 3.3 Margins

- Margins are **slot numbers** (0–63, 6 bits). Display ("pixels") is on from
  the left-margin slot up to but not including the right-margin slot; outside
  it NICK outputs the border colour (port 81h) — Nick guide.
- If right < left, the whole line is border (guide). In ep128emu the
  comparison is done per slot against the *current* slot number before that
  slot's LPB read, so:
  - a margin of 0 or 1 effectively uses the value from the previous line's LPB
    because the comparison happens before slot 0/1 has fetched the new margin
    (*inference from the ordering in* `runOneSlot()`);
  - a right margin ≥ 57 is never matched, so display stays on through the end
    of the line and into the next line until the right margin is met — this is
    what the guide's VSYNC recipe relies on (margins 63 "never reached").
- Renderer choice (mode, colour mode, ALT bits) is latched **at the left-margin
  slot** in ep128emu (`setRenderer()` is called only at margin events), so
  mode-byte changes take effect at the next left margin.
- CLK: `is_sync_or_pixels_` toggled at the margin windows; a margin value of 57
  or more is ignored; margin 0 applies at line start (`Nick.cpp`).
- MAME draws border for slots outside `[LM, RM)` within its visible range
  (`do_left_margin()`, `do_right_margin()`, `do_display()`).

### 3.4 Line counter, LD1/LD2 loading, VRES (ep128emu `runOneSlot()`)

- Slot 2: LD1 is loaded from LPB bytes 4–5 if this is the first line of the
  block **or** VRES is clear. So with VRES set LD1 keeps counting across the
  lines of the block; with VRES clear every line repeats the same data.
- Slot 3: in character modes (CH256/CH128/CH64) LD2 is first incremented by 1
  (next font row); then, if this is the first line of the block (lines
  remaining ≤ 0), LD2 is loaded from bytes 6–7 and the counter is set to the
  block's line count.
- Slot 56: lines remaining is decremented; when it reaches 0 the LPT pointer
  moves (next §3.5).
- During the "control" slots 0–7 and 54–56, **if display is enabled** (i.e. the
  margins put those slots inside the display window), LD1 still advances by 1
  (or 2 in PIXEL mode) and LD2 by 1 in ATTRIBUTE mode, mirroring a fetch that
  happens without useful data. The address advance therefore depends on the
  margins.
- MAME agrees on the LD1/VRES rule and on per-line LD2 increment in character
  modes (`do_line()`); CLK does the same at line end (`Nick.cpp`).

### 3.5 Advancing and reloading the LPT pointer; port 83h bits 6–7

**Guide (port 83h, LPH):**

| Bit | Meaning |
|---|---|
| 0–3 | LPT base address A12–A15 |
| 4–5 | unused |
| 6 | 1 = normal; 0 = inhibit clocking of the line-parameter counter |
| 7 | 1 = normal; 0 = force immediate reload of the base pointer |

Normal value has bits 6 and 7 both set. Forced-reload recipe (needed at power-on
when the pointer is random): write LPL; write LPH with bits 7,6 = 0,0; then with
bit 6 = 1, bit 7 = 0; then with both set.

**ep128emu** (`Nick::writePort()` case 3, `runOneSlot()` slot 56; `lptFlags`
documented in `nick.hpp`):

- Port write: if bit 6 is 0, the pending flags are cleared. If bit 6 is 1 and
  bit 6 changed, flag 80h ("act at end of this line") is set; if bit 6 is 1 and
  bit 7 is 0, flag 40h ("reload to base") is set.
- End of line (slot 56): if the block has ended *or* flag 80h is pending, and
  port 83h bit 6 is set: the current LPT address goes back to the base if the
  LPB's RELOAD bit or flag 40h is set, otherwise it advances by 16 (wrapping
  within 64K). With bit 6 clear the pointer stays where it is (the same LPB is
  re-used).
- Flags are then recomputed: 40h stays only while bit 6 = 1 and bit 7 = 0; 80h
  is dropped.

So in ep128emu the guide's recipe works as: step 2 (bit 6 = 0) stops the
counter, step 3 (bit 6 rising with bit 7 = 0) makes the next line start at the
base immediately (not waiting for the block to end), step 4 returns to normal.

**MAME** (`lph_w()`, `do_line()`) implements the same flag scheme (flag 80h
when clocking is re-enabled, 40h when the active-low reload bit is cleared).

**CLK** (`Nick::write()` case 3) differs: a rising edge of **bit 7** forces the
current line to be the last of its block and sets reload; bit 6 is stored but
unused; the source comment calls the top two bits "still a mystery". **Xemu**
(`nick_set_lpth()`) treats bit 6 as the LPT clock enable and bit 7 as an
active-low reset that immediately resets the LPT address, slot, pixel and
scanline counters; at init it writes random port values but forces bits 6–7 on
(`nick_init()`).

*Recommendation (inference):* follow ep128emu — it is the only model that
matches every step of the guide's recipe.

### 3.6 Power-on state

ep128emu's constructor sets defaults (1 line, RELOAD, video mode 7, margins
8/54, data bus FFh) but then randomises the four port registers
(`randomizeRegisters()`), so the LPT base is undefined until EXOS sets it —
which is why the guide prescribes the forced-reload sequence. Xemu does the
same with random ports.

## 4. Video modes

Pixel widths below are in NICK cycles; at full speed a slot is 16 NICK cycles.
Counts per slot from ep128emu renderers (`render_PIXEL_*`, `render_ATTRIBUTE`,
`render_CH*`, `render_LPIXEL_*` in `nick.cpp`) and the guide.

### 4.1 Mode summary

| VM | Mode | Data fetched per slot | LD1 | LD2 | Pixels per slot (2/4/16/256 col) |
|---|---|---|---|---|---|
| 0 | VSYNC | (ep128emu: one byte from LD1 onto the bus, nothing shown) | +1 | — | none: blanking level, sync controlled by margins |
| 1 | PIXEL | 2 bitmap bytes from LD1 | +2 | unused | 16 / 8 / 4 / 2 |
| 2 | ATTRIBUTE | attribute byte from LD1, bitmap byte from LD2 | +1 | +1 | 8 (2-colour only) |
| 3 | CH256 | char code from LD1, glyph from (LD2 × 256) + code | +1 | +1 per line | 8 / 4 / 2 / 1 |
| 4 | CH128 | char code from LD1, glyph from (LD2 × 128) + (code & 7Fh) | +1 | +1 per line | 8 / 4 / 2 / 1 |
| 5 | CH64 | char code from LD1, glyph from (LD2 × 64) + (code & 3Fh) | +1 | +1 per line | 8 / 4 / 2 / 1 |
| 6 | invalid | ep128emu: generic renderer with glyph address FFFFh | — | — | see §4.6 |
| 7 | LPIXEL | 1 bitmap byte from LD1 | +1 | unused | 8 / 4 / 2 / 1 |

Horizontal resolution with the guide's practical 42 slots: PIXEL 672 / 336 /
168 / 84; LPIXEL and character modes 336 / 168 / 84 / 42; up to 42 characters
per line in character modes, "84-column text" being achieved in PIXEL-based
software text (guide feature list). With 46 slots (margins 8–54): PIXEL 736 in
2 colours (*arithmetic*).

### 4.2 Bit-to-pixel mapping

- **2 colours:** 8 pixels per byte, bit 7 leftmost; 0 → palette 0, 1 →
  palette 1 (plus ALT offsets, §4.5).
- **4 colours:** 4 pixels per byte, leftmost first; pixel *k* (0–3) takes its
  high bit from bit (3−k) and its low bit from bit (7−k). Guide: bit pairs
  (b3,b7), (b2,b6), (b1,b5), (b0,b4). MAME's table: index = b7 | (b3 << 1).
- **16 colours:** 2 pixels per byte. Left pixel index bits 3..0 = b1, b5, b3,
  b7; right pixel = b0, b4, b2, b6. Indices 8–15 come from FIXBIAS (§5.2).
  MAME: index = b7 | b3<<1 | b5<<2 | b1<<3.
- **256 colours:** each byte is the colour byte itself; COL0–7 unused.

Sources: Nick guide (colour modes); ep128emu `fourColors`/`sixteenColors`
tables; MAME `m_pen_idx_4col`, `m_pen_idx_16col`.

*Inference:* the odd interleaving means a byte's 4- and 16-colour pixels are
formed by the same bit lines that make a 2-colour byte, just with fewer, wider
pixels; an emulator should use lookup tables (as all emulators do).

### 4.3 PIXEL and LPIXEL

- LD1 points at the first byte; LD2 is unused.
- PIXEL reads 2 bytes per slot (full horizontal resolution); LPIXEL reads 1
  byte per slot (half resolution, half the RAM).
- VRES set: each line continues from where the previous line stopped (LD1 not
  reloaded). VRES clear: the same bytes repeat on every line of the block.

Source: Nick guide (pixel modes); ep128emu (`render_PIXEL_*`, `render_LPIXEL_*`).
CLK's LPixel outputs only the first pixel of each byte in multi-bpp modes
(`Nick.cpp`) — *inference:* that is a simplification of "half the horizontal
resolution" and agrees with the per-slot counts above (each LPIXEL pixel is
twice as wide).

### 4.4 Character modes CH256 / CH128 / CH64

- LD1 points at character codes, one per slot (≤ 42 per line).
- LD2 holds the font address divided by 256/128/64: NICK supplies the low 8/7/6
  bits from the character code. The font must be aligned accordingly (guide
  states the CH128 case explicitly; the CH64/CH256 divisors are implied).
- The font is stored row-major by scanline: first the top row of every
  character, then the second row, and so on. LD2 is incremented each scanline
  (ep128emu slot 3, MAME `do_line()`, CLK line end) — so for CH128 the next
  row is 128 bytes further on.
- VRES should be clear (LD1 reloaded each line, so every scanline of the block
  re-reads the same character codes).
- The colour mode applies to the glyph byte (8/4/2/1 pixels per slot).
- Spare high bits of the character code select alternate palettes (§4.5).

Sources: Nick guide (character modes); ep128emu `render_CH256_*`,
`render_CH128_*`, `render_CH64_*`; MAME `do_ch256/do_ch128/do_ch64`; CLK
(`ram[(LD2 << index_bits) + (char & mask)]`).

### 4.5 Alternate palettes: LSBALT, MSBALT, ALTIND0, ALTIND1 (2-colour only)

| Flag (LPB) | Applies to | Effect |
|---|---|---|
| MSBALT (byte 2 bit 7) | PIXEL/LPIXEL bitmap bytes | bit 7 of each byte is forced to 0 for display; if it was 1, the byte uses colours 2/3 instead of 0/1 (palette offset +2) |
| LSBALT (byte 2 bit 6) | PIXEL/LPIXEL bitmap bytes | bit 0 forced to 0; if it was 1, colours 4–7 instead of 0–3 (offset +4) |
| ALTIND1 (byte 3 bit 6) | character modes | char code bit 7 set → colours 2/3 (offset +2) |
| ALTIND0 (byte 3 bit 7) | character modes | char code bit 6 set → colours 4–7 (offset +4) |

Sources: Nick guide; ep128emu `nick.hpp` (`altInd0`, `altInd1`, `lsbAlt`,
`msbAlt`) and renderer table. In CH128 the code is 7 bits, so bit 7 is free
for ALTIND1; in CH64 both bits 7 and 6 are free (ep128emu `render_CH64_*`
covers all four ALTIND combinations in 2 colours). In CH256 all 8 bits are part
of the code, yet ep128emu still applies ALTIND when set (*inference from its
renderer table: CH256_256 accepts any altInd; others use generic path*).

ep128emu differences to know: its specialised LSBALT/MSBALT renderers always
mask the bit, while its generic renderer masks only when the bit is set; the
offset is OR-ed with the pixel index, so in 4/16-colour modes the high bits can
overlap. Only the ALT combinations that the guide defines have fast renderers;
everything else goes through `render_Generic`, which reproduces the hardware's
"undefined" combinations (ALT bits in 4/16-colour modes, ALTIND in PIXEL mode
taken from data bits 6/7, etc.). CLK's comment notes that LSBALT/MSBALT and
ALTIND0/ALTIND1 "appear to have opposite effects" (bit 6 vs bit 7 naming) —
this is just the layout in the table above.

### 4.6 ATTRIBUTE mode

- LD1 → attribute bytes, LD2 → 2-colour bitmap; one of each per slot, 8 pixels.
- Attribute high nibble = colour for bitmap 0 (paper/background), low nibble =
  colour for bitmap 1 (ink/foreground); nibbles are palette indices 0–15, so
  8–15 come from FIXBIAS.
- VRES set: one attribute per bitmap byte. VRES clear: attributes repeat on
  each line of the block (character-cell colour like a Spectrum).
- The guide says the colour mode must be 2-colour, otherwise results are
  "unpredictable". ep128emu's `render_Generic` defines that case: in 4-colour
  attribute mode the bitmap byte drives 4 pixels (bits 7–4), in 16-colour 2
  pixels (bits 7–6), with LSB/MSB masking applied.

Sources: Nick guide; ep128emu `render_ATTRIBUTE`; MAME `do_attr()`; CLK
(`output_attributed`).

### 4.7 VSYNC mode

- No data is displayed; the video output is held at blanking level and colour
  burst is suppressed.
- The margins choose where in each line the **vertical sync pulse** turns on
  (left margin) and off (right margin). During active vertical sync, horizontal
  sync pulses are inverted to keep TVs locked.
- Guide's recommended 25-line sequence (other 12 bytes zero):

| SC | Mode | LM | RM | Effect |
|---|---|---|---|---|
| 256−3 | VSYNC | 63 | 0 | 3 lines blank; LM never reached, sync stays off |
| 256−2 | VSYNC | 6 | 63 | 2 lines; sync turns on at slot 6 and stays on |
| 256−1 | VSYNC | 63 | 32 | 1 line; sync turns off mid-line (2.5 lines of sync) |
| 256−19 | PIXEL | 6 | 63 | 19 lines with black palette, restoring colour burst |

  This leaves 287 lines for the picture, of which about 256 are visible.
- ep128emu: at the left margin of a VSYNC-mode line `vsyncStateChange(true)`
  fires; it ends at the right margin or at slot 0 of a line whose mode is not 0
  (`runOneSlot()`). Outside the sync window the renderer is `render_Blank`
  (black, not border). The VSYNC renderer still reads one byte per slot from
  LD1 onto the data bus.
- MAME blanks the whole VSYNC line and starts a new frame on entry into VSYNC
  mode (`do_line()`); Xemu uses VSYNC-mode lines to end its frame with
  thresholds `RASTER_NO_VSYNC_BEFORE` (300) and `RASTER_FORCE_VSYNC` (326)
  (`nick.c`). CLK: windows outside the margins are Blank, inside are Sync.

Source: Nick guide (VSYNC mode); emulator files above.

### 4.8 Invalid mode (VM = 6)

The guide just calls it "unused". ep128emu renders it with `render_Generic`,
behaving like a character mode whose glyph address is forced to FFFFh
(`nick.cpp`). MAME draws nothing but still applies margins/border. Real
hardware behaviour is otherwise undocumented — see Open questions.

## 5. Colours and palette

### 5.1 The colour byte

Every NICK colour (palette entries, border, 256-colour pixels) is an 8-bit
value with this bit layout (MSB → LSB):

| Bit | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|---|---|---|
| Signal | G0 | R0 | B0 | G1 | R1 | B1 | G2 | R2 |

R and G have 3 bits (R2/G2 most significant — i.e. bits 0 and 1), B has 2 bits
(B1 = bit 2). Guide: level = (4·x2 + 2·x1 + x0)/7 for R and G, (2·b1 + b0)/3
for B; output is analogue RGB plus PAL composite.

Implementations:
- MAME `initialize_palette()`: resistor-weighted DAC — R from bits 6/3/0 and G
  from 7/4/1 with 470 Ω/220 Ω/100 Ω, B from bits 5/2 with 220 Ω/82 Ω (bit 0/1/2
  being most significant via the 100 Ω / 82 Ω resistors) → slightly non-linear.
- CLK `mapped_colour`: linear, 3 bits → 4 bits by `(v<<1) + (v>>3)`, 2 bits →
  4 bits by `(v<<2)+v`.
- The guide's /7 and /3 formulas are linear.

*Recommendation:* linear scaling per the guide (R,G: v×255/7; B: v×255/3) is
the documented behaviour; MAME's resistor model is an alternative.

### 5.2 Palette entries 0–15 and FIXBIAS (port 80h)

- Entries 0–7 come from the current LPB (bytes 8–15), refreshed per line in
  ep128emu (§2.1).
- Entries 8–15 are `FIXBIAS × 8 + n` (n = 0..7), FIXBIAS being bits 0–4 of port
  80h: the high 5 bits of the colour byte come from FIXBIAS, the low 3 from the
  index. This yields 32 fixed groups of 8 colours, constant over the screen
  unless the program rewrites port 80h during the frame.
- Only 16-colour PIXEL/LPIXEL/character pixels and attribute nibbles can reach
  entries 8–15.

Sources: Nick guide (port 80h); ep128emu `writePort()` case 0 sets
`palette[8+k] = (fixbias<<3)|k`; MAME `get_color_index()`; CLK `write()`
case 0.

### 5.3 Border (port 81h)

Port 81h holds a full 8-bit colour byte shown outside the margins on non-VSYNC
lines (guide). CLK flushes pending border output on a write so a mid-line
border change appears at the correct position (`Nick::write()` case 1);
ep128emu applies it from the next border slot rendered (the `render_Border`
reads `borderColor` per slot).

## 6. Video RAM and NICK's address space

- NICK addresses **64K directly**: the four RAM segments **FCh, FDh, FEh, FFh**
  of the 4 MB Dave address space, at NICK addresses 0000h, 4000h, 8000h, C000h
  respectively, bypassing Dave's paging registers (B0h–B3h). It cannot see any
  other RAM (guide, "Video RAM"; ep128emu loads segments FCh–FFh as the video
  segments; CLK treats pages ≥ FCh as video, with a TODO about the 64K
  assumption).
- On a 128K machine the additional 64K (segments F8h–FBh) is ordinary,
  non-contended RAM (*inference* from "only the internal 64K" and the segment
  numbering).
- Any CPU memory access to a page that maps segment FCh–FFh is a video-RAM
  access and is subject to NICK contention (§8), regardless of which Z80 page
  (0–3) it is mapped into — ep128emu `readMemory()` etc. test
  `pageTable[addr >> 14] >= 0xFC`.

## 7. Video interrupt (VINT → Dave INT1)

### 7.1 Stated behaviour (guide)

- VINT set in an LPB pulls NICK's **VIRQ output low for the whole mode line**.
- VIRQ drives Dave's INT1 input. Dave is edge-triggered: the start of the low
  pulse latches an interrupt (if INT1 is enabled in Dave port B4h).
- Consecutive LPBs with VINT set give **one** interrupt; a VINT = 0 line is
  needed between them.
- The Dave latch must be cleared before the next interrupt; if interrupts are
  re-enabled before the VINT line ends, no new interrupt happens.
- The MB bit is described as causing an interrupt "at the start of this mode
  line".

### 7.2 What the emulators do — **they disagree about which end**

| Emulator | Signal passed to Dave | Dave edge | Interrupt happens |
|---|---|---|---|
| ep128emu | `irqStateChange(VINT bit)` at slot 0 of every line (`Nick::runOneSlot()`), forwarded unchanged as `dave.setInt1State()` (`Ep128VM::Nick_::irqStateChange`) | `Dave::setInt1State()` latches on the 1→0 transition ("on negative edge") | at **slot 0 of the first line after the VINT block** (end of the VINT mode line) |
| Xemu | `dave_int1(MB & 128)` at slot 0 (`nick_render_slot()`) | `dave_int1()` latches when the level drops from set to clear | **end** of the VINT block (same as ep128emu) |
| CLK | `interrupt_line_ = MB & 80h` at window 0 of a block's first line, effective at cycle 16 (`Nick.cpp`) | `advance_nick()` triggers on rising edge | **start** of the VINT block |
| MAME | VIRQ asserted/cleared per line from MB bit 7 (`do_line()`), to `dave_device::int1_w` | (in Dave device) | per Dave implementation |

ep128emu's `nick.hpp` comments say the irq flag is "true when IRQ is active
(low)", and Dave port B4h read bit 4 returns the current INT1 level in both
ep128emu and CLK. *Inference:* since ep128emu is the most hardware-validated
model, and Xemu independently agrees, the safest default is "the interrupt
latches when a VINT block ends", but because the guide's wording says "start",
this should be verified with a timing-sensitive program (e.g. a raster-split
demo). For EXOS's 50 Hz tick either choice works; the difference is the raster
position of the interrupt (exactly one block length).

### 7.3 Dave side (minimal, for the INT1 path)

ep128emu `Dave::writePort()` register 14h (port B4h): the written value is
XORed with 55h; bit 4 written as 1 enables INT1, and the INT1 latch is cleared
when bit 5 is written as 1 or when INT1 is disabled. Reads of B4h: bit 4 =
current INT1 level, bit 5 = INT1 latch. Xemu `dave_int1()` keeps the same bits
(level bit 16, latch bit 32). (Full Dave interrupt behaviour belongs in the
Dave notes.)

## 8. CPU access to video RAM: contention and wait states

### 8.1 Concept

NICK owns the 64K video RAM. Within every 16-NICK-cycle slot the RAM bandwidth
is split into two NICK fetches and one CPU access window; the Z80 is stopped
(its clock held) until its access lines up with the window. The same applies
to I/O to NICK's ports (80h–8Fh).

- CLK wiki/source: each slot = 5 cycles first VRAM read + 5 cycles second VRAM
  read + 6 cycles Z80 window; 6 NICK cycles ≈ 1.69 Z80 T-states. The Z80 clock
  can only be held in half-cycle steps, leaving ≈ 1.19 T-states of usable
  window; CLK assumes the final T-state of the bus cycle is stretched until it
  fits in a window (`Nick::get_time_until_z80_slot()` returns 0 if the current
  offset within the slot is < 3 cycles, otherwise the time until the next
  slot start). Its own comments call this a postulate.
  https://github.com/TomHarte/CLK/wiki/The-Enterprise, `Enterprise.cpp`
  (`perform_machine_cycle`).
- Note the order differs: the wiki text says reads then CPU window; CLK's code
  comment says the Z80 gets the *first* six cycles of each window. Either way
  the period is one slot.

### 8.2 ep128emu's model (`src/ep128vm.cpp`)

ep128emu interleaves CPU and NICK: per NICK slot it adds the CPU's share of
cycles (`cpuCyclesPerNickCycle` ≈ 4.4952 T-states at 4 MHz), runs Z80
instructions while the budget is positive, then runs `nick.runOneSlot()`
(`Ep128VM::run()`). I/O to NICK or Dave first catches NICK up
(`runDevices()` from `doIn()/doOut()`).

Video-RAM memory accesses do **not** use Dave's wait-state setting; instead:

- `videoMemoryWait()` (normal read/write): charge 2 T-states, compute the
  current phase within the NICK slot from the CPU cycle budget, add a
  phase-dependent wait = (phase + `videoMemoryWaitCycles`) converted to CPU
  time, rounded to **half T-state** granularity.
- `videoMemoryWait_M1()` (opcode fetch): charge 1.5 T-states, base term uses 5
  instead of 2.
- `videoMemoryWait_IO()` (NICK port I/O): gives back 1 T-state of the normal
  4-T I/O charge, then the same phase-dependent wait with its own latency.
- `videoMemoryWaitCycles*` = base CPU cycles converted to NICK time + a
  latency in picoseconds converted to NICK time; the latencies default from
  `setVideoFrequency()` = 5/16 of a NICK slot + 8271 ps (normal), −3866 ps
  (M1), +3473 ps (I/O) — i.e. ≈ 359 ns, 356 ns, 363 ns at the standard clock.

*Inference:* the net effect is that every video-RAM access ends aligned to the
next CPU window of the NICK slot cycle, costing between ~0 and ~1 slot
(≈ 0–4.5 T-states) extra depending on phase, plus a fixed component. The
latency constants were evidently tuned to match hardware measurements; an
emulator wanting identical timing should reproduce this arithmetic exactly
rather than the CLK postulate.

### 8.3 Non-video RAM and ROM: Dave port BFh wait states

| BFh bits 3–2 | ep128emu `setMemoryWaitTiming()` | CLK |
|---|---|---|
| 00 | wait on every access: M1 = 4 + w, other = 3 + w | `OnAllAccesses` |
| 01 | wait on M1 only: M1 = 4 + w, other = 3 | `OnM1` |
| 10, 11 | no wait: M1 = 4, other = 3 | `None` |

`w` (`waitCycleCnt`) = 1 at ≤ 5 MHz CPU, 2 above (ep128emu). CLK makes the
delay depend on BFh bit 1 instead: 1 T-state with bit 1 clear (8 MHz Dave),
2 with bit 1 set (12 MHz) (`dave_delay_ = 2 + (value & 2)` half-cycles),
inserted at the start of the bus cycle. Xemu: "memory wait states (non-VRAM
only!)" = 1 at 4 MHz (`dave.c`). ep128emu's constructor default is mode 1
(M1 only) but Dave reset writes 0 to BFh (mode 0, all accesses) in
`Dave::reset()`.

These waits apply to segments other than FCh–FFh; video RAM uses only the
NICK contention model (ep128emu `readMemory()` branches on the segment).

## 9. NICK I/O ports

The NICK chip decodes I/O addresses **80h–8Fh**; only the low two address bits
select a register, so 84h–8Fh mirror 80h–83h (guide: 80h–8Fh reserved, only
80h–83h used; ep128emu and CLK use `port & 3`; MAME maps 0x80–0x8F to its
4-register `vio_map`).

| Port | Name | Bits |
|---|---|---|
| 80h | FIXBIAS | 0–4 FIXBIAS (top 5 bits of palette 8–15); 5–6 external colour (EC0–EC3) priority; 7 drives output VC1 — set to disable the internal speaker |
| 81h | BORDER | 8-bit border colour |
| 82h | LPL | LPT base address A4–A11 |
| 83h | LPH | 0–3 LPT base A12–A15; 4–5 unused; 6 LPT clock enable (0 = inhibit); 7 reload control (0 = force reload) — §3.5 |

FIXBIAS bits 5–6 (from the guide) choose when the external colour inputs
EC0–EC3 (active with /EXTC low, never in border) replace the internal colour:
00 always; 01 only when the internal colour is in COL8–15; 10 as 01 or when the
external colour is in COL0–7 (EC3 low); 11 as 01 or when the external colour is
in COL0–3/COL8–11 (EC2 low). No emulator implements external colour (CLK:
"Ignored"; ep128emu: bit 7 speaker not implemented either).

**Reading** the ports: the guide says they are write-only and cannot be read
back. ep128emu `Nick::readPort()` and CLK `Nick::read()` both return the
**last byte NICK fetched from video RAM** (the floating data bus,
`dataBusState`/`last_read_`, FFh after reset). ep128emu keeps the written
values only for its debugger (`readPortDebug()`).

### 9.1 Floating data bus

ep128emu keeps the last byte read by NICK (`dataBusState`). In slots ≥ 54 (when
the right margin is beyond 54) no real fetch happens; `renderSlot_noData()`
renders the current mode as if both LD1 and LD2 pointed at the last bus byte
("in slot >= 54, repeat the last data byte from the bus"); character modes are
forced through the generic renderer with glyph address FFFFh. This is visible
on screen only with unusual margins, but it is also what NICK port reads return.

## 10. Line output format used by ep128emu (useful design reference)

ep128emu's NICK emits a compact per-line buffer (57 × 9 bytes max) of records:
a count/tag byte followed by data — 01h + one raw colour (256-colour pixel,
border, blank); 02h + two colours (16-colour); 03h + two colours + bitmap byte
(2-colour, expanded later); 04h + four colours (4-colour); larger tags for two
source bytes. The display back-end expands these to 16 pixels per slot
(`nick.cpp` renderers; `nick.hpp` `drawLine()` comment says 48 slots × 16 =
768 pixels, 96–432 bytes). *Inference for Klive:* a renderer that writes a
fixed 16 pixels per slot into a 912- (or 768-) pixel line buffer is simpler
and costs little; the important part is that the output decision is made per
slot.

## 11. Known quirks an accurate emulator must reproduce

1. **LPB re-read every line** (ep128emu): mid-block edits of mode byte,
   margins and palette in RAM take effect on the next scanline (§2.1). CLK
   disagrees (latches per block).
2. **Renderer latched at the left margin** (ep128emu): a mode change takes
   effect at the next left-margin slot; with left margin < 2 the previous
   line's value is compared (§3.3).
3. **Right margin ≥ 57 never matches**: display/sync continues into the next
   line — required for the guide's VSYNC recipe.
4. **LD1/LD2 advance in control slots when the display window covers them**
   (ep128emu), so the start address of subsequent data depends on margins.
5. **Floating data bus**: slot ≥ 54 output and NICK port reads (§9.1).
6. **Palette 8–15 change instantly** with port 80h writes; border with 81h —
   raster effects use these mid-line, so writes must be applied at slot
   granularity, synchronised with the CPU's position in the line.
7. **Forced LPT reload sequence** via 83h bits 6/7 (§3.5); power-on LPT
   address is random.
8. **Undefined combinations** (ALT bits in non-2-colour modes, attribute mode
   with more than 2 colours, VM 6) produce defined garbage in ep128emu's
   `render_Generic`; some demos may rely on them.
9. **VINT edge** (start vs end of block) differs between emulators (§7.2).
10. **Asynchronous clocks**: CPU-to-NICK phase drifts across lines; a model with
    an integer number of T-states per line will mistime contention and
    mid-line writes.

## 12. Minimal emulation algorithm (*inference*, synthesised from ep128emu)

Per NICK slot (≈ 4.4952 T-states):

1. If slot == right margin: display off, choose blank/border renderer, end
   vsync if active. If slot == left margin: display on, choose renderer from
   the latched mode/colour/ALT bits, start vsync if mode == VSYNC.
2. Slots 0–7: fetch LPB bytes (2 per slot) at `lptCurrent + 2·slot`; in slot 0
   update VINT → Dave INT1 level; slot 2: load LD1 if first line or VRES clear;
   slot 3: char-mode LD2++, and if first line load LD2 and the line counter.
3. Slots 8–53: render 16 NICK cycles of pixels via the current renderer
   (fetching via LD1/LD2, updating the data-bus latch), or border/blank.
4. Slot 54: floating-bus render if display on. Slot 55: emit the line.
5. Slot 56: decrement line counter; on block end (or pending 83h request) move
   LPT pointer (base if RELOAD/forced, else +16) when 83h bit 6 set; recompute
   flags; wrap to slot 0.

Between slots: run the Z80 for its share of time; CPU accesses to segments
FCh–FFh and NICK ports apply the contention wait (§8.2); port writes take
effect at the slot boundary they fall into.

## Open questions

1. **Exact NICK clock**: 14 237 536 Hz (912 cycles = 284 colour cycles, used by
   ep128emu and CLK) or 16/5 × subcarrier ≈ 14.1876 MHz? Is it a separate
   crystal or derived from the 4.433619 MHz crystal? A board photo/schematic
   would settle it.
2. **VINT edge**: does Dave latch at the start of a VINT mode line (guide,
   CLK) or at its end (ep128emu, Xemu)? Needs a raster-timed test.
3. **LPB fetch every line vs once per block** for mode/margins/palette
   (ep128emu vs CLK).
4. **Port 83h bits 6/7 exact semantics**: ep128emu's flag model vs CLK's
   "rising edge of bit 7" vs Xemu's immediate reset — which matches hardware
   when the bits are changed mid-line?
5. **Exact CPU contention window** within a slot (position and length), and
   whether ep128emu's tuned latencies (≈ 356–363 ns) reflect measurements.
6. **Invalid video mode 6** and the undefined ALT/colour-mode combinations on
   real hardware.
7. **Horizontal sync / colour-burst slot positions** on real hardware (CLK's
   windows 0–3 sync, 4–5 blank, 6–7 burst are its own model; ep128emu has
   none).
8. **Slot 7 and slots 54–56**: whether pixels can really be shown there when
   margins allow (ep128emu shows a placeholder at slot 7 and floating-bus data
   at 54).
9. **Default BFh value set by EXOS** and therefore the normal wait-state mode
   of a running system.
10. **External colour inputs** (FIXBIAS bits 5–6, EC0–EC3) — no emulator
    implements them; probably irrelevant unless an expansion uses them.
