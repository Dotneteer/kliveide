# Shared Z80 Back End — Refactoring Plan

**Goal.** Klive BASIC compiles to Z80/Z80N through a pipeline whose second half (MIR optimisation,
instruction selection, LIR peephole rules, emission, runtime linking, assembly, branch shaping,
CODEBANK placement, debug tables) is general compiler machinery that happens to live inside
`src/main/kbasic/`. Klive will get more languages (Pascal first). This plan moves that machinery
into **one shared back end** with a language-neutral input contract, so that every future
compiler is *a front end that produces MIR*, and **no compiler implements optimisation or Z80
code emission of its own**.

**Part B** (§11–§14) does the same for the **source-level debug support**: the debug model, stepping,
call stack, Variables panel, value decoding and watch expressions become language-independent, with
language specifics supplied as data by the producer or by a small per-language debug plugin.

**Status:** **implemented** (2026-10-25), on the decisions approved the same day (§9, §14). Both
parts are complete; §15 records how it was built and every place it differs from the text above.

**Scope.** A refactoring: Klive BASIC's observable behaviour — generated bytes, `'@emit-asm`
output, debug information, diagnostics and their codes — stays **identical** through every phase
(two planned exceptions: the `'@emit-ir` text in Phase 2, and runtime addresses after Phase 3's
runtime split, §1.1). Pascal itself is
**not** part of this plan; §8 lists what it will need from the back end so that the boundary drawn
here does not have to be redrawn.

## 1. Ground rules

1. **Byte-identical, phase by phase.** Phase 0 builds a snapshot of every corpus program's output at
   levels 0–3 on every target. Every later phase ends with that snapshot unchanged. A phase that
   needs to change generated code is wrong by construction: split it. **The one exception** is
   Phase 3's step that moves runtime routines between modules (D5): it moves code, so addresses
   change in programs that link those modules. It is its own commit, the snapshot is re-recorded once
   with the author's approval, and the program text (`'@emit-asm`) and debug statement tables must stay
   identical apart from addresses, while the whole corpus runs green on the harnesses at every level.
2. **One back end, enforced by a test.** A boundary test (Phase 0) fails when a back-end file imports
   anything from a language folder, and when a language folder imports a back-end internal it is
   not allowed to (§4.4) or does Z80 code generation of its own (imports `Z80Assembler`, writes Z80
   mnemonics, owns a peephole rule). The test starts with a baseline of today's violations, which
   may only shrink (the same mechanism as `build/style-mandate-baseline.json`), and is empty at the
   end of Phase 6.
3. **Direct imports, no wrappers** (AGENTS.md). Moved files are imported from their new path; the old
   file is deleted, never left as a re-export. There is no barrel `index.ts` for the back end
   either: §4.4 lists the files a front end may import.
4. **Provenance carries over.** The back end inherits Klive BASIC's provenance rule
   (`ZXBASIC_COMPILER_PLAN.md` §0.1): it was written from scratch and stays so. A new front end
   brings its own provenance rule; nothing from another compiler's back end is read for design.
5. **Docs move with the code.** The design notes `.docs/kbasic-mir.md`,
   `kbasic-lir-regalloc.md`, `kbasic-optimiser.md` and `kbasic-debug-builder.md` describe back-end
   machinery; each moves to a `.docs/z80-backend-*.md` name in the phase that moves its code, with
   the BASIC-specific parts (lowering of each BASIC construct, string ownership) staying in kbasic
   notes. `kbasic-string-ownership.md` stays a kbasic note.
6. **Tests move with the code, and gain a front-end-free form.** Back-end unit tests are rewritten to
   build MIR directly (Phase 1's `MirBuilder`), not by compiling BASIC, so they test the back end
   alone. The BASIC corpus remains the end-to-end guard.

## 2. What exists today (facts this plan builds on)

The compiler is ~18,400 lines in `src/main/kbasic/`. Its pipeline (`codegen.ts`,
`generateProgram`):

```
syntax/ (lexer, preprocessor, parser)  ->  semantics/ (binder)  ->  ir/lower.ts  ->  MIR
MIR -> opt/verify -> opt/mir-passes (unused routines, inlining, constant slots, folding)
    -> backend/select0 + select1 (level-0 stack machine, level-1+ tree tiling)  ->  LIR lines
    -> opt/pipeline (peephole rules, redundant loads)  ->  backend/emit (program text)
    -> runtime/runtime-linker (runtime modules in `.module core`)  ->  Z80Assembler
    -> opt/pipeline shapeBranches (jp -> jr) -> assemble again
    -> debug/builder + debug/source-level (classic and source-level tables)
```

### 3.1 The contract between a front end and the back end

A front end hands the back end exactly this:

1. **An `MModule`** (language-neutral after Phase 2): functions of blocks of typed instructions with
   statement ids; data items; statement table; the runtime labels it calls; per-function and
   per-global **debug descriptors** (§3.3).
2. **A runtime set**: the names of the runtime *packages* it links (`core` is implicit; `zx`
   platform; its own language package). Every package's modules declare, in their headers, the
   register contract of each export (§3.2).
3. **`BackendOptions`**: target, optimisation level and strategy, origin, headerless, heap size or
   address, memory/break checks, Z80N instructions, CODEBANK window/pages/depth, NEX core/stack/entry,
   build profile. Front ends translate their own option syntax (BASIC's header comments, Pascal's
   `{$...}` directives) into it.
4. **Hooks**: `isLibraryFile(fileIndex)`, and the source set for `#line`-mapped locations.

It gets back a `BackendResult`: assembler output (segments, NEX config, listing, symbols), the
emitted text and line table, both debug tables, the entry address, and a list of **structured
problems** (`{ kind: "bank-overflow", bank, contents }`, `{ kind: "inline-asm", sid, line, message }`,
`{ kind: "internal", reason }`, ...). The front end turns problems into its own diagnostics: Klive
BASIC keeps its codes (E455–E458, E503, E599) and i18n keys; a new language can use the back end's
default messages (`compiler.backend.*`) unchanged.

### 3.2 The runtime contract

Today the selector knows each runtime routine's registers from `RUNTIME_ARGS`. After Phase 3 each
module header declares them:

```
; @exports  PrintU8, PrintStr
; @abi      PrintU8(a)
; @abi      PrintStr(hl, a)
; @abi      Beep(stack, aedcb)
```

`scripts/…-runtime-index.cjs` turns these into the bundle, and the selector reads a
`RuntimeContract` (name -> argument registers, `stack` positions) built from the linked packages.
The register vocabulary (`a`, `hl`, `dehl`, `aedcb`, `stack`, `!addressFirst` variants) stays what
`RUNTIME_ARGS` uses today. Runtime packages:

| Package | Modules (today's names) | Who links it |
| --- | --- | --- |
| `core` | `program`, `errors`, `heap`, `arith16`, `arith32`, `fixed`, `float`, `rom`, `banking` | always (on demand per label, as now) |
| `zx` | `print`, `attributes`, `graphics`, `sound`, `tape`, `keyboard`, `random` | any Spectrum language |
| `kbasic` | `strings`, `arrays`, `data`, `usr` | Klive BASIC |

All modules keep linking into the single assembler module `core` with `core.<label>` names (decision
D4), so labels, link order (requires first, then name order — module names do not change), the
debugger's runtime ranges and Just My Code are untouched. Package boundaries are checked: a `core`
module may not `@requires` a `zx` or language module, a `zx` module not a language module. Today's
`@requires` lines break that in four places, which Phase 3 resolves (D5): `float` (core) requires
`print` and `strings` (for `PrintFloat`, `FStr` and `StrAlloc`); `keyboard` and `tape` (zx) require
`strings` (`StrAlloc`, `StrChr`, `StrLen`).

### 3.3 Debug descriptors

The debug builders stop reading BASIC symbols. Lowering attaches what the debugger needs, already in
the debugger's vocabulary (`@abstractions/SourceDebugInfo`):

```ts
type VariableDescriptor = {
  name: string;
  type: SourceValueType;           // already language-neutral in the abstractions
  typeLabel?: string;              // the type as the source spells it
  kind: "global" | "local" | "parameter" | "constant";
  storage: { label: string; offset?: number } | { frameOffset: number } | { constant: number | string };
  byRef?: boolean;
  array?: { elementType: SourceValueType; dimensions?: { lower: number; upper: number }[] };
  declaredAt: Span;
  bank?: number;
};
```

`MFunction.vars` and a new `MModule.globals` carry these; constants arrive already decoded (a
BASIC Float constant becomes a number in lowering, so the builder needs no float40). The builder
resolves `storage.label` through the assembler's symbols, so it no longer needs `globalName` (L11):
the mangled label is in the descriptor.

### 3.4 Types: representation in the back end, semantics in the language

Languages that share a name for a type rarely share its meaning. Pascal's `Integer` and C's `int`
are 16-bit like BASIC's `Integer`, but they differ in division and remainder (truncation and the sign
of the remainder; BASIC's `\`, C's `/` and `%`, Pascal's `div` and `mod`), in overflow (wrap, or a
range-check error with `{$Q+}`/`{$R+}`) and in shifts. Real-to-integer conversion rounds in one
language and truncates or floors in another. `Boolean` is 0/1 in one, 0/−1 (`TRUE = -1`) or "any
non-zero" in another, and its size varies. Floats come in different formats: the ROM's 5-byte format
(BASIC `Float`), Turbo Pascal's 6-byte `Real`, IEEE 32-bit `float` in z88dk's math libraries.
Strings are a heap handle with ownership (BASIC), an inline length-prefixed array with a capacity
(Pascal `ShortString`) or a NUL-terminated `char *` (C). Characters and character sets differ too.

So the back end does not try to own "the" `Integer`, `Float` or `String`. It works in two parts.

**1. MIR types are representations, and the set is open.** A representation is what the back end
needs to move, store, pass and return a value: its size, its register class, the registers it returns
in, and its alignment. The integer representations (`i8 u8 i16 u16 i32 u32`), `bool` (always 0 or 1 in a vreg, the back end's one canonical form) and `ptr` are
built in. Everything else is a **registered representation**: a record in a representation table that
names its size and register class (`r8`, `r16`, `r32`, `rflt`, or `mem`: passed by address, never in
registers), plus the runtime package that implements its operations. The table starts with today's
`fix` (16.16), `flt` (ROM float40) and `str` (Klive's owned heap handle). A Pascal front end adds
`real48` or `shortstr[N]` (a `mem` representation of N+1 bytes) through its runtime package. It does
not change the back end. The back end selects loads, stores, moves, argument passing and returns from
the table. Arithmetic on a registered representation is always an `rtcall` into its package, which is
how `flt` and `fix` work today.

**2. Operations whose meaning differs between languages say which meaning they want.** No MIR
operation has a hidden "BASIC default":

| Operation | Explicit attribute | Values |
| --- | --- | --- |
| `div`, `mod` (integers) | `rounding` | `trunc` (remainder takes the dividend's sign), `floor` (remainder takes the divisor's sign) |
| `add`, `sub`, `mul`, `neg`, `conv` narrowing | `overflow` | `wrap`, `check` (jumps to the language's overflow routine, named in the module header) |
| `conv` real -> integer | `toInt` | `trunc`, `floor`, `round-half-even`, `round-half-away` |
| `shr` (signed) | `shift` | `arith`, `logical` |
| `conv` between `bool` and a stored boolean | `truth` | the language's stored form (`0/1`, `0/-1`, any non-zero is true). Inside MIR a `bool` is always 0/1, so comparisons and logic need no attribute. Only the conversions at a variable's store and load do |
| `conv` integer -> boolean | — | always an explicit `ne 0` in lowering |

Klive BASIC's lowering writes today's behaviour as these explicit values, and the selector emits
exactly today's code for them, so the snapshot holds. A combination the selector cannot do yet (for
example `div` with `floor` on `i32`) is a verifier error that names the missing case. It is never
silently treated as another meaning. Each new semantics needs selector support and a MIR-level test.
It is added when a language needs it, not ahead of time.

**Constant folding follows the same rule.** The MIR folder (`opt/mir-passes.ts`) folds an operation
only for the attributes it implements, using the attribute's meaning (truncating or flooring
division, wrapping or checked overflow). A float representation folds only if its package registers
an exact folder: float40 has one (`numeric/float40.ts`, ROM-exact). A representation without a folder
is never folded, because folding a Pascal `real48` with JavaScript doubles would differ from the code
run on the machine.

**Strings are not a back-end type.** The back end never decides what a string is. `str` stays
Klive BASIC's registered representation, with ownership rules enforced by its lowering. A Pascal
`ShortString` is a `mem` representation plus block copies, and a C string is a `ptr`. Operations on any
of them are calls into the language's runtime package.

## 4. The boundary in detail

### 4.1 MIR changes (Phase 2)

| Today | After | Notes |
| --- | --- | --- |
| `kind: "main" \| "sub" \| "function" \| "data"` | `kind: "entry" \| "routine" \| "fragment"` | `fragment`: no frame, plain `ret` (BASIC's DATA code). Whether a routine returns a value is `returnType`, as it already is. |
| `gosub` terminator | `localcall { target, next, site }` | a `call` to a block of the same function, returning to `next`: BASIC's GOSUB; also usable for Pascal-style local labels if ever needed |
| `ongosub` terminator | `switch` with `call: true` | the selector already emits both from one case |
| `end { code }`, `raise { code }` | `exit { routine, value, width }` | a terminator that jumps (never returns) to a runtime routine with one value in A (`width: 8`) or BC (`width: 16`); lowering names `core.End` / `core.RaiseError`. Today `select1.ts` (`planRun`) tiles `end` but sends `raise` to level 0; `exit` keeps exactly that split (`width: 16` tiles, `width: 8` does not) so the code stays identical. Tiling both is a later, code-changing improvement, not part of this plan |
| `CallSite.kind` six BASIC names | `"routine" \| "localcall" \| "dispatch" \| "far" \| "runtime"` plus `returnsValue` | the debugger's `CallSiteDebugInfo.kind` keeps its values: the source-level builder maps (`routine`+`returnsValue` -> `function`, `localcall` -> `gosub`, ...). The abstractions are changed only if D6 says so. |
| `FrameVariable.symbol: VariableSymbol \| ArraySymbol` | `VariableDescriptor` (§3.3) | |
| `mtypeOf(KType)` in `mir.ts` | `kbasic/lower/types.ts` | |
| MIR types `i8 … u32, fix, flt, str, bool, ptr` | built-in `i8 … u32, bool, ptr`; `fix`, `flt`, `str` become entries in the representation table (§3.4) | the names in MIR text stay the same. The selector looks up size, register class and return registers in the table instead of switching on the name. `str` is documented as Klive BASIC's owned heap handle: the back end treats it as `r16` and never duplicates or drops one (the passes already respect this). D3 |
| `bin` / `neg` / `conv` with implicit BASIC meaning | explicit `rounding`, `overflow`, `toInt`, `shift`, `truth` attributes (§3.4) | Klive BASIC's lowering sets today's meaning explicitly; the verifier rejects a missing attribute and any combination the selector does not implement; the MIR folder folds by attribute |

The selector's output for every renamed construct is the same instruction sequence, so the
snapshot holds.

### 4.2 What stays in the language

Lexing, preprocessing, parsing, binding, constant folding of source constants, lowering (including
string ownership and every BASIC statement's runtime calls), name mangling, option syntax and its
settings keys, editor intel, inline-asm dialect conversion (`asm/zxbasm.ts`), the standard library,
the language's own runtime package, its diagnostics and i18n keys, breakpoint-line rules, and the
`IKliveCompiler` identity (`id`, `language`).

### 4.3 What the back end owns that the language must not redo

Everything from a verified `MModule` onward: MIR verification and passes, instruction selection,
LIR rules, emission, runtime linking and the runtime contract, assembler options for generated code,
two-pass branch shaping, CODEBANK planning and its checks, the NEX start stub, optimisation levels and
the debug-profile cap, and both debug tables.

### 4.4 Files a front end may import from the back end

`mir/mir.ts`, `mir/builder.ts`, `link/compile-module.ts`, `options.ts`, `problems.ts`,
`runtime/runtime-types.ts`, `numeric/float40.ts`, and from the shell `Z80LanguageCompiler.ts` and
`emit-files.ts`. The boundary test enforces this list; widening it is a reviewed change.

## 5. Phases

Each phase is one reviewable change (or a short series), ends with the snapshot identical, the
boundary baseline no larger, `npm run test:fast`, `npm run build:check`, and — when imports moved —
`npx electron-vite build --config build/electron.vite.config.ts`. The slow tier runs before Phase 6
closes.

### Phase 0 — Safety net

- **Output snapshot.** `test/z80-backend/snapshot/` compiles every program in
  `test/kbasic/corpus/` at levels 0, 1, 2 and 3, for each target the program declares (48K by
  default, plus the Next and codebank areas), and records per build: a hash of the emitted program
  text, of the assembled bytes per segment, of the source-level debug JSON and of the classic
  tables, plus the diagnostics list. Stored as one golden JSON; a mismatch prints which program,
  level and artefact changed. It runs in the fast e2e tier if it stays under 20 s, otherwise the
  e2e-kbasic tier with a 48K-only representative slice in the fast tier (per AGENTS.md). It needs no
  machine core — it compiles only — so it can sit in the unit tier if fast enough.
- **Boundary test.** `test/z80-backend/boundary.test.ts`: scans imports per §1.2, with
  `build/backend-boundary-baseline.json` listing today's violations (L1–L12 as file pairs).
- Exit: both tests green on an untouched tree; a deliberate one-byte change in `select0.ts` fails the
  snapshot.

### Phase 1 — Move the neutral machinery

- Create `src/main/z80-backend/` and move §2.1's files unchanged into `mir/`, `opt/`, `select/`,
  `emit/`, with `ir/mir.ts` moving to `mir/mir.ts` (still with its BASIC imports — the baseline
  records them until Phase 2). Update every consumer to the new paths; delete the old files.
- Add `mir/builder.ts` (`MirBuilder`: functions, blocks, vregs, statement ids) and `mir/print.ts`
  (the `'@emit-ir` printer, moved out of `emit-files.ts`).
- Move `test/kbasic/opt/*` and the selector/emitter tests to `test/z80-backend/`; rewrite the ones that
  compile BASIC only to reach MIR so they build MIR with `MirBuilder`. Keep a few BASIC-driven ones in
  `test/kbasic/codegen/` as integration tests.
- Move `.docs/kbasic-lir-regalloc.md` and `.docs/kbasic-optimiser.md` to `z80-backend-*` names.
- Exit: snapshot identical; boundary baseline unchanged or smaller.

### Phase 2 — A language-neutral MIR

- Apply §4.1: function kinds, `localcall`, dispatching `switch`, `exit`, neutral `CallSite`,
  `VariableDescriptor`s on functions and on `MModule.globals`, `mtypeOf` to `kbasic/lower/types.ts`.
- Types (§3.4): the representation table (`fix`, `flt`, `str` as its first entries) replaces the
  selector's and the passes' switches on type names. The operation attributes (`rounding`,
  `overflow`, `toInt`, `shift`, `truth`) are added to MIR. Klive BASIC's lowering sets each one to
  today's meaning, and the verifier rejects missing or unimplemented ones. The MIR folder folds by
  attribute. New MIR-level tests cover every implemented attribute value, through `MirBuilder`.
- Move `semantics/float40.ts` to `z80-backend/numeric/float40.ts`; update the binder, lowering, the
  renderer's value decoder and their tests.
- Split `.docs/kbasic-mir.md`: the IR itself becomes `.docs/z80-backend-mir.md`; §8 (lowering of
  every BASIC construct) stays as `.docs/kbasic-lowering.md`.
- The `'@emit-ir` text shows the new names (`localcall` for `gosub`, ...): the only user-visible change
  in this plan. It is an `internal`-level note unless the author wants it in the CHANGELOG (D7).
- Exit: no back-end file imports `kbasic/`; snapshot identical (the IR-text artefact is excluded from
  the snapshot from this phase, or re-recorded once with the author's approval).

### Phase 3 — The runtime contract and packages

- Add `@abi` header lines to every runtime module (§3.2), generated once from `RUNTIME_ARGS` by a
  throw-away script and then checked by hand; teach the index script to read them; the selector takes a
  `RuntimeContract` and `RUNTIME_ARGS` is deleted. A test checks every `rtcall` name lowering can
  produce has a contract entry (today: a missing entry is a `CodegenError` at build time).
- Split `src/main/kbasic/runtime/` into `z80-backend/runtime/core/`, `z80-backend/runtime/zx/` and
  `kbasic/runtime/` (§3.2) and the bundle into one per package; the BASIC stdlib leaves the runtime
  bundle and gets its own (`kbasic/stdlib/`), since it is BASIC source, not runtime.
- `resolveRuntimeModules` takes the package list; lowering's `RUNTIME_EXPORTS` check reads the same
  contract.
- Move the runtime tests (`test/kbasic/runtime/`) beside their package.
- Rename `npm run kbasic:runtime` to a back-end name and keep `kbasic:runtime` as an alias for one
  release, or update every reference (AGENTS.md, READMEs) — D8.
- Resolve the four cross-package dependencies (D5) in a separate, last commit of the phase: the
  only step of this plan that changes bytes (§1.1's exception).
- Exit: snapshot identical before the D5 commit (link order unchanged because module names are);
  after it, re-recorded once as §1.1 describes; the package-dependency check passes.

### Phase 4 — The back-end driver

- Extract `link/compile-module.ts` from `codegen.ts`: verify, optimise, select, rules, plan banks,
  emit, link, assemble, shape branches, check the window, build debug tables. It takes
  `MModule + runtime packages + BackendOptions + hooks` (§3.1) and returns `BackendResult` with

## 8. What Pascal will need later (recorded, not built here)

So that this boundary need not move again, the MIR is checked against these, all of which are
**additive** (new instructions or fields) rather than changes to what Phase 2 defines:

- **Nested procedures**: a static link (a hidden first parameter, or a display) and `frame` slots
  addressed through an outer frame — a new `Slot` kind `{ kind: "outer"; depth; offset }`.
- **Aggregates by value** (records, arrays, ShortStrings, sets): a block-copy instruction
  (`copy dst src size`, selected as `ldir`) and frame slots larger than 5 bytes.
- **Value strings** (length-prefixed, fixed capacity) rather than BASIC's owned heap handles: a
  registered `mem` representation `shortstr[N]` and a Pascal runtime package with its own string
  routines; MIR `str` stays BASIC's (D3, §3.4).
- **Its own numeric meanings**: `div`/`mod` with Pascal's rounding, `{$Q+}`/`{$R+}` checked overflow,
  `Trunc`/`Round` conversions, and possibly a 6-byte `Real`. All of these are operation attributes and
  registered representations (§3.4), each added to the selector with tests when Pascal arrives.
- **Sets**: bit operations over byte blocks — runtime routines first, MIR operations if profiling
  shows a need.
- **`case` statements**: the existing `switch` terminator, with ranges lowered to comparisons.
- **Typed files / I/O**: language runtime over the `zx` package's `tape`/`print`.
- **Watch expressions and value display in the debugger**: per-language (§10).

# Part B — Language-independent debug support

**Goal.** The core of source-level debugging — the debug model, stepping, the frame locator, the call
stack, the Variables panel, value decoding and watch evaluation — knows **machine and ABI facts
only**: statements, callables, activations, frames, call sites, value *representations*, memory
locations, banks. Everything that belongs to a language (type names, how a local subroutine is
named, error report texts, watch-expression syntax and built-ins) comes either **as data from the
producer** or from a small **language debug plugin**. A new language then gets the whole debugger by
producing the model, and at most writes a plugin; it never edits the core.

Part B is independent of Part A's phases except where noted (B3 uses Part A's descriptors), and
can be done before, after or between them.

## 12. Target: three layers and a plugin

```
Producers (back end, Boriel adapter, z88dk adapter)
   |  fill the neutral model (data: names, type labels, layouts, report tables)
   v
1. Debug model        @abstractions/SourceDebugInfo + CompilerInfo   JSON, versioned, no language words
2. Debug engine       src/emu/machines/SourceStepDecision.ts, the stop tracker, MachineController's
                      source part                                     machine-side, reads the model only
3. Presentation core  src/renderer/appIde/debugger/source/*, call stack, stop location, routine map
                      value decoding by representation, watch evaluation over a neutral AST
   ^
   |  asks, by `language`
Language debug plugins   src/renderer/appIde/debugger/languages/<lang>.ts
                         watch parser + built-ins, local-call label, literal formatting
```

Rules, enforced by a boundary test like Part A's (`test/debugger/debug-boundary.test.ts`): layers
1–3 import nothing from `src/main/kbasic/`, `boriel-integration/` or `z88dk-integration/`, and contain
no language keyword literal (`GOSUB`, `SUB`, `FUNCTION`, `BASIC` in code, not comments); plugins are
imported only by the plugin registry.

### 12.1 The model (layer 1)

| Today | After | Notes |
| --- | --- | --- |
| `CallSiteDebugInfo.kind: sub / function / gosub / on-gosub / far` | `kind: "routine" \| "local" \| "far"`, plus `dispatch?: true` and `returnsValue?: true` | `local`: the callee runs in the caller's activation and frame (BASIC's GOSUB; any language's local subroutine). `dispatch`: reached through a table (ON ... GOSUB). `routine` with `calleeIndex` covers SUB, FUNCTION, C function, Pascal procedure |
| `SourceActivationInfo.kind: main / routine / gosub` | `"entry" \| "routine" \| "local"` | |
| `SourceStopInfo.returnedFromGosub` | `returnedFromLocal` | |
| `SourceValueType` (BASIC names + `char`, `pointer`), a closed enum | a **representation id** from an open **decoder registry**: built-ins `i8 u8 i16 u16 i32 u32 ptr16 char8`, `bool` with a declared truth convention (`bool8/01`, `bool8/ff`, `bool8/nz`), `fix16.16`, `float40`, and string representations `str.heap` (pointer to a length-prefixed heap block: Klive/Boriel), `str.short:N` (inline length byte, capacity N: Pascal), `str.c` (NUL-terminated: C) | the producer always gives `typeLabel` (`Integer`, `unsigned int`, `Longint`), so the core never names a type itself. A representation the registry does not know (a future `real48`, an IEEE `float32`) is shown as raw bytes in hex with its `typeLabel` until a decoder is registered. Decoders are registered by the core or by a language plugin (§12.4), never hard-coded in the panel |
| `array: { elementType, dimensions? }` read through the runtime descriptor | `array: { element, layout: "descriptor" \| "inline", dimensions? }` | `descriptor`: today's Klive/Boriel layout (ABI §2.3); `inline`: contiguous at `location`, row-major, static bounds |
| `CallableFrameInfo.returnType` (registers inferred) | `returns: { type, in: "a" \| "hl" \| "dehl" \| "aedcb" \| "hl-ptr" }` | the producer states the registers; the decoder no longer knows an ABI |
| `errorEntry` + the ROM's report table in the engine | `errorStop: { entry, code: { register: "a" } \| { address }, reports: "zx-rom" \| string[] }` | `zx-rom` names the Spectrum ROM table, which moves to a platform file (`src/common/zx/rom-reports.ts`), not a BASIC one |
| `codebank.shadowStackKind?: "zxbc"`, `bankMask` | `codebank.shadowStack: { recordSize, grows: "up" \| "down", bankOffset, returnOffset, bankMask?, stride }` | both of today's layouts become data; a new far-call runtime needs no engine change |
| `CallableFrameInfo.convention: frame / entrypoint / fastcall` | unchanged values, `fastcall` documented as "frameless" | ABI words, already neutral in meaning |
| `language?: string` | required for new producers; the plugin key | all three producers already set it |
| `labels` ("GOSUB rows name their subroutine by them") | unchanged, documented as "named code addresses" | |

**Compatibility.** The sidecar format goes to version 2. A reader (`source-debug-sidecar.ts`) upgrades
version 1 in memory with a single mapping function (`sub`/`function` -> `routine` + `returnsValue`,
`gosub` -> `local`, `on-gosub` -> `local` + `dispatch`, BASIC type names -> representations + `typeLabel`,
`shadowStackKind: "zxbc"` -> its layout, `errorEntry` -> `errorStop` with `zx-rom`), so NEX files built
by older Klive versions keep debugging. The same function is the producers' migration aid: each
producer is switched to the new vocabulary in its own step, with the upgrade covering the others
meanwhile.

### 12.2 The engine (layer 2)

`locateActivations`, the stop tracker and `getSourceStopInfo` use only the neutral kinds;
`basicErrorReport` leaves `SourceStepDecision.ts` for the platform report table, chosen by
`errorStop.reports`; the shadow-stack reader takes its layout from the model. No behaviour changes:
the existing stepping, call-stack and error-stop tests for all three producers are the guard.

### 12.3 The presentation core (layer 3)

- `value-decoder.ts` becomes a registry of decoders keyed by representation id. Each decoder knows
  only bytes: its size, how to turn bytes into a neutral value (`{ number }`, `{ text }`, `{ bytes }`)
  and back for editing. How a value is *shown* (numeric format, character set for text, how a boolean
  is written: `True`/`TRUE`/`1`) is the language plugin's `formatValue`. The default is neutral.
  It takes `float40` from Part A's
  `z80-backend/numeric/float40.ts` (or, if Part B runs first, from a neutral `src/common/zx/float40.ts`
  that Part A then uses), reads result registers from `returns.in`, shows `typeLabel`, and reads strings
  by their representation.
- `variables-model.ts` reads arrays by `layout`.
- The call stack and the stop location ask the plugin for a local activation's label
  (`GOSUB 100` for BASIC); the default is a translated "local routine" text through `t()`.
- Watch evaluation runs over a **neutral watch AST** (literals, variable references, array indexing,
  unary/binary operators, built-in calls). As in the MIR (§3.4), no operator has a default meaning.
  The plugin's parser produces explicit nodes: integer division with `trunc` or `floor`, the result
  width and whether it wraps (C's 16-bit `int` arithmetic wraps; BASIC's watches compute in full
  precision), comparison results in the language's truth convention, string concatenation in the
  language's string semantics. The evaluator implements each meaning once, for every language.
- State is `sourceWatches` (actions, reducer, project file), with the project loader reading
  `debugger.basicWatches` from old project files. Watches stay one list per project; per-language
  lists are not needed while a project builds one language.
- The routine map takes the compiler's name and routine-source label from the compilation (a
  `compilerName` on `DebuggableOutput`, set by each compiler), fixing B-L13.

### 12.4 Language debug plugins

```ts
type DebugLanguageSupport = {
  id: string;                                   // SourceLevelDebugInfo.language
  /** Parses a watch into the neutral AST; errors carry translated messages. */
  parseWatch(text: string): { ast: WatchExpr } | { error: string };
  /** Built-ins the parser may produce calls to, evaluated over neutral values. */
  builtins: Record<string, WatchBuiltin>;
  /** The call stack's label for a local activation, given the nearest label. */
  localActivationLabel?(label: string | undefined): string;
  /** A string value as a literal of the language ("..." with BASIC's doubled quotes, C escapes). */
  formatString?(value: string): string;
  /** Whether variable names match case-insensitively (BASIC: no; Pascal: yes). */
  caseInsensitiveNames?: boolean;
  /** How a decoded value is written in this language (numbers, booleans, characters, the charset). */
  formatValue?(value: NeutralValue, representation: string, typeLabel?: string): string;
  /** Decoders for representations only this language uses (Pascal's `real48`, say). */
  decoders?: Record<string, ValueDecoder>;
};
```

- `basic` plugin: today's `watch-expression.ts` parsing (the kbasic lexer/parser, whose import moves
  here) and its built-ins; `GOSUB` labels. Boriel BASIC uses the same plugin (`language: "basic"`).
- `c` plugin: a small C-expression parser (identifiers, literals, `+ - * / % & | ^ << >> == != < <= > >=
  && || !`, `[]`, unary `*` and `&` on pointers), so z88dk programs get watch expressions for the first
  time; written from scratch.
- No plugin for a language: the Variables panel, call stack and stepping still work; the watch box
  says watches are not available for that language.
- The registry (`debugger/languages/registry.ts`) is the only file importing plugins.

## 15. As built (2026-10-25)

**Order.** Part A's Phase 0 snapshot and Part B's B0 goldens came first, together. B1-B5 followed in
one go, because the model's new value types forced the presentation core (B4) and the plugins (B5) at
once. Then Part A's Phases 1-6, with Phase 5 (debug builders) folded into Phase 2, because the neutral
MIR's variable descriptors needed the builders changed with them.

**Byte-identical, with two recorded exceptions.** Every phase kept `test/z80-backend/snapshot/` (192
corpus programs × levels 0-3: program text, bytes, both debug tables, diagnostics) identical, except:

1. **D5** (Phase 3): `StrAlloc`, `StrLen`, `StrChr` moved into the new core module `strcore`, and
   `PrintFloat` into a new zx module **`printfloat`**, *not* into `print` as D5 said: in `print`,
   every program that prints would have linked the float module. The program text stayed identical
   everywhere; the runtime after it moved for 312 of 768 builds; the corpus ran green at every level.
2. **The DATA dispatch** (Phase 6): the three pieces of Z80 text Klive BASIC's lowering still wrote
   became back-end MIR operations — `jumpvia` (READ's jump to the next DATA item), `param.reload` and
   `result.capture` (zxbc's FASTCALL and asm-FUNCTION conventions). `jumpvia` is a terminator, so the
   dead `ret` the old asm left after `jp (hl)` is gone: the 10 READ/RESTORE programs are one byte
   shorter, ran green at every level; the other two operations are byte-identical. This was not in
   the plan; it closes the last place a language emitted Z80 itself.

**Types and meanings (§3.4).** As specified, with these specifics:
- BASIC's `MOD` is neither truncating nor flooring: it is the remainder of the magnitudes (`-100 MOD
  3` is 1, `arith16.kz80.asm`). `rounding` therefore has a third value, `magnitude`. The BASIC
  debugger plugin used to evaluate `MOD` in watches as a truncating remainder; it now uses
  `magnitude`, so watches agree with the compiled program (a fix).
- Klive BASIC's other meanings: integer division `trunc`, arithmetic and narrowing `wrap`, reals to
  integers `floor` (then wrap), signed `SHR` `arith`, Boolean stored `01`. Implemented meanings are
  exactly these; the verifier (S3, every level) names any other.
- Representations are a table in `mir/representations.ts` (size, signedness, register class, result
  registers, debug representation, runtime package). It is not extensible at run time: a new
  representation is a new entry plus selector support, as §3.4 says it may need.
- `truth` sits only on `bool` conversions (a `bool` in a vreg is always 0 or 1), not on comparisons.

**Runtime (§3.2).** Packages `core` (10 modules), `zx` (8) and `kbasic` (4); one generated file per
package and one for Klive BASIC's standard library, by `scripts/runtime-index.cjs` (`npm run
runtime:bundle`, D8), which also checks the package rule and the `@abi` lines. The runtime tests stay

**Debug model (§12).** As specified, with these specifics: the boolean representations are `bool`

numbers and do not wrap at the width of `int`; the ZX Spectrum ROM's report table lives in
`src/common/spectrum/rom-reports.ts`; the NEX sidecar keeps its file suffix `.kbasic-debug.json`. The
profiler's routine table header changed with the B-L13 fix: "Routines from the source program's
