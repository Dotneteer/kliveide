# Guides Overhaul Plan

Status: **accepted** (2026-10-24; decisions G1–G5 accepted as proposed, §8). Follows [DOCS_SITE_MODERNIZATION_PLAN.md](DOCS_SITE_MODERNIZATION_PLAN.md),
whose Phase 1 moved the old `working-with-ide/` and `howto/` pages into `docs/content/en/guides/`
but did not review or rewrite them. Its §2.2 grouping was only half applied (no *Editing*, no
*Customizing Klive*, no Klive BASIC or Boriel BASIC page, no Call Stack page, nothing on the
Next registers, SD card, NEX files or the sprite and palette editors). That plan's ground rules
R3 (no text in pixels), D4 (dark-theme screenshots only) and its illustrations pipeline (§5) apply
here unchanged.

## 0. Goals

1. **Every guide matches the app as it is now.** The UI was redesigned in Sept 2026 (#1337–#1342).
   No page shows a screenshot taken before that, and no page describes a control, label or default
   that has changed.
2. **Guides are task-oriented.** A page opens with what the reader will get done, then the steps,
   then the details. Long reference tables move to Reference or to the end of the page.
3. **A structure that follows the reader's journey**: pick a machine, load something, write a
   program, build it, debug it, then go deeper (Next hardware, analysis, testing, customizing).
4. **Screenshots where they add value, and only there.** Generated by `scripts/doc-shots/`
   recipes, so they can be re-captured after the next UI change instead of rotting.
5. **Every feature that ships has a guide** (or a deliberate decision that the Reference covers it).

- **Next breakpoints and NEX material move to the Next group.** Next users look there, and it
  shrinks breakpoints by 300 lines.
- **Shortcuts and syntax colours go to Customizing, not Editing.** Both are about changing
  defaults.

## 3. Page standard

Every rewritten or new page follows this shape. Existing good pages are brought to it only
where cheap.

1. **Front matter `description`**: one real sentence saying what the reader can do. It is shown
   in search and on the overview, so never cut it off at a colon.
2. **Lead (2–3 sentences)**: what this is for, and when you'd use it.
3. **Applies to** line when the feature is machine-specific: e.g. "*ZX Spectrum 128K, +2A/+3,
   Pentagon, Scorpion*".
4. **Task sections first**: numbered steps (Nextra `<Steps>`) for anything with an order. Name
   controls by their current English label (look it up in `src/common/i18n/locales/en/`) and give
   the menu path (`Machine › Disks › Insert Disk`), the command, and the shortcut on both platforms.
5. **Reference details after**: tables, options, edge cases.
6. **Related**: 2–5 links, including the Reference page and the Under the Hood article when one
   exists. Don't restate "how it works" when Under the Hood covers it.
7. Links are **absolute** (`/en/guides/...`) so the link checker sees them (§6).
8. No colour names for UI state ("the red dot"). Colours are theme tokens now and change with the
   accent. Name the state instead ("an unresolved breakpoint").

## 4. Screenshot policy

### When a screenshot earns its place
- **Orientation**: the first view of a panel, dialog or editor the reader has not seen
  (Settings dialog, Copper view, NEX viewer, Call Stack + Variables while paused).
- **State that is hard to describe**: a paused debug session with the highlighted statement, the
  heat map over memory, the media strip with a cartridge inserted, a tape viewer with blocks.
- **Results**: what success looks like (a program running, an export dialog filled in correctly).

### When it does not
Text, a table or a code block is better, and stays correct through restyles, for:
- single icons and glyph tables (breakpoint types, the four build icons)
- key close-ups (the five single-key crops on the keyboard page)
- tooltips
- before/after register values (TSP)
- command output
- a menu that a menu path already names
- settings pages beyond one overview shot

### Rules
- **Generated, never hand-captured.** One recipe per page (or a shared recipe per group) in
  `scripts/doc-shots/recipes/`, with the seeded preset: dark theme, fixed accent, 1280×820 window
  at 2x, fixed fonts.
- **Element-scoped crops** (`locator.screenshot()`), not whole windows, unless the point *is* the
  whole window (the emulator window page, the IDE tour).
- **WebP**, rendered with `<Shot>` (figure number, caption, HTML `markers` for numbered callouts,
  R3). Every `<ClickableImage>` in the Guides (62 today) is replaced as its page is rewritten.
- **Path convention**: `docs/public/images/en/guides/<group>/<page>/<name>.webp`. `<Shot>`
  resolves `images/<lang>/<src>`, so this keeps Guides ready for translation later without any
  change.
- **Budget**: typically 1–4 shots per page, within `doc:check:weight`'s 1.5 MB per page.
- **Recipes double as UI checks.** A recipe that cannot reach a state is a bug report about the
  page or the app.

## 6. Tooling changes

1. **Check relative links.** Remove the `!raw.startsWith("/")` skip in
   `scripts/check-docs-links.cjs:75`. Resolve relative hrefs against the page URL (the site uses
   `trailingSlash: true`) and fail on the 21 broken ones until they are fixed. That is how this
   class of error stays fixed.
2. **No pre-redesign images.** Add a `doc:check` rule that fails when a Guides page references
   `images/getting-started/`, `images/howto/` or the pre-2026-09 `working-with-ide/` files (an
   explicit list). The list shrinks to zero during Phase 3, and then the old files are deleted.
3. **Asset golden.** `.plans/docs-assets.golden.txt` changes with every published or deleted
   image. Update it in the same change as the page.
4. **Freshness check.** Before each release, re-run all Guides recipes into `.doc-shots/` and
   review the diff. This is the DOCS_SITE_MODERNIZATION_PLAN §5.6 idea; it is cheap once every
   Guides image has a recipe.
