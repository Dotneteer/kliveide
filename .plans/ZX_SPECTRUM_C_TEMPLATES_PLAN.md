# ZX Spectrum family C (z88dk) templates — verification plan

Status: ✅ **done** (2026-10-22): T0–T6. T7 (machine-flavoured templates) is optional and not started. Builds on `.plans/Z88DK_INTEGRATION_PLAN.md` (implemented, all
phases Z0–Z7), whose rules carry over unchanged: Klive runs `zcc` and never copies z88dk; test
fixtures are zcc output, committed, regenerated by `npm run z88dk:fixtures`, never hand-edited; CI
never runs zcc; every user-facing text goes through `t()`; the changeset comes with the commit that
completes this plan.

Goal: every ZX Spectrum family machine and model Klive emulates offers a `z88-dk` project template,
and **each template is proven** — by committed tests on the real cores and by a local IDE check — to
**compile, run, and debug** (breakpoint on a C line, call stack, locals, globals) and to **export** its
native format.

---

## 1. Where things stand (surveyed 2026-10-22)

The C integration itself is complete: `Z88dkCompiler`, the machine → target table
(`src/main/z88dk-integration/z88dk-targets.ts`), the map parser, the C language provider, the
source-level debug adapter, export through appmake, and the setup dialog.

Templates are copied from `src/public/project-templates/<machineId>/<template>/`; a machine's
models share its templates (`getTemplateDirs` in `src/main/RendererToMainProcessor.ts`).

| Machine (models) | zcc target | `z88-dk` template | Template proven by a test? |
|---|---|---|---|
| `sp48` (48K PAL, NTSC) | `+zx` | yes | IDE check only: `run`, `debug`, `export` (`scripts/z88dk-ide-check.cjs`) |
| `sp48` (16K) | refused (org `$8000`) | listed, build refuses clearly | — (no action, see §5) |
| `sp128` (128K, **Pentagon 128**) | `+zx`, injected in 48 BASIC | yes | no |
| `spp3e` (+2A/+3/+2E/+3E) | `+zx -subtype=plus3`, injected in 48 BASIC | yes | no |
| `timex` (TC2048) | `+zx` | yes (shared) | no |
| `timex` (TC2068/TS2068) | `+ts2068` | yes (shared) | no |
| `scorpion` | `+zx`, injected in 48 BASIC | **missing** | — |
| `zxnext` | `+zxn -subtype=nex -clib=classic`, loads the `.nex` | yes | no |

What the committed core tests prove today (`test/z88dk/*.core.test.ts`) uses the **fixtures**
(`test/z88dk/fixtures/zx-hello`, `zx-banked`, `zxn-hello`, …), whose sources are *not* the template
sources:

- the `+zx` image returns to BASIC on the 48K, and runs through the 48 BASIC injection on the 128K
  and +3 (not on the Pentagon, Scorpion or either Timex);
- the source-level debugger stops, steps and shows the call stack, locals and globals — on `+zx`
  only. The Next's map (1.2 MB) is not committed, so no Next debugging test exists.

A trial compile of the five shipped Spectrum templates (`zcc <target> -debug -m -create-app -lndos`)
succeeded for every target on the local **v2.3** install, which is *outside* the supported range
(v2.4+, decision C3). It shows nothing is obviously broken; it proves nothing about v2.4.

### The gaps this plan closes

| # | Gap |
|---|---|
| G1 | No test builds the **shipped template sources**; a template can drift or break unnoticed. |
| G2 | Run is unproven on the Pentagon, Scorpion, TC2048, TS2068 and Next for template-shaped code. |
| G3 | Debugging is proven only on the 48K (`+zx`); not on the 128K family's 48 BASIC route, `+ts2068`, or `+zxn`. |
| G4 | The Scorpion has no `z88-dk` template although its target is supported. |
| G5 | The IDE check exercises templates only for the 48K and the ZX81. |
| G6 | Docs list the machines with a template, without the Scorpion and Pentagon. |

## 2. Decisions (need the author's OK)

| # | Proposal |
|---|---|
| **T-D1** | **One program for every Spectrum template** (today's `main.c`: `counter`, `square`, `printf`), kept identical except where a target's library lacks a call (the Next's template already drops `zx_cls`/`zx_border`). The debugging walkthrough in the docs is then the same everywhere. Machine-flavoured demos (AY on the 128K, Timex hi-res, Next sprites) are an optional phase (§3, T7), not a requirement. |
| **T-D2** | **Fixtures are compiled from the template files themselves.** `scripts/z88dk-fixtures.cjs` gains `tpl-<machine>[-<model>]` cases whose source is read from `src/public/project-templates/…/code/main.c`, and a unit test fails when a committed fixture's `main.c` differs from its template (G1). |
| **T-D3** | **Template maps are committed gzipped** (`"map": "gzip"` → `program.map.gz`), the Next's included. *Changed in T1 from "a trimmed map"*: gzip keeps zcc's output whole, so nothing the debug adapter reads can be dropped by a filter, and it is small (the Next's v2.4 map: 70 KB gzipped; all six template fixtures 460 KB). |
| **T-D4** | **Fast/slow split** (`build/e2e-tests.ts`): one representative per route stays in the fast `e2e-cores` tier (48K inject, 128K via 48 BASIC, Next `.nex`); the per-model sweep (Pentagon, +2A/+3E variants, Scorpion, TC2048, TS2068) goes to `e2e-slow`. |
| **T-D5** | **TS2068 tests skip without its ROM** (`hasTimexRom("ts2068")`, `KLIVE_TS2068_ROM`), as the Timex harness already does, and say so in the skip message. |

## 3. Phases (each is one reviewable step)

### T0 — Toolchain (prerequisite, needs the author)

- Install z88dk **v2.4** through Klive's own *Z88DK Integration* dialog (Online → v2.4 → *Download
  and install*, default `~/KliveTools/z88dk/v2.4`), or point `Z88DK_ROOT` at an existing v2.4.
  `~/z88dk` on this Mac is v2.3 (build 22110), which the fixture script refuses.
- Done when `Z88DK_ROOT=<v2.4> npm run z88dk:fixtures` regenerates the current fixtures with **no
  diff** (proves the environment matches the one that made them).
- **As built (2026-10-22):** v2.4 (build 23854) at `~/KliveTools/z88dk/v2.4`, installed by the dialog.
  The regeneration matched except two places where zcc/appmake vary on every build, both left at
  the committed version: the order of two `zx-banked` map lines that share one name after the
  temp-name normalisation, and the 4-byte card ID appmake randomises in the Z88 card's header
  (`z88-app/program.{63,ap0,epr}`). Re-generating fixtures will show these two diffs every time.

### T3 — Run on the real cores, every route and model (G2)

`test/z88dk/z88dk-templates-run.core.test.ts`, listed in `build/e2e-tests.ts` (T-D4). Each case
delivers the fixture the way `Z88dkCompiler`'s output tells Run to, then asserts the template's
observable result: `counter` reaches 6 (the loop runs 1..5), the first character row holds ink
(z88dk's own font), and control is back in BASIC (PC in the ROM's main loop / the editor waits).

| Case | Harness | Route |
|---|---|---|
| 48K | `createSp48Session` | inject at `CRT_ORG_CODE`, subroutine |
| 128K, **Pentagon**, Scorpion | `createSp128Session("sp128" \| "pentagon" \| "scorpion")` | `getCodeInjectionFlow("sp48")` |
| +2A, +3, +3E (one fast, the rest slow) | `createSp128Session(<P3ModelId>)` | `getCodeInjectionFlow("sp48")` |
| TC2048 | `createTimexSession("tc2048")` | inject, `+zx` image |
| TS2068 | `createTimexSession("ts2068")`, skipped without ROM (T-D5) | inject, `+ts2068` image at `$9C40` |
| Next | `test/harness/zxnext` | load the `.nex` as Run does (`prebuiltNex` path) |

- **Verify, don't assume**: the Pentagon's ROM must offer the 48 BASIC flow the inject uses, and
  the TS2068's injection flow must exist. Where a harness lacks a capability, add a session method
  (harness README, "Adding a method"); never reach into `session.machine`.
- A failure here is a product bug to fix in `z88dk-targets.ts` or the injection flow, recorded in
  `.ai/z88dk/targets.md` — not a reason to drop the model from the template.
- Done: all cases pass; `npm run test:timings` keeps every fast file under 20 s.
- **As built (2026-10-22):** no product change was needed — every model ran first time.
  - `test/z88dk/zccReplay.ts` builds through the real `Z88dkCompiler` with zcc replayed from a fixture
    (gzipped maps unpacked), narrows with `isInjectableCompilerOutput` and makes Run's `CodeToInject`
    as `injectCode` does; `Z88dkCompiler.test.ts` now uses it too (its own copy is gone).
  - `test/z88dk/templateRun.ts` plays the machine's own flow (`playInjectionFlow`) and asserts: `counter`
    reaches 6, ink in the top two character rows (it is 0 and none before Run, checked), and 50 frames
    later PC in the ROM with FRAMES counting (the program returned into BASIC).
  - Fast (`z88dk-templates-run.core.test.ts`, ~10 s of tests): 48K, 128K, +3E (fdd1), TC2048 on the
    shipped 48K ROM, Next. Slow (`z88dk-templates-run-models.core.test.ts`): 48K NTSC, Pentagon, Scorpion
    on the 128K ROMs, the other 11 +2A/+3/+2E/+3E models, and the ROM-gated TC2048 (own ROM), TC2068 and
    TS2068.
  - **The Next** runs from the harness's direct `.nex` load after `prepareBasic()`, which hands over
    the 48K BASIC ROM and system variables as `.nexload` does; it asserts the loop and the screen, not
    a return (interrupts stay off without NextZXOS). The real `.nexload` route is T5's.
  - **The Scorpion with its own ROM** refuses Run (`requireKnownRom`: Klive does not know that ROM's
    editor); the test pins the refusal. Without its ROM, the Scorpion boots the 128K ROMs and runs.
  - Locally the TC2048 and TS2068 cases passed with ZEsarUX's ROMs named in `KLIVE_TC2048_ROM` /
    `KLIVE_TS2068_ROM` (`$9C40` origin on the TS2068). No TC2068 ROM was available: that case is
    unverified.

### T4 — Debug on the real cores, one per route (G3)

Extend the pattern of `test/z88dk/z88dk-debugger.core.test.ts` (map → `z88dk-debug-adapter` →
`SourceLevelDebugInfo`, breakpoints resolved by file and line) to the template fixtures:

| Case | Proves |
|---|---|
| `tpl-sp48` | the template's own lines (the existing test uses a different program) |
| `tpl-sp128` on the 128K via 48 BASIC | debugging survives the 48 BASIC injection route |
| `tpl-timex-ts2068` (ROM-gated) | `+ts2068`'s origin `$9C40` and its map |
| `tpl-zxnext` | `+zxn` classic: the `.nex` load, its map, the frame-pointer chain |

Each: a breakpoint on `int result = value * value;` (line 12) stops the machine there; the call
stack reads `square` ← `main`; `value` = 1 at the first stop; `counter` = 1 in the globals; step
over reaches `return result;`; step out returns into `main`'s `printf` line; continue runs to the
next stop with `value` = 2.

- Done: all pass; the Next case runs from the committed gzipped map with no zcc.
- **As built (2026-10-22):** no product change was needed. `test/z88dk/z88dk-templates-debug.core.test.ts`
  (fast tier, ~13 s with core start-up): 48K, 128K via 48 BASIC, TS2068 (ROM-gated; passed locally),
  Next (direct `.nex` load after `prepareBasic()`). `templateRun.ts`'s `debugWalkthrough` does it the
  IDE's way at every point: the build's debug profile (zcc replayed), Debug's delivery (the injection
  flow), the breakpoint bound through the build's **list items** (as a C line's breakpoint is),
  `hasSourceLevelDebug` (what Debug sends the emulator), source stepping with the IDE's default **Just My
  Code**, the stop built as `MachineController.getSourceStopInfo` builds it, and the Call Stack and
  Variables from the IDE's own models (`buildSourceCallStack`, `buildVariableSections`).
  - The lines are found from the template's text, not numbered (the Next's template is shorter):
    the breakpoint is `int result = value * value;` (line 11 on the Spectrum templates, 10 on the Next).
  - Observed at every route: the stop names its line first, the stack is `square` ← `main` ←
    `(startup)`; `value` 1 / `counter` 1; Step Over → `return result;` with `result` 1; Step Out → the
    printf line in `main`; Continue → `value` 2 / `counter` 2. Before its line runs, `result` shows
    whatever the stack held (e.g. -31974), as an uninitialised C local does in any debugger.

### T5 — The IDE check sweeps every template (G5)

`scripts/z88dk-ide-check.cjs` gains a `templates` part that, for each machine/model of §1
(TS2068 only with its ROM configured), runs on the built app:

1. `newp <machine> ccheck z88-dk`, open it (the machine and model switch);
2. **Build** — no Problems; **Run** — the screen shows the template's output (screenshot);
3. **Debug** — a breakpoint on line 12 pauses; the Call Stack names `square` and `main`;
   Variables shows `value` and `result`; Watch shows `counter`;
4. **Export** — the native file (`.tap`, `.dsk`, `.nex`) equals the one zcc wrote, byte for byte.

- Local only (needs z88dk); screenshots in `.z88dk-ide-check/templates/`.
- Done: `node scripts/z88dk-ide-check.cjs templates` reports every check passed.
- **As built (2026-10-22):** `templates` (and `templates:<case>`) in `scripts/z88dk-ide-check.cjs`; nine
  cases, one fresh app each: 48K, 128K, Pentagon, +2E, +3, Scorpion, TC2048, TS2068 (when
  `KLIVE_TS2068_ROM` names its ROM), Next (copies the NextZXOS card `~/Klive/ks2.cim`, or
  `Z88DK_IDE_CARD`, into the app's home). 14 checks each - Build (zcc's result line, no errors), Run
  (`counter` 6 in the Watch panel, polled: the Next's first Run boots NextZXOS from the card), Debug
  (pause on the `result` line, Call Stack `square` ← `main` ← `(startup)`, Variables `value`/`counter`,
  Step Over → `result` 1, Step Out → the line that called `square`), Export (byte-identical native
  file). It sets "Sync the Source with the Current Breakpoint" (off by default) so the editor follows
  stops off screen. **126/126 passed** with v2.4.
  - **The sweep found two real faults in the Next template**, both fixed:
    1. `main` returned. `.nexload` leaves no return address (`_input/nexload.asm`), so the return reset
       the machine. The template now ends in `while (1) {}` (`for (;;) {}` fails to link at `-O2`).
    2. **A z88dk v2.4 bug**: the classic Next crt runs into printf's format table, so whether a
       program using `printf` starts depends on where the `%d` handler lands (`.ai/z88dk/targets.md`).
       Run's `-O2` build hit it. The template prints with `putchar` (`print_text`/`print_number`), and
       `Z88dkCompiler` now warns (`ZCC-PRINTF`, `compiler.z88dk.printfTableInStartup`) whenever a map
       puts `__printf_format_table` in `code_crt_init` (`printfTableInStartupCode`); fixture `zxn-printf`.
  - The core tests had missed both because every fixture was Debug's build: each template now also has
    a `tpl-<x>-build` fixture (Run's `-O2`), `buildTemplate` takes the profile's fixture and fails when
    zcc's arguments differ from the fixture's, and the Next's fast run test checks that the program
    stays in its own code after the loop.
  - `squared = square(counter);` is a statement of its own in the Next template: in
    `print_number(square(counter))`, sccz80's one-line look-ahead attributes the rest of the line to the
    next one, so Step Out showed the following line.
  - Not explained: once (the first full sweep), the TC2048 and TS2068 cases had `main.tap` open as the
    active preview tab at the Debug stop; it did not recur in five later runs of each.

## 5. Out of scope and known limits

- **16K Spectrum**: zcc's `+zx` org is `$8000`; the build refuses with a clear message. Lowering the
  org (`-zorg`) to fit 16K is a separate feature, not a template fix.
- **SDCC builds** keep the C4 limitation (no `-debug`); templates use sccz80.
- **Banked builds** (128K/Next banks) are covered by the existing `zx-banked` tests; templates are
  non-banked.
- ZX80, ZX81 and Z88 templates are not Spectrum family and are already covered by the integration
  plan's tests.

## 6. Risks

| Risk | Mitigation |
|---|---|
| A model's route fails (e.g. Pentagon 48 BASIC flow) | T3 surfaces it as a product fix, recorded in `targets.md` |
| The TS2068 ROM is not available in CI | ROM-gated skip (T-D5); the IDE check covers it locally |
| The Next map is too large to commit | Committed gzipped (T-D3) |
| v2.5 changes the map | C3's version range; fixtures regenerate with the pinned version |
| The fast tier slows down | T-D4 split; `npm run test:timings` |
