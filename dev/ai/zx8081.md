# Sinclair ZX80 / ZX81: Decisions, As-Built Notes and What Is Open

Two plans built these machines and were closed on 2026-11-04, every phase done; both are in git
history:
- `dev/plans/ZX8081_WASM_PLAN.md`: one C/WASM core for the ZX80 and ZX81 (implemented 2026-10-03):
  the shared Z80's new hooks, the ULA, the picture, tape, the models, the debugger, the virtual
  keyboards.
- `dev/plans/ZX8081_CODE_INJECTION_PLAN.md`: machine code for them (implemented 2026-10-16):
  `.model ZX80`/`ZX81`, `.defzx`, Run/Debug as a `1 REM` program, `.p`/`.o` export, `klive run`.

This note keeps what a later session needs and the two READMEs do not say. Read them first:
- `src/emu/machines/zx8081/wasm/README.md`: the core. Its layout, how the ULA maps onto the shared
  Z80's hooks, the picture and its window, tape (fast load, real time, SAVE), the models, the build
  and its size and speed, the access profile, the test folders.
- `test/harness/zx81/README.md`: the harness (real ROM, boot to the K cursor, typing, program loading,
  the debugger, history).
- The lessons for the next machine built on the WASM core: `dev/ai/wasm-migration-intent-and-lessons.md`.
- The ROM annotations: `dev/ai/rom-annotations/zx81-authoring-guide.md`.

## Provenance

- The ULA logic and its constants, the program-file recognition, the keyboard mapping and the typer
  tables are ported from Clock Signal (CLK) by Thomas Harte, **MIT**, commit `096de574…`, extracted
  to `dev/research/clk-zx8081/` (read its README). Every Klive file derived from a CLK file keeps CLK's
  copyright and permission notice as a header comment naming the upstream file;
  `THIRD_PARTY_NOTICES.md` carries the notice. CLK was a design input, not a drop-in: its
  per-half-cycle bus model and CRT waveform were rewritten to Klive's hooks and an RGBA raster.
- The ROMs are not MIT. Their notice allows free non-commercial use and ships with them as
  `src/public/roms/zx8081-roms-readme.txt` (decision D5).
- GPL emulators (EightyOne, sz81, MAME `zx.cpp`, ZEsarUX) may be **run** as behavioural oracles, with
  only observed results recorded in Klive's words; their source is not read for design.
- Test programs are written for Klive, or come from `dev/research/zx81-tapes/` (MIT or Unlicense, each
  pinned to a commit, licences in `licenses/`). Any other third-party `.P` needs the same provenance
  before it enters the repo, and a fixture copied from there brings its licence file along.

## Core decisions

Accepted by the project author on 2026-10-03. Code cites them by ID.

- **D1, R in the shared core:** the second M1 of a prefixed instruction increments R, for every
  machine (hook C4 below). Real Z80 behaviour that the ZX81 depends on; no tact moved.
- **D2, two machine IDs, one host, one artifact:** `zx81` (models 1K, 16K, 64K and the NTSC "US"
  variants) and `zx80` (1K, 16K, and the ZX80 with the 8K ROM). Users think of them as two machines:
  different keyboards, ROMs and file types.
- **D3, the keyboard matrix:** the core reuses the Spectrum's `zx-spectrum-keyboard.c` through
  `#define` aliases. It is a Sinclair matrix, not a Spectrum feature (moving it to a neutral folder
  is a possible refactor).
- **D4, the visible window:** 352 x 288 (352 x 240 NTSC), the Spectrum-like border.
- **D5, the ROMs ship** with their notice (see "Provenance").
- **D6, one artifact** with a run-time ZX80/ZX81 flag (`zx8081Configure`), not two builds. The
  benchmark did not object.

The shared Z80's hooks, each a default no-op so a core that does not define one is unchanged
(`dev/scripts/check-wasm-cpu-contract.cjs` checks this):
- **C1** `Z80_REFRESH(address)`: every refresh (unprefixed M1, the halted cycle, the NMI and INT
  acknowledges, the second M1 of a prefixed instruction), with I:R **before** the increment,
  immediately before the refresh tact, so "end of refresh" is `cpu.tacts + 1` on every path.
- **C2** the opcode-substitution contract of `Z80_AFTER_OPCODE_FETCH`: the hook may overwrite
  `cpu.opCode` and the dispatch uses the new value. Documented and tested; the ZX81 does not use it
  (see "The core as built").
- **C3** `Z80_NMI_ACK_WAIT()`: between the 2 + 2 T of the NMI acknowledge (the split only exists
  under `#ifdef`). **C3′** `Z80_INT_ACK()`: after the INT acknowledge's 6 T.
- **C4** R on the second M1 (D1). Tact placement is unchanged; the second M1 refreshes and fires C1.

Tests: `test/wasm/z80-hooks/` (a test-only translation unit for C1-C3), `test/z80/r-register.test.ts`
(C4, both CPUs).

## The core as built

Deviations from the original design that the README does not already state, each found on the way:

- Phases 2 and 3 (skeleton, ULA and video) were done together: without the ULA the ROM runs the
  display file as code and never reaches the K cursor.
- `ZxPFile.ts` decides the memory model from E_LINE (past $4400 means 16K), not from the file size as
  CLK does, which misjudges files with trailing bytes. The character tables come from the ROMs'
  glyphs: CLK's have the symbol rows swapped between the machines.
- No audio ABI: the machine has no `getAudioSamples`, which the renderer treats as silence. A stock
  ZX80/81 has no sound; the VSYNC buzz is the follow-up that would need one.
- The ZX80's key-wait point ($013F, `ZX80_KEY_WAIT`) was found by sampling the PC at the prompt; there
  is no ZX80 listing. The "load finished" points are ZX81 $06D1 and ZX80 $0203 (CLK's).
- The CPU panel has no "last opcode" field. While the display file runs, the CPU executes forced NOPs,
  so the disassembly (real memory) and the executed instruction differ; the executed $00 is
  `machine.opCode` (`test/zx8081-hw/debug.test.ts`).
- The BASIC Listing view lists both machines (`zx8081BasicListing.ts`) as the ROMs' LIST does: a line
  runs to its NEWLINE (the ZX81's length field is not what LIST follows), line numbers print their
  thousands as one character ($1C + n, so 14393 is `E393`), and each ROM's token spacing (ZX81 TOKENS
  $094B; ZX80 $0584/$05A8). `test/zx8081-hw/basic-listing.test.ts` compares it with the ROMs' screens.
- Timing notes to keep before anyone "fixes" a constant: the delay hooks drain WAIT before the access,
  where the real ULA samples it at T2 (at most 2 T apart; the jitter test is the guard, and a
  `Z80_WAIT_SAMPLE` hook is the fallback). `z80.c` models M1 as 3 + 1 T against the real 2 + 2, so the
  picture may sit one T (2 px) off the real ULA, invisible inside the window.
- The per-T ULA work is the hot path; the hooks are `noinline` and should stay branch-light.

## Files, tape and the IDE

- `.p`/`.81` (ZX81) and `.o`/`.80` (ZX80) are registered in `src/renderer/registry.ts`, open in the
  program-file viewer, and are the tape. The Explorer's entries (`TapeLaunchMenu.tsx`) and the
  machine menus (`src/main/machine-menus/zx8081-menus.ts`) run the same `tape-load` command.
- "Load and Run" resets the machine, types `LOAD ""` (`LOAD` on the ZX80), waits for the ROM's "load
  finished" point and types RUN. Fast load is an option. A ZX80 with the 8K ROM also takes `.p`/`.81`.
- The machine registry gives each machine a ZX81 or ZX80 character map for the memory panel and the
  custom ZX81 disassembler (`zx81-disassembler.ts`): the error-code byte after `RST $08`, and after
  `RST $28` the calculator literals up to `end-calc`, whose numbering (the ROM's table at $1923)
  differs from the Spectrum's (`end-calc` is $34 here).
- Docs: `docs/content/en/guides/machines/zx81-zx80.mdx` and
  `docs/content/en/reference/z80-assembler/zx80-zx81.mdx`; screenshots from
  `dev/scripts/doc-shots/recipes/zx81.cjs`, which also checks the machine in the running app.

## The virtual keyboard

The ZX81 design was approved by the project author on 2026-09-27; the ZX80's was built later on the
same geometry. The components are the reference now (`src/renderer/appEmu/Keyboard/Zx81Key.tsx`,
`Zx81Keyboard.tsx`, `Zx80Key.tsx`, `Zx80Keyboard.tsx`; `KeyboardPanel.tsx` picks one). Do not
re-derive the design. The facts the code relies on:

**ZX81 geometry.** Measured from the reference photo
<https://dn710202.ca.archive.org/0/items/ZX81_Keyboard_Layout/ZX81_keyboard.jpg> (629 x 228 px) at
`U = 100 / 45.5` key units per pixel:

| Quantity | Units | Notes |
|---|---|---|
| Key face | 100 x 74.7, `rx` 8 | every key, SHIFT, NEW LINE and SPACE included |
| Horizontal pitch / gap | 128.1 / 28.1 | the gap is the SVG's `marginRight` |
| Vertical pitch | 124.6 | keyword band + key + function band; the cell is 100 x 124.6, the face at y 24 |
| Row stagger | 0 / 68.1 / 98.9 / 37.4 | digits, Q-P, A-NEW LINE, SHIFT-SPACE |
| Outer margin | 15.4 | |
| Whole keyboard | 1382 x 501 | `DEFAULT_WIDTH` / `DEFAULT_HEIGHT` for `calculateKeyboardZoom` |

The legend positions and sizes inside a key are the constants in `Zx81Key.tsx`. The font is
`Helvetica, Arial, sans-serif`; the photo's face is a condensed, heavier Helvetica, the one accepted
visual gap.

**ZX81 legends.** From the ROM's key tables: `K-UNSHIFT` $007E, `K-SHIFT` $00A5, `K-FUNCT` $00CC and
`K-GRAPH` $00F3. `FETCH-1` ($04F7) indexes `K-GRAPH` from $00C7, so the graphics start at key A, and
Z, X, C, V, B, N, M, `.` and the other non-graphics keys carry none. The photo confirms every glyph.
The key table is `Zx81Keyboard.tsx`'s. The block graphics' quadrants are `Zx81Key.tsx`'s `GLYPHS`
(codes $01-$0A, bit 7 swaps ink and paper, the chequer stays). Deliberate choices: `INKEY$` where the
photo prints "IN KEY$", and ARCSIN/ARCCOS/ARCTAN as the keyboard prints them, not the screen's ASN,
ACS, ATN. The `0` key's main legend is the slashed zero.

**ZX81 zones and clicks:**

| Zone | Hit area | Click (either button) |
|---|---|---|
| `main` | the key face and the keyword above it | holds the key; the right button adds SHIFT |
| `shift` | the red legend or arrow | holds SHIFT with the key |
| `below` | the function under the key | queues SHIFT + NEW LINE (FUNCTION mode), then the key |
| `glyph` | the graphic box | queues SHIFT + 9 (GRAPHICS on), SHIFT + key, SHIFT + 9 (off) |

The keyword above a key is the main key: the ROM shows it whenever it is in K mode. There is no
symbol-shift or extended mode. Clicks are ignored while `getKeyQueueLength() > 0`. Queued keys are
held 4 frames and step 10 (`HOLD`, `STEP`): the ROM's debounce rejects the 48K's 0/3/10 offsets.

**Visual states.** A light key face is new among device keyboards: on a white key the hover colour is
the accent's dark end, while the keyword and function print on the black body use the light end, so
the ZX81 has two highlight tokens. A pressed key's face becomes the light accent. The colours are
L1 `DEVICE` entries in `palette.ts` with `--*zx81*` aliases in `componentAliases.ts`; the lessons are
in `dev/ai/ui-theming-intent-and-lessons.md`. There is no per-machine keyboard height: the keyboard
zooms to fit.

**ZX80.** The ZX81's key face, gap and row stagger, at the project author's request (a measurement of
the ZX80 photo agreed within its error). Nothing is printed under a ZX80 key, so its cell is 114 units
high. Reference photo: an original 4K-ROM ZX80, top-down, 2048 x 1538 (Tynemouth Software, "ZX80
Keyboard Overlays", <http://blog.tynemouthsoftware.co.uk/2017/05/zx80-keyboard-overlays.html>): blue
keys on a black case, white main legends, amber shifted legends (above the number keys and NEW LINE,
on the face of the others), white keywords above the letters, BREAK in dark blue above SPACE. The
legends come from the 4K ROM and `test/controls/Zx80Keyboard.test.tsx` checks them against it:
unshifted at $006C, shifted at $0093 (39 bytes each, matrix order without SHIFT), tokens from $00BA,
the K-mode rule at $0346; the graphics are the character set's ($0E00) codes $02-$0B. The keyboard
prints CONT, GOTO, GOSUB, RET and RAND for the ROM's longer tokens. Zones: `main` (the face, the
keyword, BREAK) and `shift` (any amber legend, arrow or graphic); nothing is queued. **A ZX80 with the
8K ROM shows the ZX81 keyboard** (`MC_ZX80_ROM8K`): it types as a ZX81, and the upgrade kit shipped
with a ZX81 overlay.

## Machine code decisions

Accepted by the project author on 2026-10-16. Code cites them by ID; they are a separate series from
the core's D1-D6.

- **D1, two models in the shared enum:** `SpectrumModelType` has `ZX80 = 5` and `ZX81 = 6`. RAM size
  is not part of the model; the fit is checked against the running machine.
- **D2, what the model changes in the assembler:** `.model ZX80`/`ZX81` and `#ifmod`; `.bank`/`.page`
  and Next pragmas and instructions are errors; code at $8000 or above is warning Z0378 (it cannot
  execute on a stock machine, but data may live there); **`.defzx "TEXT"`** emits text in the
  machine's character set, a lower-case letter giving the inverse-video capital, and a character the
  set lacks is error Z0381. ZX80/ZX81 diagnostics are Z0378-Z0381.
- **D3, one program-image builder, two layouts:** `buildZx8081ProgramImage` in
  `src/common/zx8081/programImage.ts` turns the assembler output into the memory a `.p` (ZX81, from
  $4009) or `.o` (ZX80, from $4000) holds; Run and Export both use it, so what runs is byte for byte
  what is exported.
  - *Layout A, the REM container (default):* code at or above the REM body ($4082 on the ZX81, $402B on
    the ZX80) becomes `1 REM <bytes>` / `2 RAND USR <entry>` (entry: `.ent`, else the first segment),
    then a display file (collapsed for 1K, expanded for 16K), the variables' end marker and consistent
    system variables. Errors: a segment below the REM body or reaching $8000, an image that does not fit
    with a minimal stack, and on the ZX80 a $76 in the REM body (its lines have no length field, the ROM
    scans for $76).
  - *Layout B, the full image:* a first segment at the image base means the source *is* the image
    (sysvars, BASIC lines and display file in `defb`/`defw`); the builder copies it and validates it.
  - Anything starting between the base and the REM body is an error naming both layouts.
- **D4, Run and Debug boot, write the image and type RUN:** the flow is `ReachExecPoint` (the key-wait
  point), `Inject`, `KeepPc`, `Start`, `QueueKey` R + NEWLINE. The code starts as it would after LOAD
  on real hardware, through `USR` with the ROM's state; `RET` goes back to BASIC. Jumping in from the
  key-wait loop would leave IX (the SLOW-mode NMI's) and the ROM's stack to luck. A model mismatch is
  the usual "cannot run on this virtual machine" error. `.injectopt` options are ignored. **Inject**
  alone writes the image and the user types RUN.
- **D5, `CodeToInject` unchanged:** the emulator builds the image from the segments, the entry and the
  model, because only it knows the RAM size; Export builds it on the renderer side.
- **D6, shared placement:** the builder and the character sets and token tables
  (`src/common/zx8081/charset.ts`, moved out of `ZxPFile.ts`) are in `src/common/` and import nothing
  from `src/emu/` or `src/renderer/`.
- **D7, source-level debugging needs nothing new:** the REM container keeps every byte at its assembled
  address. Verified in the running IDE (`dev/scripts/zx81-ide-check.cjs`): the SLOW-mode NMI does not
  disturb stepping.
- **D8, export:** `expc -f p` (ZX81) or `-f o` (ZX80); with no `-f`, the build's model (or the
  machine's ROM) picks it. TAP/TZX/NEX on these models is an error. The Export dialog offers formats by
  machine.
- **D9, other compilers** (Klive BASIC, zxbc, Pasta80, sjasmplus) emit Spectrum code; on a ZX80/81 the
  model-mismatch error refuses it.
- **Q1, the default model is the running machine's:** a source with no `.model` is assembled for the
  running machine, on every machine.
- **Q2:** Layout A uses lines 1 and 2. **Q3:** no RAMTOP layout (a `.p` cannot set RAMTOP; Layout B can
  express a copying loader by hand). **Q4:** the 64K model's $2000-$3FFF is not used.

## How code injection works

- **The ROM facts it rests on**, checked by typing the lines on the emulated machines and pinned by
  `test/zx8081/program-image.test.ts` and `test/zx8081-hw/program-image.test.ts`:
  - ZX81 lines are number (2 bytes, big-endian), length (2 bytes, little-endian), body, $76. `1 REM`'s
    body starts at $4082 (16514) and may hold any byte, $76 included (the ROM follows the length; only
    LIST shows garbage). A number in a line is its digits, $7E and the 5-byte float:
    `2 RAND USR 16514` is `00 02 0E 00 F9 D4 1D 22 21 1D 20 7E 8F 01 04 00 00 76`.
  - A ZX81 `.P` runs on load when the saved NXTLIN ($4029) points at a line.
  - ZX80 lines have no length field. Its tokens are $D4-$FE in the order of the ROM's keyword table
    ($00BA-$013A), `ZX80_TOKENS`; functions such as `USR` are letters, numbers are text:
    `2 RANDOMISE USR(16427)` is `00 02 EF 3A 38 37 DA 1D 22 20 1E 23 D9 76`. The ZX80's display file
    lies after E_LINE and is not part of a `.o`.
  - `USR` code runs with the ROM's state: on the ZX81 IY = $4000, and in SLOW mode the NMI display
    routine needs IX, IY and AF' untouched.
- **Default origin.** Code with no `.org` under a ZX80/ZX81 model starts at the REM body, not $8000
  (`modelDefaultStartAddress` in `common-assembler.ts`).
- **Q1 lives in `Z80Compiler`.** With no options (the IDE, the worker, the CLI), `Z80Compiler` builds
  `AssemblerOptions` with `currentModel` from the app state's machine (`defaultModelTypeForMachine` in
  `SpectrumModelTypes.ts`); `output.modelType` stays unset, so run/debug still take the machine's own
  flow. Next pragmas work on a Next without `.model`; `.bank` and Next instructions still need one
  (`test/z80-assembler/default-model.test.ts`).
- **Injection writes, it does not LOAD.** `injectCodeToRun` writes the program area and only the
  *layout* system variables (`ZX81_LAYOUT_SYSVARS` / `ZX80_LAYOUT_SYSVARS`); FRAMES, CDFLAG, MARGIN and
  the keyboard state stay the running machine's. The ZX81 gets an empty edit line (`7F 76`) at the new
  E_LINE. The ZX80's edit line and display file live after E_LINE, so they move with it and its
  D_FILE/DF_EA/DF_END/P_PTR are relocated. Typing RUN clears and rebuilds the rest. No Spectrum-style
  CLS.
- **The 8K-ROM ZX80 waits elsewhere.** It has no NMI generator, so its ROM idles in FAST mode and never
  reaches SLOW-DISP ($04CF); its key-wait point is the FAST-mode display call $0229
  (`ZX81_FAST_KEY_WAIT`), for the tape-load flow too.
- **Model strings.** The code's model reaches the host as `"zx80"`/`"zx81"` (`modelTypeToMachineType`,
  `bootModelFor`).
- **Renderer pre-check.** `zx8081InjectionProblem` (`src/renderer/appIde/utils/zx8081-code.ts`) builds
  the image before anything is sent, so a layout error is a plain command error; it also refuses
  debugging a unit test on these machines.
- **Export.** `-as` means *run when loaded* on a `.p` (sets NXTLIN to the `RAND USR` line). There is no
  `--ram`: the running ZX80/81's RAM is used, else 16K. The Export dialog (`formatOptionsFor`) swaps a
  saved Spectrum format for the machine's, hides the Spectrum loader options and labels the checkbox
  *Run the program when loaded* on a `.p`.
- **Templates.** `src/public/project-templates/zx81/default` prints a centred welcome and the machine's
  name in inverse video through the ROM's `PRINT-AT` ($08F5) and `PRINT-A` (`RST $10`); `zx80/default`
  prints the same screen. The ZX80's `RST $10` keeps its print state in the alternate registers
  (DE' = DF_EA, BC' = S_POSN), which `USR` code must load and store back as the ROM's PRINT does
  ($06E0 / $073A); with no PRINT AT it positions by NEWLINEs made at run time, because a REM line cannot
  hold $76 (`test/zx8081-hw/project-templates.test.ts`).
- **Headless.** `klive run` builds and runs ZX80/81 projects (`test/cli/klive-run-e2e.test.ts`, the
  `runzx81` fixture).
- **Harness note.** A tiny program finishes its fast load while the harness is still typing `LOAD ""`,
  so `loadProgram` never sees the auto-RUN; such tests wait on the program's effect.

## Open

- **The unit-test runner** does not run on the ZX80/ZX81 (`src/main/unit-tests/unitTestMachines.ts`);
  it needs a return point for the runner on these machines.
- **Checkpoints:** the core has no `captureCheckpoint`/`tryRestoreCheckpoint`, so the injection flow
  boots every time (well under a second of emulated time). Copying the whole linear memory, as the
  Next does, would be cheap here.
- **`.model ZX80` on a ZX80 with the 8K ROM is not refused:** `"zx80"` is also the machine id that code
  with no `.model` arrives as there. The image is laid out for the ROM (ZX81) whatever the model says.
- **Keyboard glyph race:** queued GRAPHICS toggles can race on fast repeated clicks, as on the 48K. A
  cursor-mode check would read the ZX81's MODE system variable ($4006, see `K-DECODE` $04DF).
- **Oracle runs** against EightyOne or CLK were not done; the evidence is the ROM itself, the corpus
  programs and hi-res.
- **Follow-ups not started:** the Chroma 81 colour interface; the ZonX AY and Quicksilva sound boards
  and the VSYNC buzz; TZX ZX81 blocks (block $19) and TZX/WAV fast load; CHR$128 and UDG boards; the
  Timex TS1000/TS1500 and the Lambda 8300.
