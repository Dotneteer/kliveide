Next palette debugging

The Next Palettes panel shows the eight palette banks, but only as a sample: it re-reads them on the shared state poll, and nothing tells you what changed or who changed it. This page proposes a PAL: breakpoint and a Palette document that pops out of the panel.

Does the panel refresh today?Yes, by polling: at once after every stop or step, at most every 750 ms while running, every 5 s when nothing moves. Each refresh reads all 2048 entries.
What it missesEverything between two samples (fades, Copper raster colours), what changed since the last stop, and who wrote it.
Does a palette change deserve a breakpoint?Yes. The target is computed state ($40 index + $43 select at write time), so no address, I/O or NR: breakpoint can name it. The sprite watch is the template in the core.

Mockup 1 · Phase 1 and 3

The Next Palettes panel, kept compact

What changes

  • Pop-out button in the header opens the Palette document.
  • Change dot: the device had a palette write since the last stop (from a core dirty bitmap).
  • Breakpoint dot: a PAL: breakpoint watches this device.
  • Refresh on change: a core generation counter makes the panel refresh when the palette changed, and skip the read when it did not.
  • The bank chips and the thumbnail stay as they are.

Mockup 3 · Phase 2

PAL: breakpoints

A hardware stop like SP:, INT: and DMA:: no address, no gutter. Set it from the command line, a swatch's context menu or the details pane.

; any write to sprite bank 1, entry 3 bp-set PAL:SPR1:$03 ; Layer 2 entries 0-15 in either bank, real changes only bp-set PAL:L2:$00-$0F -changed ; Copper writes count too (off by default, as for NR:) bp-set PAL:ULA2 -c ; the tilemap's live bank flips ($6B bit 4) bp-set PAL:TM:LIVE ; filters work as everywhere else bp-set PAL:ANY -if palNew == $1C7 -log "{palSlot} {palIndex}"
