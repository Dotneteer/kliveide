DMA Debugging Tools

Seven tools for seeing what the courier does: what it was told, what it actually holds, who owns the bus and when, and where the bytes went. Each one is aimed at a trap described in DMA: One Bus, Two Masters. The mockups use Klive's dark theme and an example run of that chapter's sample player: 2,048 bytes from $C000 to the Specdrum DAC on port $DF, burst mode, prescaler 55.

What Klive has todayDMA program regions decoded in the disassembly (decode: "dma"), the pure decoder src/common/zxnext/dma/dmaDecoder.ts, and port and NextReg breakpoints that report a DMA hit.
What is missingNo view of the DMA's live registers, no record of what was written to $6B/$0B, no picture of bus ownership, and no way to stop on a DMA event or step it.
What the core already holdsEvery field these mockups show is a static in zxnext-dma.c (start and working addresses, counter, sequencer, prescaler, read sequence, zxnDDMA state). EmuApi exposes none of it yet.

Answers

  • Which dialect am I in? The last port touched decides N or N + 1 bytes.
  • Start or working address? Both, side by side. The working one changes colour once it moves away from the start.
  • What will this prescaler sound like? Nominal rate, the exact 4 × P + 3 period, and the measured period with its jitter.
  • What will the next IN return? The read-sequence pointer and mask.

Catches

  • Enable without $CF
  • A half-written register group (the decoder's follower count)
  • WR4 bit 4: deaf until reset
  • Auto restart in continuous mode
  • zxnDDMA settings left on by an earlier transfer
DMA · warnings in other states
The CPU will not get the bus back. Auto restart in continuous mode. Only a reset, or an interrupt enabled in NextRegs $CC–$CE, ends it.
Deaf until reset. WR4 $91 asked for an interrupt control byte and gave no port B address. The DMA ignores every byte from here.
Enabled without a load. $87 came after a WR0 at PC $8031 but no $CF. The transfer uses the working addresses $C800 and $00DF from the last block.
Expecting 2 more bytes for WR0 (length low, length high). The next byte you write is taken as a follower, whatever it is.
Prescaler in continuous mode. The DMA keeps the bus while it waits: about 6.5 frames with the CPU frozen for this block.
Physical mode is still on. $DF $01 from transfer #27 stays until the next $DF or $C3.

Data from the core

  • A ring buffer of DMA port accesses: frame, tact, PC, port, value, direction, and the sequencer state after the byte (dmaWrSeq).
  • Recording on only while the panel is open or a DMA breakpoint is set, so normal runs cost nothing.

Interaction

  • Click a PC to open the source line; click a transfer to open it in tool 4.
  • "Copy as .defb" turns a setup into source, decoded comments included.

Answers

  • Why did my game drop a frame? A continuous transfer held the bus across the frame interrupt.
  • Is my sample rate right? The measured period against the prescaler's exact one.
  • How much CPU does burst mode leave me? Per frame, read off the bar.

Data from the core

  • A per-byte trace: tact of the request, the grant, the read and the write, the source, the destination and the value.
  • Bus request and acknowledge edges (dmaBusRequested, dmaBusAcknowledged) and the interrupt lines' pulses, so a lost pulse can be marked.

Answers

  • Did the copy land where I meant? The destination range, in bank and page terms when it went through the MMU.

Builds on

  • The Memory panel's existing range highlighting.
Tool 5 · Breakpoints panel + debug toolbar

Breakpoints and stepping: stop on what the DMA does

New breakpoint kinds for DMA events, and DMA stepping for the case the CPU stepper cannot cover: while the DMA holds the bus, the CPU does not run, so stepping the CPU never moves. Following the WASM core rule, each stop is a core candidate, and TypeScript decides what it means.

Add DMA breakpoint
Why memory breakpoints need a DMA flag A CPU memory breakpoint watches the CPU's accesses. The DMA reaches the same memory through the same MMU, so a write it makes into the screen is invisible to today's breakpoint. The proposal adds "CPU", "DMA" or "both" to memory breakpoints, as port and NextReg breakpoints already report a DMA hit.
Tool 6 · Klive assembler editor

Editor support: decode the setup before it runs

A .dma pragma, like the existing .copper one, marks a block of .defb as a DMA program. The editor then shows a code lens with the transfer's summary, a hover with the decoded groups, and warnings for the traps that are visible in the bytes alone.

Lint rules (from the bytes alone)

  • Enable without $CF; no leading $83 or $C3
  • A group's followers run past the block's end, or a later base byte would be swallowed
  • WR4 bit 4 set; a byte that matches no group
  • Auto restart with continuous mode; a prescaler in continuous mode
  • WR1 prescaler byte (accepted and dropped); zxnDDMA commands sent to $0B

Builds on

  • dmaDecoder.ts already decodes the bytes; the pragma only tells the editor where they are. The assembler output is unchanged.
  • The decoded region kind dma in program annotations, so the same summary appears in the disassembly.
