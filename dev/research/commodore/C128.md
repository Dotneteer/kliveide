# Commodore 128 — research notes

Facts for the Klive Commodore plan, gathered 2026-11-23. This file records what is **specific to the
C128**. The shared parts live in the sibling files and are not repeated here:

- the 8502 instruction set, its 7-bit processor port and 2 MHz electrical behaviour: `CPU_6502_FAMILY.md`
- the VIC-II core (badlines, sprites, raster timing), including the 8564/8566 VIC-IIe silicon: `C64_VIC_II.md`
- SID: `C64_SID.md` (or the SID file of the pack)
- the CIAs, cartridges (GAME/EXROM), tape, the IEC bus: `C64_SYSTEM.md`
- the 1541/1571 drive (GCR, MFM, the 1571's WD1770/1772, its CIA): `DRIVE_1541.md`

Conventions: every fact carries a source. *Inference* marks something concluded rather than read.
GPL sources (VICE, the MiSTer core, Denise) were read for facts only and are paraphrased; nothing was
copied into the repository. No commented ROM disassembly was used. ROM entry points quoted below come
from public reference pages (c128lib) and must be re-established by running the ROM before Klive relies
on them (the ROM-landmark rule the SAM and Enterprise work already follows).

## §1 Models

### §1.1 The three production families

| Model | Case | Drive | VDC | VDC RAM | ROMs (chips) | Years |

| C128DCR ("D Cost Reduced", metal) | metal desktop | internal cost-reduced 1571 ("1571CR") | **8568** | **64 KB** | 2 chips: U34 (32 KB, C128 BASIC) and U32 (32 KB, C64 + C128 KERNAL/editor/Z80 BIOS) + U18 | 1987– |

Sources: MAME `src/mame/commodore/c128.cpp` (machine list: `c128`, `c128p`, `c128d`/`c128dp`, `c128dcr`/`c128dcrp`,
`c128cr` prototype, national variants; DCR machine config fixes the VDC RAM option to `"64k"`, flat
defaults to `"16k"`); Wikipedia "MOS Technology 8563" (16 KB expandable to 64 KB in the original C128,
64 KB in the DCR); HandWiki "MOS Technology 8568" (the C128D got 16 KB or 64 KB depending on
manufacture date); MiSTer C128 README (chipset selectable "original C128 flat and newer C128 DCR").

- **PAL vs NTSC.** NTSC machines carry the **8564** VIC-IIe, PAL machines the **8566** (MAME `c128.cpp`
  tags both as U21, NTSC config uses `MOS8564`, PAL `MOS8566`). Line/frame geometry is the C64's
  (NTSC 65 cycles × 263 lines, PAL 63 × 312): see `C64_VIC_II.md`. The VDC runs from its own 16 MHz
  crystal in both (§5.3).
- **CR prototype.** MAME's `c128cr` is an engineering sample (Jun 1986, "2568R1X VDC", 3 ROMs: combined
  BASIC, combined C64/KERNAL, char ROM). Not a production target.
- **SID and CIAs per model.** Flat C128s shipped with the 6581 SID and 6526 CIAs; the DCR with the 8580
  and 8521 CIAs. *Inference / common knowledge, not verified in a primary source* — the MiSTer core's MRA
  files select "CIA, SID and VDC chips" per hardware variant (README), which supports there being a
  per-model difference (OQ4).
- **RAM.** 128 KB (two 64 KB banks) in every model; the MMU can address 256 KB (banks 2/3) but no
  production machine populated it (§4.6).

### §2.2 The 8502 at 1 and 2 MHz

- **Switch.** VIC-IIe register **$D030 bit 0** = 1 selects 2 MHz; bit 1 is the VIC "test" bit; the
  other bits read 1 (VICE `src/vicii/vicii-mem.c`, `d030_store` keeps `value | 0xfc` and sets
  `fastmode = value & 1`; MAME and the MiSTer README agree on bit 0). $D030 exists in C64 mode too
  (it is a VIC register), which is why the C128 can run C64 software at 2 MHz in the border.
- **What 2 MHz does to the display.** In fast mode the 8502 uses both halves of every cycle, so the
  VIC-IIe loses its φ1 accesses: the 40-column picture shows garbage while the CPU is fast; the KERNAL
  blanks the VIC screen when it enters FAST (search summary of the C128 PRG; MiST issue #101 "the VIC
  would then just display garbage while the cpu is running at 2 MHz which also happens on the real
  c128 in c64 mode"). The VDC is unaffected.
- **What still costs the CPU cycles in fast mode** (VICE `src/vicii/vicii-clock-stretch.c`,
  `src/c128/c128cpu.c`, GPL, facts only):
  - VICE does **not** steal badline cycles in fast mode (`vicii.c`: the badline steal runs only when
    `fastmode == 0`).
  - **DRAM refresh** still happens: VICE keeps a refresh alarm starting at cycle 11 of each line and
    stretches the CPU over the refresh cycles (cycles 11–15 of the line, 5 refreshes), pushing the
    alarm to the next line once past 15.
  - **I/O accesses are stretched** to the 1 MHz bus: a read in fast mode adds a half cycle when it
    falls on the wrong phase; a read-modify-write to I/O adds a full cycle. The chips at $D000–$DFFF
    (VIC, SID, CIAs, MMU, VDC) are 1 MHz devices.
  - Z64K's changelog: "DRAM refresh in 2 MHz mode reads valid data" (z64k.com).
- **"When does 2 MHz take effect in the border."** Software sets FAST from a raster IRQ below the
  display window and SLOW again above it; Wikipedia quotes ~35 % overall gain for that technique. VICE
  applies the switch on the store (it resets its half-cycle phase on the write). The exact cycle at
  which the new speed takes effect, and what the VIC fetches on the line where the switch happens, is
  not documented in any source found (OQ2). The VIC-II file should own the display side; this file owns
  the CPU side.

### §2.3 The Z80's real timing

This is the subject sources disagree on most. What is solid:

1. **The Z80 gets two clock ticks per φ0 cycle, both in the half-cycle the VIC is not using, and its
   clock is held during the other half.** ytmytm `c128-z80-8mhz` (GitHub, a hardware mod): "during
   system clock CLK1MHZ low phase VIC generates two clock ticks for Z80"; in the other half "we will not
   output any clock pulses — just like in the original setup", i.e. the Z80 is stopped "as its clock is
   held low". The Z80 clock comes from the VIC-IIe. So the Z80 is a 4 MHz part run in 2-tick bursts:
   **one Z80 T-state = half a φ0 cycle**, effective 2.045/1.970 MHz.
2. **No extra wait states on memory or I/O.** Real-hardware measurements in VICE bug #1979
   (sourceforge, 2024): an `OUT` takes 12 Z80 cycles = 6 φ0 cycles; a PAL raster line is 126 Z80
   cycles = 63 φ0 cycles; instructions combine freely (7+7 runs as fast as 10+4); a block copy measured
   10.5063 φ0 cycles per byte against a theoretical 10.5 (an LDIR iteration is 21 T-states → 10.5 φ0
   cycles, so *inference*: no stretch on LDIR's memory cycles). VICE's `src/c128/z80.c` says the Z80
   mode has no clock stretching because every memory/IO transaction runs at 1 MHz; its
   `z80_clock_stretch()` is empty. VICE's Z80 steps the main clock in half-cycle units and aligns to a
   whole φ0 cycle when entering and leaving Z80 mode.
3. **The VIC's DMA stops the Z80.** MAME `c128.cpp` drives the Z80's HALT-like stall from VIC BA
   (`vic_ba_w`), so badlines and sprite fetches stop the Z80 as they stop the 8502. Bug #1979 notes that
   timing over badlines is "not so simple": adding or removing one φ0 cycle before a badline shifts the
   result by 2 cycles or by none (*inference*: the Z80 stops on a 2-T boundary that need not match the
   cycle where BA falls).
4. **Unexplained residue.** Real hardware shows a 2-cycle variation in about half the per-line
   measurements; VICE's maintainer could not "get a firm grasp" on a clock-stretch mechanism and was
   about one cycle off without one; he speculated Z80 refresh might collide with the 8502/VIC refresh.
   Z64K reproduces the fluctuation of a conditional-RET test but with the opposite phase. (OQ1)
5. **HALT** advances in units of 2 φ0 cycles on real hardware (bug #1979). VICE originally treated HALT
   as a short wait instead of waiting for an interrupt (fixed in r45031).
6. **Popular description.** Commodore's own material and most secondary sources say "Z80 at 4 MHz,
   effectively 2 MHz because of the VIC"; one forum post argues the practical CP/M penalty is closer to
   70 % than 50 % because the BIOS also waits on the VDC (lemon64 t=75034). Both statements are
   consistent with 1–3 above.

**For Klive** (*inference*): Klive's `z80.c` can run the C128's Z80 unmodified if the host counts one
T-state as half a φ0 cycle, adds no memory/IO delay, and freezes the CPU (on a T-state pair boundary)
while VIC BA holds the bus. The shared core's `Z80_DELAY_*` hooks (`src/emu/z80/wasm/README.md`) are
enough to express a BA stall at M-cycle granularity; whether a finer stall point is needed is OQ1.

## §3 The two-CPU design

### §3.1 Bus ownership

- One bus, two CPUs, never running together. **MMU MCR $D505 bit 0** selects: 0 = Z80, 1 = 8502
  (MAME `mos8722.cpp`: bit 0 "8500" drives the `Z80EN` output; c64-wiki "Commodore 128/Memory Model").
- **Power-on state is 0, so the Z80 runs first** ("Since this bit is reset to %0 when the system is
  reset or powered on, the Z80 always has control of the system before the 8502", C128 PRG via
  manualslib search summary; MAME and MiSTer reset MCR to 0).
- **How the inactive CPU is held.** MAME: the MMU's `Z80EN` drives the Z80's **BUSREQ**; the MMU's bus
  acknowledge plus VIC BA drive the 8502's **RDY** (`update_rdy`); the 8502's AEC is pulled low while
  the Z80 owns the bus (c64-wiki, marked "unsure"). The consequence (*inference*, consistent with all
  three emulators): neither CPU is reset by a switch — each **freezes mid-program and resumes after the
  instruction that switched**. This is what makes the 8502↔Z80 "ping-pong" of CP/M work.
- **Switch latency.** Z64K's changelog says its "Z80 and 8502 switch timing results match real
  hardware", measured with a CIA timer (C-128 forum thread "Using CIA timer to measure the duration of
  Z80<>8502 switch"); VICE switches inside the MCR store by triggering a "DMA" to the other CPU's main
  loop (`c128mmu.c`, `mmu_switch_cpu`). The cycle count was not found (OQ3).
- **Interrupts.** MAME wires one IRQ merger (CIA1, VIC, expansion IRQ) to **both** the Z80 /INT and the
  8502 IRQ; the NMI merger (CIA2, RESTORE, expansion NMI) goes **only to the 8502**. The Z80's NMI is not
  connected. Interrupt modes 0 and 2 need a vector on the data bus, which nothing on the C128 supplies,
  so only **IM 1** (RST $38) is usable (comp.sys.cbm thread "C128 Z80 — Interrupts", reasoning, not a
  spec). Whether the shipped Z80 ROM/CP/M BIOS enables Z80 interrupts and which mode it sets is OQ6.
  After `EI` the interrupt is taken only after the following instruction, and a run of `EI`s cannot be
  interrupted (VICE bug #1979, confirmed against a cycle-level simulation) — standard Zilog behaviour,
  which Klive's core already has.

### §3.2 The Z80's memory view

- **Z80 ROM window.** Z80 addresses $0000–$0FFF are translated to $D000–$DFFF of the **system ROM in
  U35** (the 4 KB under the 8502's I/O area). Three implementations agree it applies only with RAM bank
  0 selected:
  - MAME `mos8722.cpp`: active when MCR bit 0 = 0 (Z80), CR bit 6 = 0 and the address < $1000; the
    translated address is $D000 | (A & $0F00); MS0/MS1 select system ROM.
  - MiSTer `rtl/mmu8722.vhd` (Erik Scheffers): when CR bits 7–6 = 00, page $00–$0F and the Z80 is
    selected, it forces bank 0, translated page $Dx, ROM bank "system ROM".
  - VICE `src/c128/z80mem.c`: the 4 KB BIOS is visible only in C128-mode configs whose A16/A17 are 0;
    other configs see RAM there.
- **Everything else** goes through the normal MMU translation (CR, common RAM, page pointers), exactly
  as for the 8502 (§4).
- **No I/O in memory space.** In C128 mode a Z80 *memory* read of $D000–$DFFF never reaches the I/O
  chips; VICE serves it from function ROM or RAM according to CR (`z80mem.c`, noting the Z80 "can't
  see charrom" in 128 mode, VICE bug #1987). In C64 mode the Z80 memory map follows the C64 configs
  (I/O visible in configs 13–15).

### §3.3 The Z80's I/O view (IN/OUT)

The Z80 drives the full 16-bit address on I/O cycles (`IN r,(C)` / `OUT (C),r` put BC on the bus), and
the C128 decodes those addresses like memory addresses with a separate "I/O cycle" input (`z80io`) to
the PLA (MAME `c128.cpp`: the Z80 I/O map spans $0000–$FFFF and calls the same `read_memory` with
`z80io = 0`).

VICE's `z80mem.c` (facts) gives the page map:

| Z80 I/O page | Reaches |
|---|---|
| $00–$0F | bank-0 **RAM at $D000–$DFFF** (the RAM that the ROM window hides), unless CR bit 6 is set |
| $D0–$D3 | VIC-IIe |
| $D4 | SID |
| $D5 | MMU (hidden in C64 mode; VICE also blocks it when CR bit 0 = 1) |
| $D6 | VDC |
| $D7 | (C128: unused / expansion) |
| $D8–$DB | colour RAM |
| $DC / $DD | CIA1 / CIA2 |
| $DE / $DF | I/O1 / I/O2 (cartridge) |
| everything else | falls through to the memory map — an I/O cycle reads/writes whatever RAM/ROM is mapped |

(VICE does not name the $D0–$D4 handlers; VIC/SID is the C64 layout — *inference*.) The MMU's LCR
mirror at $FF00–$FF04 is reached by ordinary Z80 memory writes (c128lib startup: the Z80 writes $3E to
$FF00 as a memory store).

### §3.4 The boot hand-over (Z80 first, then 8502)

From c128lib "StartupSequence" (a public walk-through of the ROM; facts restated, not the listing):

1. The Z80 starts at $0000 (the ROM window), writes $3E to $FF00 and jumps on.
2. It writes the MMU: MCR ($D505) = $B0 and reads it back; copies 11 bytes of MMU initialisation to
   $D50A…$D500.
3. It scans the keyboard for the **C= key** (the C64-mode selector) and checks GAME/EXROM (c64-wiki:
   "On initial power up, the Z80 is active, checks GAME/EXROM lines, and hands over control to the MOS
   8502 in C128 MMU mode if neither line is active, or in C64 MMU mode otherwise").
4. It copies an 8-byte stub to $1100 (sets bank 15, jumps through $FFFC) and a 31-byte CPU-surrender
   block to $FFD0, writes $1100 into the 8502's NMI/RESET/IRQ vectors in RAM, and finally writes
   **MCR = $B1** — the 8502 takes over.
5. The 8502 starts at its RESET vector ($1100 in RAM), selects bank 15 (KERNAL ROM) and jumps through
   the ROM's RESET vector ($FF3D → KERNAL RESET at $E000).
6. KERNAL RESET: SEI, stack, CLD; MMU table to $D500…; C64-cartridge detect (→ C64 mode); IOINIT;
   RUN/STOP+SHIFT check; RAMTAS (skipped on warm start when the "DEJAVU" byte $0A02 = $A5); RESTOR;
   CINT (editor, $C000); then the monitor ($B000), BASIC cold start ($4000), or C64 mode ($E24B).
7. BASIC cold start prints the banner and calls PHOENIX ($FF56): runs C128 cartridges/function ROMs and
   tries to **auto-boot from disk** (§7.4).

The surrender block at $FFD0–$FFEF is how either CPU later hands control back (the MCR write is followed
by the code the other CPU resumes into). c128lib notes its own copy of this block is ambiguous, so the
exact bytes must come from running the ROM (OQ7).

*Note for Klive*: the 8502 does **not** start from a reset vector in ROM at power-on on a real C128 —
its first fetch comes from RAM vectors the Z80 wrote. An emulator that resets the 8502 directly into
the KERNAL works for C128 mode but skips the Z80 stage (MAME, VICE and MiSTer all run the Z80 stage;
MiSTer has a `cpumode` reset option to start with the 8502 directly).

### §3.5 How CP/M 3.0 runs

- **Disk side.** CP/M Plus for the C128 boots from a CP/M system disk: the 8502's boot-sector loader
  (§7.4) starts it, the Z80 is switched on, and CPM+.SYS is loaded (Retro Isle "C128 CP/M" article;
  Wikipedia "Commodore 128"). The 4 KB Z80 ROM holds the power-on code and the CP/M boot support; the
  CP/M BIOS proper comes from disk (*inference* from the ROM being 4 KB and CPM+.SYS carrying the
  banked BIOS; the task brief's "BIOS in the Z80 ROM" is only partly right — D7).
- **8502 as I/O processor.** The Z80 BIOS hands serial-bus disk I/O (and other KERNAL-level work) to an
  8502 routine through a shared parameter block in common RAM, flips MCR bit 0, and the 8502 does the
  IEC/fast-serial transfer and flips back (Wikipedia; the comp.sys.cbm thread describes the same
  "switch the 8502 on to serve it, then return" pattern for interrupts). The exact protocol (block
  address, command codes) is in DRI/Commodore's CP/M BIOS sources, which were published; read them for
  facts only if needed (OQ8).
- **Memory.** CP/M runs banked: bank 0 system, bank 1 TPA, with common RAM at the top (§4.4); the MMU
  page pointers relocate page 0 for the Z80 if the BIOS chooses (*inference*: the ROM window occupies
  bank 0's $0000–$0FFF, so the TPA bank must see RAM at $0000 — bank 1 does).
- **Display.** CP/M uses the VDC (80 columns) or a 40-column VIC window onto an 80-column virtual
  screen; slowness is partly the BIOS waiting on the VDC's ready bit (lemon64 t=75034).
- **Disk formats.** On a 1571, CP/M reads several MFM formats (IBM, Kaypro, Osborne, Epson, …) besides
  Commodore GCR (`DRIVE_1541.md` for the drive side).

## §4 MMU 8722

### §4.1 Register map

I/O registers at **$D500–$D50B** (visible when CR bit 0 = 0, i.e. I/O selected) and the **load
configuration registers at $FF00–$FF04**, visible in every configuration in C128 mode. Sources: MAME
`mos8722.cpp` (BSD-3), MiSTer `mmu8722.vhd`, VICE `c128mmu.c` (facts), c64-wiki "Commodore 128/Memory
Model". Where they disagree it is noted.

| Addr | Name | Function |
|---|---|---|
| $D500 / $FF00 | CR | configuration register |
| $D501–$D504 | PCRA–PCRD | pre-configuration registers (CR-format values) |
| $FF01–$FF04 | LCRA–LCRD | **writing any value copies PCRx into CR** (the written byte is discarded); reading returns PCRx |
| $D505 | MCR | mode configuration |
| $D506 | RCR | RAM configuration |
| $D507 / $D508 | P0L / P0H | page-0 pointer |
| $D509 / $D50A | P1L / P1H | page-1 pointer |
| $D50B | VR | version (read only): **$20** |
| $D50C–$D5FF | – | read $FF (VICE) |

### §4.2 CR ($D500 / $FF00)

| Bits | Meaning |
|---|---|
| 0 | 0 = I/O at $D000–$DFFF; 1 = ROM/RAM there |
| 1 | $4000–$7FFF: 0 = system ROM (BASIC low), 1 = RAM |
| 3–2 | $8000–$BFFF: 00 system ROM, 01 internal function ROM, 10 external function ROM, 11 RAM |
| 5–4 | $C000–$FFFF: same encoding |
| 7–6 | RAM bank (bit 6 on a 128 KB machine; bit 7 used only with 256 KB) |

$0000–$3FFF is always RAM. With CR = $00 ("bank 15" in BASIC) the 8502 sees KERNAL/BASIC/I/O; with
$3F it sees bank 0 RAM. MAME stores CR & $7F and reads bit 7 back as 1 (VICE/MiSTer keep 8 bits; D3).

### §4.3 MCR ($D505)

| Bit | R/W | Meaning |
|---|---|---|
| 0 | W/R | CPU select: 0 = Z80, 1 = 8502 |
| 1–2 | – | unused, read 1 |
| 3 | W/R | FSDIR — fast-serial direction (drives the buffer between CIA1 SP/CNT and the IEC DATA/SRQ lines) |
| 4 | R | GAME input (cartridge) |
| 5 | R | EXROM input (cartridge) |
| 6 | W/R | **C64 mode** (1 = C64) |
| 7 | R | **40/80 DISPLAY key**: 1 = up (40 columns), 0 = down (80) |

The 40/80, GAME and EXROM pins are bidirectional with weak pull-ups: a register bit written 0 can pull
the line low (MiSTer outputs `d4080 = input and reg`, likewise GAME/EXROM/FSDIR), and a read reflects
the pin (MAME: a low input clears the bit on read). VICE forces bits 4–5 to 1 on every write.

### §4.4 RCR ($D506): common RAM and the VIC bank

| Bits | Meaning |
|---|---|
| 1–0 | common-area size: 00 = 1 KB, 01 = 4 KB, 10 = 8 KB, 11 = 16 KB |
| 2 | common area at the **bottom** ($0000 up) |
| 3 | common area at the **top** ($FFFF down) |
| 5–4 | unused |
| 7–6 | VIC-II bank (A16, A17): which 64 KB bank the VIC fetches from (bit 7 only with 256 KB) |

Boundaries (MAME): size 0 → below $0400 / from $FC00; 1 → $1000/$F000; 2 → $2000/$E000; 3 →
$4000/$C000. The common area always comes from **bank 0**, overriding CR's bank bits, but ROM/I/O
selection still applies over it. The KERNAL default is 1 KB at the bottom (c64-wiki). MAME masks
writes with $4F (bits 4, 5, 7 not stored) — on a 128 KB machine bit 7 has no effect anyway.

### §4.5 Page 0 / page 1 relocation

- P0L/P1L hold the physical page, P0H/P1H its bank (bit 0 = A16; bit 1 = A17 on 256 KB).
- **Write order matters**: a write to P0H/P1H only latches; the value takes effect when P0L/P1L is
  written (MAME, MiSTer, VICE all agree).
- Reset: P0 = page $00, P1 = page $01, bank 0. VICE and c64-wiki read P0H/P1H with the upper nibble set
  ($F0/$F1-style); MAME stores only bit 0; MiSTer stores 4 bits (D4).
- Effect: CPU accesses to page 0 ($00xx) and page 1 ($01xx) go to the pointed page; **and the pointed
  page is swapped back**: an access to that page in the pointer's bank lands on physical page 0/1
  (MAME, MiSTer). The swap does not apply where I/O is selected at $Dxxx (MiSTer). In C64 mode the
  relocation is off.
- The 8502 uses this for fast zero-page/stack per task; the Z80 is subject to it too.

### §4.6 Version register and RAM expansion

VR reads **$20** in every emulator and on stock machines. VICE's comment: a value of $40 would mean a
4-bank (256 KB) MMU configuration, unconfirmed on hardware. Widely quoted reading (c128lib-style docs):
high nibble = number of 64 KB banks the MMU supports? (2), low nibble = MMU revision (0) — *not verified
in a primary source* (OQ9). VICE (`c128_full_banks`) and MiSTer (`sys256k`) implement banks 2/3 as an
option; no shipped model has them.

### §4.7 C64 mode

- Setting **MCR bit 6** switches to C64 mode. It is **one-way**: in C64 mode the MMU's I/O registers
  vanish (MAME: reads return the bus value, writes are ignored, translation is bypassed; VICE marks the
  MMU page "unconnected" in C64 mode) and $FF00 is ordinary memory, so only a reset returns to C128
  mode.
- Entry paths: KERNAL GO64 (BASIC `GO64`), the **C= key** held at reset, or a C64 cartridge pulling
  GAME/EXROM at reset (KERNAL RESET step 6; Z80 stage §3.4).
- In C64 mode the 8502 port bits 0–2 act as LORAM/HIRAM/CHAREN and the PLA reproduces the C64 map
  (c64-wiki); the 2 MHz bit and the extra keyboard rows remain available (they are VIC-IIe features),
  and the VDC stays reachable at $D600 (*inference*: VICE keeps the $D6 page mapped to the VDC in the
  C64-mode Z80/8502 I/O tables).

### §4.8 What the PLA (8721) decides

The MMU only translates addresses and outputs mode lines (MS0–MS3, CAS0/CAS1, Z80EN, FSDIR, 128/64);
the 8721 PLA turns those plus LORAM/HIRAM/CHAREN, GAME/EXROM, BA/AEC, the Z80 I/O signal and the
address into chip selects: ROM1 (U32, C64 ROM), ROM2/3 (U33/U34 BASIC), ROM4 (U35 KERNAL/editor/Z80),
FROM (U36, internal function ROM), CHAROM (U18), colour-RAM bank, I/O, ROML/ROMH (c64-wiki; MAME
converts the PLA's published equations, `8721-reduced.txt` on zimmers.net, into a table). The **colour
RAM is 2 KB in two 1 KB banks**: the CPU's bank comes from port bit 0 and the VIC's from port bit 1 in
C128 mode, so the two can see different banks; BASIC uses bank 1 for text colours (c64-wiki; MAME's
`m_clrbank` from the PLA). The VIC sees the character ROM at $1000/$5000/$9000/$D000 of its bank unless
port bit 2 hides it (c64-wiki).

## §5 VDC 8563 / 8568

### §5.1 Access

- **$D600 write** selects the register (low 6 bits). **$D600 read** is the status register.
- **$D601** reads/writes the selected register.
- Status ($D600 read): **bit 7 = ready** (1 = the chip has finished the last update; poll with
  `BIT $D600 / BPL`), **bit 6 = light-pen latched**, **bit 5 = vertical blank**, bits 4–3 = 0, **bits
  2–0 = version** (§1.2). (C128 PRG via manualslib summary; MiSTer `vdc_top.sv`.)
- The KERNAL wraps the access in routines at $CCDA/$CCDC (Wikipedia "MOS Technology 8563").
- VDC RAM is **not** CPU-visible; everything goes through R18/R19 (update address) and R31 (data, which
  auto-increments R18/R19).

### §5.2 Registers (37 on the 8563, R0–R36; R37 on the 8568)

Bit layouts from MAME `mos8563.cpp` and MiSTer `vdc_top.sv`; reset/KERNAL values from the MiSTer table

### §5.3 Timing

- **Dot clock 16 MHz** from the VDC's own crystal (MAME `XTAL(16'000'000)`; VICE `vdc.c` converts with
  a 16 MHz dot clock). It is **not locked to the VIC/CPU clock**: the CPU-to-VDC phase drifts, which
  shows up as jitter in VDC/VIC timing measurements (c-128.freeforums "VDC raster split" thread,
  willymanilly: "the VDC and VIC-II use different clocks").
- Character clock = (R22 bits 7–4) + 1 dots, normally 8 (doubled in pixel-double mode).
- Line: (R0 + 1) × 8 dots. KERNAL R0 = 126 → 1016 dots = **63.5 µs (15.748 kHz)**; with R0 = 127,
  64 µs (15.625 kHz). VICE's comment: default KERNAL values give "about 64 µs" PAL and "63.5 µs" NTSC.
- Frame (my arithmetic from the KERNAL values, *inference*): NTSC R4 = 32 → 33 rows × 8 = 264 lines →
  ~59.7 Hz at 63.5 µs; PAL R4 = 39 → 40 × 8 = 320 lines → 49.2 Hz at 63.5 µs or 48.8 Hz at 64 µs. The
  VDC is therefore a CGA-like 15.7 kHz RGBI monitor signal in both regions; 50 Hz units output a
  non-CGA frame rate that many CGA monitors still accept (Wikipedia).
- **Memory fetch schedule per scan line** (logic-analyser measurements by "remark", PAL, 80×25 text,
  R0 = 127, c-128.freeforums post 5516, 2020): 80 character-pattern fetches, then R36 refresh cycles (5),
  then on the first two lines of a row 40 screen-pointer fetches, on lines 3–4 40 attribute fetches,
  otherwise idle; ~3 idle cycles at the end. So the 80 screen and 80 attribute bytes of the *next* row
  are prefetched spread over the current row's lines. With R36 = 15 the refresh takes 15 slots. In a
  480-wide colour bitmap mode (R0 = 126, R36 = 0): 60 bitmap + 60 attribute fetches + 7 idle; going
  below ~5 idle cycles per line corrupts the display (tokra).
- **CPU access to VDC RAM uses the idle slots.** The ready bit stays clear until the VDC has had a free
  slot to perform the R31 read/write or the next block-op word. *Inference* from the fetch schedule and
  from the MiSTer RAM interface ("perform CPU action" in the free slots): the ready-bit latency — and
  so CP/M's and the editor's speed — depends on the display mode, which is why a faithful model fetches
  per character clock. MAME instead completes one block-op byte per character clock unconditionally
  (`mos8563.cpp`); VICE's `vdc.c` renders once per raster line and its block ops are not timed in the
  part read.
- **Light pen** can be triggered from CIA1 PB4 like the VIC-II's and repeatedly per frame; the latched
  values are character-counter positions (thread above). Demos use this to measure VDC timing against
  the VIC.

### §5.4 Block copy / fill, R31 auto-increment

- R30 = word count (1–255; 0 = 256 *inference*, OQ10). Writing R30 starts the operation at the update
  address R18/R19. **Fill** (R24 bit 7 = 0) writes the last byte written to R31; **copy** (bit 7 = 1)
  copies from R32/R33. Both addresses advance; ready goes low until done (MAME; MiSTer `vdc_ramiface.sv`:
  updating word count starts the op, "does not change WC or DA"; reading DA loads the next value).
- The blitter runs concurrently with the CPU; the screen editor uses it for scrolling and clearing
  (Wikipedia).

### §5.5 Modes

Text (8×N cells from a font in VDC RAM — there is **no character ROM**; the KERNAL copies the VIC's
patterns into VDC RAM at start-up), attribute mode, bitmap (640×200 standard; interlace up to 640×400
and beyond with 64 KB; demo modes up to 720×700 or 800×600 mono, FLI-style colour modes rewriting
attributes per line), semigraphics, double-width (40 columns), reverse, blink, underline, cursor
(Wikipedia; vdcmaniac blog; MAME). 16 KB machines are limited to text and 640×200 monochrome bitmap
(16 000 bytes); colour bitmap needs 64 KB (*inference* from the sizes).

### §5.6 16 KB vs 64 KB

- 16 KB = two 16K×4 DRAMs (4416); 64 KB = two 64K×4 DRAMs. The address multiplexing differs, so **R28
  bit 4 must match the fitted RAM**: MAME linearises the address when bit 4 = 1 and applies a fixed bit
  shuffle when 0; MiSTer's `ram64k` input plus R28 bit 4 ("0 = 16k accessible, 1 = 64k accessible").
  The KERNAL leaves bit 4 = 0 (16 KB layout), so a 64 KB machine runs stock software in 16 KB mode.
  (elektronaut/badline PR #518 calls the 64 KB parts "4164" — D6.)
- **Detection** (*inference*, OQ11): set R28 bit 4, write distinct values to two addresses that alias in
  a 16 KB machine (e.g. $0000 and $8000 or $2000), read back; equal values mean 16 KB.

### §5.7 Revisions and known quirks

- R7A vs R8/R9: horizontal smooth scroll (R25 3–0) and its reset/KERNAL value differ (FalvoTech; MiSTer
  "0 for v0, 7 for v1"); the KERNAL reads the version and initialises accordingly.
- 8568: R37 sync polarity (a "38th register" used for an inverted-sync EGA-monitor mode, c-128
  forum t=502); different pinout (a separate composite-sync/interrupt arrangement — not confirmed, OQ12).
- Early 8563s had yield/heat problems and **timing faults that break indirect register loads and
  stores** (Wikipedia) — the reason software must poll the ready bit even for register (not RAM)
  accesses on some chips (*inference*).
- MiSTer TODO list: some high-resolution interlace bitmap modes misbehave (fetch alignment; odd lines
  per row); "VSS exceeding CTV should result in solid line(s) at field start"; cursor lines wrong in
  interlace. MAME has one FIXME: its interlace address-counter behaviour after R6 is fitted to results,
  not derived from hardware. VICE: interlace is a known weak spot on all revisions (feature request
  #144); `vdc.c` has FIXMEs on hsync constants ("semi-randomly selected"), light-pen timing, and active
  display starting left of the screen.
- A real-hardware stall (~15 s) in a 512-byte per-byte-handshaked transfer under one interlace mode was
  not reproduced by VICE or Z64K (vdcmaniac blog) — a measure of how far emulated ready-bit timing is
  from silicon.

### §5.8 Output

Separate **RGBI** connector (DE-9, CGA-compatible: R, G, B, intensity, HSYNC, VSYNC; 16 colours =
8 colours × 2 intensities) plus a monochrome composite signal on pin 7 (forum t=502: white, two greys
and black; works on flat and D machines, reported "a bit blurry" on a DCR). Klive needs an RGBI palette (VICE ships several; MiSTer has
"multiple colour palettes") and a second screen: the C128 drives two monitors at once (MiSTer offers
side-by-side; VICE a second window; MAME a second `screen80`).

### §5.9 What accuracy matters (*inference* from the sources above)

1. **Software-visible timing is only through $D600/$D601**: the ready bit, the VBLANK bit, light pen.
   A model that clocks the VDC at 16 MHz in its own time base and converts to φ0 (VICE uses a 16.16
   fixed-point step per line; Klive could do the same per character clock) is sufficient for ordinary
   software.
2. **Demos** (Risen from Oblivion VDC v2, VDC Mode Mania, Colour Spectrum) rewrite R4–R9/R12–R13/R20–R21/
   R27 mid-frame and rely on when the VDC latches row addresses ("attribute latching occurs at the end
   of the last line"; text display memory latches at the start of the last line — willymanilly). They
   need the per-character-clock fetch schedule, the latch points and the exact R0/R4/R5/R7 behaviour.
3. **Per-line rendering** (VICE) is enough for the 80-column editor, CP/M and GEOS 128.
4. The VDC needs no coupling to the VIC's cycle stepper; it can be a separate clocked device stepped
   to the CPU's current φ0 time whenever $D600/$D601 is touched and at frame end ("catch-up" model).

## §6 Keyboard

### §6.1 Matrix

The C64's 8×8 matrix (CIA1 port A drives columns, port B reads rows: `C64_SYSTEM.md`) plus **three
extra drive lines K0–K2** from VIC-IIe **$D02F bits 0–2**, read on the same CIA1 port B. MAME
`cia1_pb_r` ANDs a K row in when the matching $D02F bit is 0. Extra keys (MAME input ports, port-B bit
in brackets):

| Line | bit 7 | bit 6 | bit 5 | bit 4 | bit 3 | bit 2 | bit 1 | bit 0 |
|---|---|---|---|---|---|---|---|---|
| K0 | KP 1 | KP 7 | KP 4 | KP 2 | TAB | KP 5 | KP 8 | HELP |
| K1 | KP 3 | KP 9 | KP 6 | KP ENTER | LINE FEED | KP + | KP − | ESC |
| K2 | NO SCROLL | → (top row) | ← | ↓ | ↑ | KP . | KP 0 | ALT |

- The top-row cursor keys are separate keys from the C64-style CRSR keys (MiSTer README: "top-row
  cursor keys").
- **CAPS LOCK** (ASCII/DIN on national machines) is a latching key read on the **8502 port bit 6**
  (input) — MAME `cpu_r`: port bit 6 = CAPS LOCK, bit 4 cassette sense, bits 0–2 read back as 1.
- **40/80 DISPLAY** is a latching key read on **MMU MCR bit 7** (§4.3); the KERNAL reads it at reset
  and on RUN/STOP-RESTORE to choose the screen.
- **SHIFT LOCK** is a mechanical latch in parallel with left SHIFT (MAME gates row 1 with it).
- **RESTORE** goes to the NMI merger (§3.1).
- **ALT** is in K2 bit 0 (not on the CPU port, despite the brief's guess).
- On a VIC-IIe the low 3 bits of $D02F hold the written K-line value and the other bits read 1
  (*inference*; VICE treats $D02F/$D030 as VIC-IIe registers only when `viciie` is set). On a C64
  VIC-II (6567/6569) both read $FF; software uses that to detect a C128 running in C64 mode.

### §6.2 For auto-typing

The KERNAL scans K0–K2 in C128 mode only; in C64 mode the C64 KERNAL scans the 8×8 matrix (the extra
keys read as nothing unless software scans them). The C128 keyboard buffer is commonly given as 10
bytes at **$034A** with the count at **$D0** (vs $0277/$C6 on the C64) — from memory of the C128 memory
maps, **unverified** (OQ13); establish by running the ROM.

## §7 C128-mode software environment

### §7.1 ROM layout (8502 view, CR = $00)

| Range | Chip | Content |
|---|---|---|
| $4000–$7FFF | U33 | BASIC 7.0 low |
| $8000–$AFFF | U34 | BASIC 7.0 high |
| $B000–$BFFF | U34 | machine-language monitor |
| $C000–$CFFF | U35 | screen editor (CINT at $C000) |
| $D000–$DFFF | U35 | **Z80 ROM** (hidden by I/O for the 8502) |
| $E000–$FFFF | U35 | KERNAL (RESET at $E000) |
| (C64 mode) $A000–$BFFF, $E000–$FFFF | U32 | C64 BASIC 2.0 and KERNAL |

(c64-wiki ROM table; c128lib for the entry points; MiSTer `boot0.rom` order "ROM1 C64 BASIC+KERNAL,
ROM4 editor+Z80 BIOS+KERNAL, ROM2+3 BASIC, char ROM".) The character ROM holds the C64 set and the
C128 (or national/ASCII) set, 4 KB each.

### §7.2 BASIC 7.0 memory map (essentials)

- BASIC **program text in bank 0 starting at $1C01** ($1C00 = 0). When a bitmap is allocated
  (`GRAPHIC 1`, bitmap at $2000–$3FFF) the program is moved to **$4001**.
- **Variables, arrays and strings in bank 1** (from $0400), so a program gets ~58 KB of text and ~64 KB
  of variables.
- 40-column VIC text at $0400 (bank 0), colour in colour-RAM bank 1; the VDC's screen at VDC $0000,
  attributes at VDC $0800, font at VDC $2000 (KERNAL values, §5.2).
- Banks as BASIC sees them (`BANK 0..15`) are MMU CR presets; BANK 15 = CR $00 (ROMs + I/O).
- *Sources*: C128 PRG ch. "Memory map" (pagetable.com PDF, not fetched in full this session) and common
  knowledge; the $1C01/$4001 facts are also what MiSTer's PRG injection detection relies on ("Direct
  file injection with detection of C128 or C64 mode" — a $1C01 load address means C128 mode). OQ14 asks
  for verification against the ROM.

### §7.3 Program loading and injection (*inference* for Klive)

- A C128 BASIC `.prg` has load address $1C01; a C64 one $0801. After injecting, the BASIC pointers
  (start/end of text, start of variables in bank 1) must be set the way the KERNAL's LOAD + BASIC's
  relink would leave them, or the program is typed `RUN` after a real `LOAD` through the KERNAL. Klive's
  Run of machine code can stage a `SYS` program in bank 0 (above $1C01, below $4000) and type `RUN`.
- Reset landmark for "BASIC is ready": the editor's key-wait loop after the READY. prompt; take the
  address from running each ROM revision (r2/r4/DCR, national), not from a listing.

### §7.4 Auto-boot from disk and function ROMs

- **Boot sector** (PHOENIX → BOOT_CALL at $FF53): the KERNAL reads **track 1 sector 0** of drive 8 into
  $0B00; if it starts with **"CBM"** it reads the header — load address and bank for additional sectors,
  their count, a zero-terminated message printed as "BOOTING …", a zero-terminated file name to load
  and run — and then calls the code that follows. CP/M disks and many commercial titles boot this way.
  (From the C128 PRG's boot-sector description as remembered; the exact byte offsets are OQ15 — take
  them from the PRG text, which is not a ROM disassembly.)
- **Function ROMs**: internal socket U36 (CR $8000–$FFFF encoding 01) and external (10). At reset the
  KERNAL polls both at $8000 and $C000 for a **"CBM" signature at offset 7** and an ID byte at offset 6,
  and calls the ROM's cold-start entry; PHOENIX later calls installed C128 cartridges "regardless of ID"
  (c128lib). Offsets from memory — OQ15.
- C64 cartridges are detected by the Z80 stage/KERNAL through GAME/EXROM (§3.4) and force C64 mode.

## §8 Fast serial (burst) to the 1571

- **Hardware**: CIA1's serial port is connected to the IEC bus through a bidirectional buffer: **SP ↔
  DATA, CNT ↔ SRQ**; the direction is **MMU MCR bit 3 (FSDIR)** (MAME `update_iec`: with FSDIR = 1 the
  CIA's SP/CNT drive DATA/SRQ, otherwise DATA/SRQ feed SP/CNT; c64-wiki "Fast serial bus protocol" and
  search sources describe the same buffer "controlled by the MMU"). MAME also routes **SRQ to CIA1's
  FLAG** input. The user port's SP1/CNT1 pins share the same CIA lines.
- **Protocol** (c64-wiki "Fast serial bus protocol"): SRQ is the clock; DATA carries the bits, **MSB
  first**; the talker holds CLK low for the whole byte; the listener samples on SRQ's rising edge. The
  C128 sends at 10 µs per bit (SRQ 5 µs low/5 µs high), the 1571 at 7 µs (3/4). "Host request fast": the
  computer sends $FF (eight SRQ pulses) before ATN; a fast device answers with $00 when asked to listen.
  A listener accepts either protocol depending on whether CLK or SRQ moves first. **Burst mode** is the
  same hardware driven by explicit "U0" burst commands (MFM/GCR sector reads, fast load).
- **What an emulator needs** (*inference*): a CIA serial port with correct shift timing in both
  directions (`C64_SYSTEM.md`), the FSDIR buffer, SRQ on the IEC bus model, and a 1571 whose own CIA
  serial port and firmware are emulated (`DRIVE_1541.md`). A 1541 ignores SRQ, so slow fallback must
  keep working.
- **MFM vs GCR**: the 1571 reads Commodore GCR (1541-compatible, double-sided) through its 1541-style
  logic and MFM (CP/M and PC formats) through a WD1770/1772 controller; the DCR's internal drive is the
  cost-reduced variant. Drive internals belong to `DRIVE_1541.md`. Note that Klive already has a
  WD1793-family core shared by the Beta 128, TVC, Enterprise and SAM (`wd1793.c` with 1770/1772
  variants) — a 1571 could reuse it (*inference*).

## §10 Consequences for the architecture (*inference*, for the plan to weigh)

1. **Klive's Z80 core is reusable inside the C128 core.** Count T-states as half-φ0 ticks, no
   contention delays, a BA stall from the VIC-IIe at least at M-cycle granularity, IM 1 only, NMI not
   connected, BUSREQ-style freeze/resume on MCR bit 0. The 8502 and the Z80 must share one φ0 clock
   and one memory/IO funnel (the MMU + PLA translation), with the Z80's I/O cycles flagged so the PLA
   can tell them from memory cycles.
2. **The debugger has two CPUs.** Breakpoints, history and stepping must know which CPU is active;
   "step over" an MCR write that switches CPUs ends on the other CPU (VICE switches its monitor's CPU
   type on the switch).
3. **The VDC is its own clock domain** (16 MHz, free-running relative to φ0). A catch-up model stepped
   per VDC character clock, synchronised on $D600/$D601 access and at frame end, is the natural fit.
   Two video outputs (VIC 40-column, VDC 80-column) need two canvases.
4. **ROM handling**: four 16 KB chips (flat/D) vs two 32 KB chips (DCR) plus national char ROMs; the
   Z80 ROM is a 4 KB slice of the KERNAL chip, not a separate file.
5. **The boot runs through the Z80.** An honest power-on runs the Z80 stage; a "boot straight into the
   8502" option is a convenience, not the default.

## Disagreements between sources

- **D1 — Z80 speed.** "4 MHz with wait states, effectively 2 MHz" (Commodore marketing, most secondary
  sources) vs "2 clock ticks per φ0 half-cycle, no wait states, every memory/IO transaction at 1 MHz"
  (ytmytm hardware analysis; VICE `z80.c`; bug #1979 measurements). Same throughput; the second is the
  mechanism. A residual 2-cycle per-line variation on hardware is unexplained (OQ1).
- **D2 — What the Z80 checks at power-on.** c64-wiki: GAME/EXROM; another source: CP/M disk, cartridges
  and the C= key; c128lib: MMU test, timers, keyboard (C= key), then hand-over. The CP/M-disk check is
  done by the 8502's boot routine, not the Z80 (*inference*). Run the ROM.
- **D3 — CR bit 7 read-back.** MAME stores 7 bits and reads bit 7 as 1; VICE and MiSTer store all 8.
  On 128 KB machines bit 7 is irrelevant to mapping.
- **D4 — P0H/P1H width.** MAME 1 bit, MiSTer 4 bits, VICE reads upper nibble as 1s; c64-wiki gives
  reset values $F0/$F1-style reads. Upper-bit read-back needs a hardware check.
- **D5 — VDC version numbers.** MiSTer: 8563R9 → 1, 8568 → 2; c128lib: R7A → 0, R8/R9 → 1; MAME returns
  1 for both 8563 and 8568.
- **D6 — 64 KB VDC RAM part.** "4164" (badline PR) vs 64K×4 parts (two chips for 64 KB) — two 4164s
  (64K×1) could not give 64 KB on an 8-bit bus, so "4164" is probably loose wording (*inference*).
- **D7 — "CP/M BIOS in the Z80 ROM".** The ROM is 4 KB and holds boot code; the CP/M BIOS is loaded
  from CPM+.SYS (*inference*, OQ8).
- **D8 — Z80 ROM window condition.** MAME: Z80 selected, CR bit 6 = 0. MiSTer: Z80 selected, CR bits
  7–6 = 00. VICE: A16 = A17 = 0 configs. Identical on 128 KB machines; differ only with bank 2/3.
- **D9 — VDC R0 on PAL.** MiSTer: KERNAL writes 126, the PAL DCR 127; VICE: PAL ≈ 64 µs (implies 127);
  remark's PAL measurements used 128 character clocks. Whether the flat PAL KERNAL writes 126 or 127 is
  unverified (OQ17).
- **D10 — Badline stall in 2 MHz mode.** VICE steals no badline cycles in fast mode (the VIC display is
  garbage anyway); no hardware measurement found either way.
